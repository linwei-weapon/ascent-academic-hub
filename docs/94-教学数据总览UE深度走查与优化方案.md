# 教学数据总览 UE 深度走查与优化方案

> 版本：V1.0
> 模块：教学管理分析 / 教学数据总览
> 状态：已确认，按 T1—T7 分步实施
> 共同基线：`docs/93-教学管理分析UE公共契约.md`

## 1. 本次走查范围

本次不是只检查首页视觉，而是按真实管理操作路径检查了：

1. 教学数据总览首页；
2. 学院详情；
3. 专业详情；
4. 课程详情；
5. 学生名单与学生核查抽屉；
6. 完整学生档案的进入与返回；
7. 教务处、二级学院、辅导员三类身份；
8. 指标的后端计算、统计周期、数据来源和前端名称；
9. 页面加载、重复请求、下钻条件继承和权限边界；
10. 表格列设置与公共契约的差距。

本模块的合理定位应是：

> 用稳定的事实页面帮助管理者判断“当前整体情况、与上期相比发生了什么、哪些学院/专业/课程偏离、应下钻核查什么”，不代替预警处置、培养方案核查或 AI 决策研判。

## 2. 当前页面实际表现

### 2.1 正面基础

- 已形成“全校—学院—专业—课程—学生”的主要下钻链路。
- 已在页面展示当前身份、明细范围和统计学期。
- 学院横向表已经包含加权平均分和平均 GPA。
- 二级学院可以看本院明细，也可以看其他学院聚合对比，权限边界基本正确。
- 学生名单详情采用当前页抽屉，避免了每次查看学生都离开清单。
- 主要 KPI 已有公式 Tooltip，真实、合成和受限数据已有初步披露。

这些能力可以保留，但目前尚未形成稳定、可信、可执行的管理总览。

### 2.2 实测样例

以教务处身份、`2025-2026-2` 学期为例，首页显示：

- 在籍学生 12,670 人；
- 当前预警 3,603 人；
- 当前挂科率 36.1%；
- 历史挂科经历率 89.6%；
- 首次通过率 95.7%。

这些数字被平铺展示，但页面没有直接告诉管理者：

- 与上一学期相比是改善还是恶化；
- 哪些学院对全校变化贡献最大；
- 3,603 名预警中哪些是本学期新增、持续或升级；
- 36.1% 的分母是否都有本学期有效成绩；
- 89.6% 的历史挂科经历率为何值得在当前首屏重点关注；
- 应先核查学生、专业还是课程。

## 3. 已确认问题

### 3.1 P0：下钻后的分析范围会静默扩大

从“人工智能学院—计算机科学与技术—新青年·习党史”进入课程详情时：

- 专业年级表中该课程样例为 12 人修读；
- 课程详情变为全校当前学期 75 人；
- 页面仍保留学院和专业面包屑，容易让用户误以为仍在专业范围；
- 再进入学生名单后，结果变为历史上修过该课程的 2,118 人。

根因：

- 课程详情接口只接收课程和学期，不接收来源学院、专业、年级等分析范围；
- 学生名单的课程条件不与学期绑定，实际查询的是所有历史学期修过该课程的学生；
- 页面把“导航来源”误当成“当前统计范围”，没有单独展示口径变化。

风险：

- 同一条操作链路的数字无法核对；
- 管理者可能基于不同范围的数据进行错误判断；
- 面包屑看似正确，但数据语义已经改变。

### 3.2 P0：专业学生名单首次进入可能显示全校结果

从专业详情进入学生名单后，页面筛选框已显示：

- 人工智能学院；
- 计算机科学与技术；
- `2025-2026-2`。

但首次结果显示“共 12,670 名学生”，即全校人数。手动点击一次“查询”后才恢复为 586 人。

根因是两个请求竞态：

1. `DataTable` 恢复用户的每页行数偏好并触发一次列表加载；
2. 页面完成 URL 筛选初始化后再次加载；
3. 先发出的全校请求较慢，最后返回并覆盖了正确的专业结果。

这不是偶发现象，而是当前组件初始化顺序导致的稳定风险。

### 3.3 P0：所选学期与课程通过率的统计周期不一致

首页标注统计学期为 `2025-2026-2`，但以下指标实际读取 V2 全学期累计：

- 首次通过率；
- 补考通过率；
- 重修通过率；
- 公共必修首次通过率；
- 挂科集中课程表中的三类通过率。

旧口径“末次通过率”也使用跨学期累计，而不是所选学期。

结果是同一页面和同一表格中混合了：

- 所选学期的挂科人数、平均分；
- 全历史累计的首次、补考和重修通过率；
- 当前时点的有效预警。

页面虽然在副标题中写了“全学期累计加权”，但整体筛选语义仍会让用户认为所有数据都受所选学期控制。

### 3.4 P0：同名指标存在不同聚合算法

当前各层级对平均 GPA 的计算并不统一：

- 总览和跨学院聚合：先算每名学生当前学期课程 GPA 均值，再对学生求平均；
- 学院专业表：直接对专业全部成绩记录的 GPA 求平均；
- 专业年级详情：直接对年级全部成绩记录的 GPA 求平均；
- 学生名单：按筛选学期计算每名学生的课程 GPA 均值。

修读课程多的学生会在后两种算法中获得更高权重，因此同一专业在不同页面可能出现不一致结果。

挂科率也混用了两种对象：

- “至少一门未通过的学生数÷学生数”；
- “未通过成绩人次÷修读人次”。

当前名称有时都写成“挂科率”，用户无法仅凭页面判断分子分母。

### 3.5 P0：缺失数据被展示为健康的 0

辅导员身份实测范围为 89 名学生，但当前学期没有可关联的开课、教师和有效成绩时，页面显示：

- 本学期开课 0；
- 相关授课教师 0；
- 当前挂科率 0%；
- 当前预警 0；
- 应届毕业率 0%（0/0）；
- 学位授予率 0%（0/0）。

“无数据”“不适用”和“真实为 0”被混成同一种展示，0% 会被误读为情况正常。

### 3.6 P1：首页首屏信息多，但管理聚焦不足

教务处首页首屏包含：

- 6 个在校生指标；
- 2 个合成毕业指标；
- 5 个课程通过率指标；
- 一条较长的证据警告。

二级学院和辅导员还会看到 5 张全部为“—”的全校课程通过率卡片。首屏占用很大，但没有给出“变化、偏离、优先核查对象”。

尤其是：

- 在籍人数、教师数和开课门数属于范围背景，不应与风险指标争夺同等视觉权重；
- 历史挂科经历率 89.6% 过于饱和，缺少当前管理区分度；
- “末次通过率（旧口径）”不应继续占据正式 KPI 卡；
- 合成毕业率、学位率不应作为默认正式管理结论。

### 3.7 P1：学院聚合对比仍需要用户自己找问题

二级学院可以看到全校学院聚合，这是正确的权限设计，但当前只平铺所有学院：

- 没有本院排名；
- 没有与全校均值的差值；
- 没有分位位置；
- 没有按某一管理指标切换排序；
- 没有指出本院最需要核查的偏离项。

用户只能逐行肉眼寻找差异，尚未把“可比较”转化为“可判断”。

### 3.8 P1：学院和专业页的比较语义不够准确

- 专业表中的“对比全院”只有红色上箭头和绿色下箭头，缺少差值和方向说明；
- 当前挂科率与全院平均值的比较没有统计基数提示；
- 学院“各年级课程学分通过占比”容易被理解为培养方案完成度；
- 专业页“培养方案完成率”混合了合成毕业表已修学分与真实方案总学分；
- 专业页毕业率和就业去向来自合成数据，却占据正式分析区域。

### 3.9 P1：专业详情过长，所有年级明细同时展开

专业详情默认展开每个年级和每个年级的挂科课程表，导致：

- 页面纵向过长；
- 用户不能快速识别最异常年级；
- 各年级被赋予相同视觉权重；
- 课程表反复出现相同表头；
- 查看一个年级需要在大量信息中滚动。

### 3.10 P1：课程详情的班级含义和完整性不清

“各班级详情”实际按学生行政班统计，不一定等同于教学班。

同时：

- 只返回 6 个班级，但页面没有标明 TOP6；
- 没有解释排序依据；
- 平均分和成绩分布的分母可能包含成绩为空的记录；
- 分数段占比可能因空成绩而不能合计到 100%；
- 从专业或学院进入后，没有明确展示当前是“全校课程”还是“来源范围课程”。

### 3.11 P1：学生核查链路丢失工作现场

- 学生名单标题同时有学院和专业时，只显示学院名称；
- 在学生名单抽屉中打开完整档案后，“返回”直接回专业详情，不回学生名单；
- 列表的分页、滚动位置和已应用筛选不能得到可靠恢复；
- 列表中的 `GPA` 没有说明是所选学期 GPA 还是累计 GPA；
- 全局路由没有统一滚动恢复策略，新页面可能继承上一页滚动位置。

### 3.12 P1：加载耗时与反馈仍有改进空间

同一台原型环境、热服务、教务处身份的接口实测：

| 接口 | 单次耗时 |
|---|---:|
| 教学数据总览 | 约 2.58 秒 |
| 学院详情 | 约 1.57 秒 |
| 专业详情 | 约 1.34 秒 |
| 课程详情 | 约 0.02 秒 |
| 专业学生名单 | 约 0.12 秒 |

浏览器中的学院、专业页面完整呈现约为 4 秒体感。当前总览还会先请求主体、再串行请求跨学院比较，受限角色等待时间更长。

学院接口存在逐专业查询，专业接口存在逐年级查询；前端主要使用整页加载遮罩，没有分区骨架和请求失效保护。

### 3.13 P1：表格实现尚未达到公共契约

现有 `DataTable` 已支持：

- 显示/隐藏列；
- 上移/下移列；
- 行密度；
- 每页行数；
- 浏览器本地偏好。

但仍缺少：

- 拖拽调整列顺序；
- 必选列；
- 最大显示列数；
- 左侧识别列、中间业务列、右侧操作列的区域约束；
- 工作身份隔离；
- 配置版本；
- 对初始化页容量偏好的安全回写；
- 主要原生 `el-table` 的统一迁移。

## 4. 目标管理逻辑

### 4.1 校领导和教务处

页面应优先回答：

1. 本学期成绩数据覆盖是否足够形成判断；
2. 当前学业结果与上一学期相比是改善还是恶化；
3. 哪些学院偏离全校基线；
4. 哪些课程影响学生最多；
5. 从哪一项进入可核查的学院、专业、课程或学生证据。

### 4.2 二级学院

页面应优先回答：

1. 本院在全校处于什么位置；
2. 本院哪一个专业、年级或课程是主要风险来源；
3. 本院变化是局部异常还是持续问题；
4. 可以下钻查看哪些本院明细；
5. 他院数据只用于聚合参照，不能误导为可查看明细。

### 4.3 辅导员、班主任和导师

综合教学总览不是这三类角色的主要工作入口。

建议：

- 默认入口继续为“我的班级/学生”或“学业预警监控”；
- 如保留“教学数据总览”，只展示授权学生范围的紧凑事实摘要；
- 不展示不适用的全校课程指标、合成毕业指标和跨院比较；
- 数据缺失时显示覆盖不足，不显示健康的 0%；
- 明确引导进入“我的班级/学生”完成个体核查。

## 5. 建议的信息架构

### 5.1 教学数据总览首页

#### A. 当前分析上下文

保留：

- 当前工作身份；
- 明细范围；
- 所选学期；
- 数据更新时间。

新增：

- 当前学期有效成绩覆盖学生数/范围内学生数；
- 预警指标为“当前时点快照”的说明；
- 数据不足时的醒目标识。

#### B. 管理摘要

默认只保留 4 个核心管理指标：

1. 当前挂科学生率：当前学期至少一门未通过学生数÷当前学期有有效成绩学生数；
2. 平均 GPA：先算学生学期 GPA，再对学生求平均；
3. 当前有效预警学生率：当前有效预警学生数÷授权范围学生数；
4. 当前学期首次通过率：当前学期首次修读通过人次÷当前学期首次修读人次。

每张卡同时显示：

- 人数或人次；
- 与上一可比学期的变化；
- 数据覆盖；
- 是否可下钻。

在籍学生、开课门数、授课教师数改为紧凑的“范围背景”，不再作为同权 KPI。

历史挂科经历率移入“持续风险结构”，不再占首屏核心卡。

#### C. 学院比较与偏离

学院表默认列建议为：

1. 学院；
2. 有效成绩学生数；
3. 当前挂科学生率；
4. 较全校差值；
5. 平均 GPA；
6. 当前预警学生率；
7. 较上期变化；
8. 详情。

交互建议：

- 支持按“挂科学生率、平均 GPA、预警学生率、变化幅度”切换排序；
- 本院角色固定高亮本院；
- 展示本院排名和与全校均值差；
- 他院行保持“仅聚合比较”，不提供伪点击效果；
- 列设置遵守公共契约，默认不超过 8 个业务列。

#### D. 重点课程影响

把“挂科集中课程 TOP8”改为“本学期重点核查课程 TOP10”。

排序不再只看挂科率，至少综合：

- 未通过学生人数；
- 修读规模；
- 首次未通过率；
- 较上一学期变化；
- 是否公共必修或大面积课程。

页面明确说明“为什么进入 TOP10”，并支持进入课程详情。

GPA 分布降为辅助结构分析，与重点课程区分开，不和首要核查事项争夺视觉焦点。

#### E. 原型数据能力

合成毕业率、学位率和就业去向不再放在默认正式管理 KPI 中。

如仍需展示产品能力，收纳到可折叠的“原型能力示例”，并持续标识“合成数据，不形成正式管理结论”。

旧口径末次通过率从正式页面移除，只在口径兼容说明或内部核验中保留。

### 5.2 学院详情

首屏建议：

- 本院当前挂科学生率及较全校差值；
- 本院平均 GPA 及全校排名；
- 当前有效预警学生率及较上期变化；
- 需要优先核查的专业数。

主体分为：

1. 专业比较表；
2. 年级差异；
3. 本院重点核查课程；
4. 口径与数据覆盖。

专业表中将“▲/▼”改为明确文本，例如：

- “高于全院 3.2 个百分点”；
- “低于全院 1.4 个百分点”。

“各年级课程学分通过占比”统一改名为“本学期课程学分通过占比”，不得使用“完成度”。

### 5.3 专业详情

移除或降级：

- 合成培养方案完成率；
- 合成毕业率；
- 合成就业去向。

若学生与真实培养方案已有有效绑定，可以引用培养质量模块提供的统一事实指标；未绑定时显示“暂无法形成培养方案进度结论”，不使用合成数据补齐。

年级详情改为：

- 顶部先按风险排序展示各年级摘要；
- 默认展开最值得核查的 1 个年级；
- 其他年级使用折叠面板；
- 点击年级后再加载其课程明细；
- 每个年级显示当前学期有效成绩覆盖和较上期变化。

### 5.4 课程详情

页面顶部必须新增“当前分析范围”：

- 全校该课程；
- 某学院修读该课程；
- 某专业修读该课程；
- 某年级修读该课程。

从学院、专业或年级进入时，默认继承来源范围；有全校权限的用户可主动切换到“全校该课程”，不得静默扩大。

课程详情统一展示：

- 当前学期有效成绩人数；
- 平均分；
- 首次未通过率；
- 优秀率；
- 较上一学期变化；
- 成绩覆盖。

班级表必须明确是“教学班”还是“学生行政班”：

- 有教学班标识时优先按教学班；
- 只有行政班数据时，标题改为“修读学生行政班分布”；
- 默认显示风险 TOP10；
- “查看全部”在抽屉或独立清单中展示。

### 5.5 学生名单和档案衔接

从本模块进入学生名单时，使用一个明确的“已应用分析上下文”：

- 学期；
- 学院；
- 专业；
- 年级；
- 课程；
- 来源页面。

必须满足：

- 页面首次结果与筛选框一致；
- 只保留最后一次请求结果；
- 课程名单与课程详情使用完全相同的学期和范围；
- 标题同时显示学院和专业；

## 6. 统一指标口径建议

| 指标 | 建议计算逻辑 | 管理用途 |
|---|---|---|
| 有效成绩覆盖率 | 当前学期至少一条有效成绩的去重学生数÷授权范围在籍学生数 | 判断本页是否具备统计解释条件 |
| 当前挂科学生率 | 当前学期至少一门未通过的去重学生数÷当前学期有有效成绩的去重学生数 | 判断受影响学生范围 |
| 当前未通过人次率 | 当前学期未通过有效成绩人次÷当前学期有效成绩人次 | 判断课程教学结果，不与学生率混用 |
| 平均 GPA | 先计算每名学生当前学期课程 GPA 均值，再对范围内有 GPA 学生求平均 | 避免修课门数不同造成重复加权 |
| 加权平均分 | `Σ(成绩×课程学分)÷Σ课程学分`，仅有效成绩且学分大于 0 | 观察总体成绩水平 |
| 当前有效预警学生率 | 当前有效预警去重学生数÷授权范围学生数 | 判断当前需要关注的预警覆盖 |
| 首次通过率 | 所选学期首次修读通过人次÷所选学期首次修读人次 | 判断课程首修教学结果 |
| 补考通过率 | 所选学期补考通过人次÷所选学期补考人次 | 判断补考恢复效果 |
| 重修通过率 | 所选学期重修通过人次÷所选学期重修人次 | 判断重修资源效果 |
| 本学期课程学分通过占比 | 所选学期通过课程学分人次÷所选学期修读课程学分人次 | 观察本学期修读结果，不代表培养方案进度 |
| 历史挂科经历率 | 在校期间曾有未通过记录学生数÷授权范围学生数 | 观察长期受挫经历，仅作为结构指标 |

所有比率在分母为 0 时返回 `null`，前端显示“暂无可比数据”，不得显示 0%。
