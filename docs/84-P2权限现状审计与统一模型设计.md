# P2 权限现状审计与统一模型设计

> 审计日期：2026-07-19
> 适用分支：`产品终稿`
> 目标：在不扩大任何现有用户数据范围的前提下，把旧库、V2、AI和人员关系中的权限逻辑统一为可迁移、可测试、可审计的权限上下文。

## 1. 审计结论

当前系统已经具备菜单授权、角色范围、V2范围映射和班主任/导师关系四类权限素材，但它们不是一套统一的授权模型。

最需要优先处理的风险有六项：

1. `sys_role_scope`按角色绑定范围。同一角色下的不同真实用户会共享学院、专业或班级范围，不能支持多学院和多人使用。
2. 旧库权限解析存在“受限角色没有范围记录时按全校放行”的 fail-open 风险。
3. V2和AI分别复制了全校角色白名单与范围解析函数，同一用户在不同接口可能得到不同边界。
4. 账号没有稳定关联教职工工号，无法可靠使用班主任、导师和任课教师关系。
5. 当前没有辅导员—行政班真实关系表；辅导员范围仍由演示角色固定绑定三个班级。
6. 2,331条班主任—学生关系中，2,248条使用77个`ADVISER-*`临时人员标识；只有83条关系、3名班主任能关联正式工号。

因此，P2不应继续给各路由增加角色判断。正确顺序是先建立统一权限上下文和用户身份关系，再逐步迁移接口。

## 2. 当前五层权限来源

| 层次 | 当前来源 | 当前用途 | 主要问题 |
|---|---|---|---|
| 菜单权限 | `sys_role_menu` | 决定侧栏和页面入口 | 只能表示页面准入，不能作为数据安全边界 |
| 旧库数据范围 | `sys_role.data_scope_type`、`sys_role_scope` | 学生、学院、专业过滤 | 按角色共享；无映射时可能放行全校 |
| V2范围桥接 | `access_scope_mapping` | 把原型范围代码映射到真实组织、专业、行政班 | 仍按角色绑定；与旧库形成两套真值 |
| 人员—学生关系 | `staff_student_scope` | 班主任、导师可见学生 | 账号未关联工号；辅导员关系缺失；有效期不完整 |
| 路由局部白名单 | `ADMIN_ROLES`、`V2_ALL_SCOPE_ROLES`、`V2_MAPPED_SCOPE_ROLES`、`_QUALITY_MANAGERS` | 管理写操作、V2读取、教学运行操作 | 分散、重复，无法统一审计和缓存隔离 |

## 3. 当前数据证据

### 3.1 旧库账号、角色与范围

- `sys_user`：11个账号，每个账号只有一个`role_id`。
- `sys_role`：10个角色。
- 全校范围角色：`dean`、`school_leader`、`dept_operation`、`dept_research`、`dept_practice`、`quality_office`。
- 学院范围角色：`college_dean`、`college_secretary`。
- 专业范围角色：`dept_director`。
- 班级范围角色：`counselor`。
- `sys_role_scope`共6条：
  - `college_dean`、`college_secretary` → `C01`；
  - `dept_director` → `M042`；
  - `counselor` → `B0360`、`B0363`、`B0364`。

当前表结构没有用户—角色有效期、账号—工号、当前工作身份、范围来源和状态。

### 3.2 V2范围映射

`access_scope_mapping`共6条且全部为`mapped`：

- `C01`映射为组织代码`233`；
- `M042`映射为专业代码`08002`；
- 三个辅导员班级范围映射为真实行政班名称。

该表适合在迁移期承担“旧编码到真实编码”的桥接，但不应继续作为生产授权真值，因为主键仍以`role_id`开头。

### 3.3 班主任、导师与辅导员关系

`staff_student_scope`共2,511条：

| 关系 | 关系行数 | 人员数 | 人员标识质量 | 有效期情况 |
|---|---:|---:|---|---|
| 班主任 | 2,331 | 80 | 3名正式工号；77个临时`ADVISER-*`标识 | 统一从`2022-09-01`开始，均无结束日期 |
| 学业导师 | 180 | 100 | 使用真实导师工号 | 有开始日期，当前记录均无结束日期 |
| 辅导员 | 0 | 0 | 尚未取得真实关系表 | 无 |

班主任源文件提供行政班代码、行政班名称、班主任、所属院系和职称，但大部分记录缺教师工号。导师源文件提供学生学号、导师工号、导师类型、开始/结束日期、发布状态和有效状态。

### 3.4 辅导员—行政班生产数据契约

原型阶段可以继续使用现有三个班级范围演示，但生产接口按以下结构接收学校数据：

| 字段 | 必填 | 说明 |
|---|---:|---|
| `relation_id` | 是 | 学校源关系主键；没有时由学校代码、工号、班级、起始日期生成稳定键 |
| `staff_id` | 是 | 辅导员工号，必须可与统一身份账号关联 |
| `class_code` | 是 | 稳定行政班代码，不以班级名称作为主键 |
| `relation_type` | 是 | `counselor`或学校确认的同义代码 |
| `valid_from` | 是 | 生效日期 |
| `valid_to` | 否 | 失效日期；空表示当前有效 |
| `status` | 是 | `active`、`inactive`或源系统等价状态 |
| `source_system` | 是 | 来源系统或接口 |
| `source_updated_at` | 是 | 源记录最后更新时间 |

唯一性按`staff_id + class_code + relation_type + valid_from`控制。当前权限只使用状态有效且查询日位于有效期内的关系；历史记录仅用于审计。

## 4. 代码使用位置

### 4.1 旧库范围

统一入口当前位于`code/backend/api/deps.py`：

- `_get_scope`
- `student_data_scope`
- `college_data_scope`
- `major_data_scope`

调用模块包括：

- 教学数据总览：`dashboard.py`
- 学业预警：`alert.py`
- 学生分析：`students.py`
- 教学运行：`operation.py`
- 师资保障：`faculty.py`
- 管理专题：`reports.py`
- AI研判：`ai.py`
- 元数据筛选：`meta.py`

`teacher.py`还直接读取`sys_role_scope`取得教师工号，属于独立旁路。

### 4.2 V2范围

`v2.py`使用：

- `require_v2_reader`
- `require_v2_all_reader`
- `_student_scope`
- `_assert_student_access`

已做学生范围过滤的接口包括培养方案管理总览、关注学生、专业核查、学生毕业准备详情、困难学生、低年级受挫、毕业准备、学生成长、方案课程和学生建议。

课程质量、师资资源、排课策略、课程开设、课程团队、教师排课偏好和教室统计等接口仍使用“仅全校角色”守卫，没有统一的学院业务对象范围。

### 4.3 AI独立逻辑

`ai.py`重复维护：

- `V2_ALL_SCOPE_ROLES`
- `V2_MAPPED_SCOPE_ROLES`
- `_v2_student_scope`
- `_management_scope_context`
- 多处直接`role_id`判断

AI管理要情同时拼接旧库学生范围、V2学生范围和V2教学任务范围。缓存键主要依赖用户名、角色和部分筛选条件，尚未使用统一范围指纹。

## 5. 已确认的安全语义

### 5.1 角色与范围

- 角色定义功能能力上限。
- 用户当前工作身份决定本次会话启用哪一个角色。
- 用户范围和有效业务关系决定能看到哪些对象。
- 菜单可见不等于接口可访问。
- 受限身份缺少范围、人员映射或有效关系时默认拒绝，不得回退全校。
- 系统管理员、校领导和教务处的全校范围是显式授权，不是缺失映射的默认结果。

### 5.2 明细与比较

- `detailScope`控制明细、名单、档案、导出和证据下钻。
- `comparisonScope`控制允许查看的校级或其他学院聚合值。
- 二级学院可以在指定页面查看其他学院聚合对比，但不能得到他院学号、姓名、名单、档案或可反向识别的小样本。
- 聚合比较接口和明细接口必须使用不同的权限声明。

### 5.3 业务对象归属

| 业务对象 | 明细授权依据 |
|---|---|
| 学生、成绩、预警、成长轨迹 | 学生所属组织，或有效带班/导师关系 |
| 培养方案与执行进度 | 方案所属专业/学院与学生所属范围同时校验 |
| 教学任务、排课、调课 | 教学任务开课组织 |
| 课程质量 | 本院开课任务明细；跨院只返回获准聚合 |
| 教师与课程团队 | 教师组织和开课组织分别标识，页面明确当前采用的观察口径 |
| 教室 | 原则上为校级教学资源聚合；明细开放由页面动作权限控制 |
| AI管理要情与研判 | 不产生新权限，完全继承当前身份和上述对象语义 |

## 6. 统一权限上下文

后端建立单一解析器，登录、`/auth/me`、业务API、导出、AI和审计均使用同一结构：

```json
{
  "userId": "11",
  "username": "example",
  "staffId": "T001",
  "activeIdentityId": "UR-001",
  "activeRole": "college_dean",
  "menuPermissions": ["dashboard", "alert"],
  "actionPermissions": ["student.detail", "college.compare"],
  "detailScope": {
    "type": "organization",
    "organizationIds": ["233"],
    "majorCodes": [],
    "classCodes": [],
    "studentIds": []
  },
  "comparisonScope": {
    "type": "school_aggregate",
    "allowOtherOrganizations": true,
    "minimumGroupSize": 10
  },
  "fieldPolicy": {
    "studentIdentity": "detail_scope_only",
    "export": "authorized_only"
  },
  "scopeFingerprint": "sha256:..."
}
```

`scopeFingerprint`至少由账号、当前身份、角色、有效范围、有效人员关系版本和字段策略生成。缓存、AI会话和导出任务必须带入该指纹；身份切换或关系失效后旧缓存不可复用。

## 7. 目标关系模型

授权配置表位于现有可写系统库；学生、教师和业务关系继续以V2真实数据为事实源。

### 7.1 `sys_user_staff`

账号与学校人员主数据的关联。

- `username`
- `staff_id`
- `valid_from`
- `valid_to`
- `status`
- `source`
- `source_updated_at`

### 7.2 `sys_user_role`

支持一人多角色和当前工作身份。

- `user_role_id`
- `username`
- `role_id`
- `is_default`
- `valid_from`
- `valid_to`
- `status`
- `source`

### 7.3 `sys_user_scope`

只保存组织、专业、行政班等显式配置范围，不复制导师—学生等动态业务关系。

- `user_scope_id`
- `user_role_id`
- `scope_type`
- `scope_id`
- `valid_from`
- `valid_to`
- `status`
- `source`

### 7.4 `staff_student_scope`

继续作为班主任、辅导员、导师等人员关系事实表，并补强：

- 稳定`relation_id`或等价唯一键；
- 标准关系代码；
- `status`；
- `source_system`和`source_updated_at`；
- 真实工号；
- 完整有效期。

任课教师可见学生优先由教学班选课关系实时推导，不把每名任课教师—学生组合永久复制为授权配置。

## 8. 保留、迁移、废弃清单

| 对象 | 决策 | 处理 |
|---|---|---|
| `sys_user` | 保留并迁移 | 保留账号；角色改由`sys_user_role`表达，增加人员关联 |
| `sys_role` | 保留 | 定义能力上限；`data_scope_type`迁移后仅作兼容，不作为唯一授权 |
| `sys_role_menu` | 保留 | 继续保存角色叶子菜单权限 |
| `sys_role_scope` | 废弃为授权真值 | 仅作为一次性迁移输入和兼容读取，完成迁移后禁止新增依赖 |
| `access_scope_mapping` | 迁移后降级 | 保留旧编码到真实编码的桥接价值；不再按角色决定当前用户权限 |
| `staff_student_scope` | 保留并规范 | 接入账号工号、关系状态、有效期和来源质量 |
| 路由角色白名单 | 逐步废弃 | 转为统一动作权限和权限上下文 |
| `teacher.py`直接读角色范围 | 废弃 | 改为当前人员工号和任课关系 |
| AI独立范围函数 | 废弃 | 改用统一权限上下文和范围指纹 |

## 9. 迁移顺序与兼容策略

1. 新建关系表和幂等迁移脚本，不删除旧表。
2. 把每个现有账号的`role_id`迁移为一个默认`sys_user_role`身份。
3. 把现有`sys_role_scope`按当前账号迁移到`sys_user_scope`。
4. 使用`access_scope_mapping`把原型范围转换为V2真实组织、专业和行政班编码。
5. 为具备真实工号的导师、班主任账号建立`sys_user_staff`；临时班主任标识只允许原型演示并显示数据质量边界。
6. 建立统一权限解析器，先双读新旧结构并比较结果；发现不一致时取更小范围并记录审计。
7. 接口按模块迁移到统一上下文，禁止新增旧函数依赖。
8. 所有接口迁移、反向测试通过后，停止以`sys_role_scope`和AI/V2白名单作为授权依据。

## 10. P2实现门禁

在进入下一阶段前必须满足：

- 受限角色无范围时返回403或空授权结果。
- 两个相同角色、不同范围账号互不共享数据。
- 校领导、教务处和系统管理员通过明确身份获得全校范围。
- 辅导员/班主任按有效班级关系隔离。
- 导师按有效导师—学生关系隔离。
- 过期关系不授予当前明细权限，但保留审计记录。
- 他院聚合可见时，他院学生明细、导出和证据链接仍被拒绝。
- 旧库、V2、AI、导出和缓存使用同一个`scopeFingerprint`。
- URL直接访问、API传入越权ID和自然语言越权请求均不能扩大范围。
