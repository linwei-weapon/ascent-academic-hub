# 本科教学分析与学业决策支持平台

## 学校电子反馈导航与重点确认清单

> 适用对象：教务处、二级学院教学管理人员及信息化建设人员
>
> 配套文件：`本科教学分析与学业决策支持平台需求调研及指标口径确认书V2.md`（V0.12）
>
> 使用方式：本清单用于快速组织学校反馈；完整指标名称、计算逻辑、分子分母、数据来源和边界以V0.12确认书为准。

---

## 一、建议学校如何反馈

学校不需要一次性重写整份需求，也不需要理解系统内部的技术实现。建议按以下方式直接在电子文档中反馈：

| 反馈代码 | 含义 | 建议填写内容 |
|---|---|---|
| A | 认可建议口径 | 填“A”，可补充责任部门 |
| B | 需要修改 | 写明学校实际制度、阈值或统计范围 |
| C | 需要校内进一步讨论 | 写明需参与确认的部门或岗位 |
| D | 当前数据不具备 | 写明预计数据来源、责任部门和可提供时间 |
| E | 不纳入本校建设 | 简要说明原因，避免后续反复确认 |

建议由一名教务处联系人汇总意见。二级学院可以重点补充“看什么、为什么看、异常后如何核查”，信息化部门重点补充接口、字段、更新频率和部署条件。

## 二、第一轮必须确认的12项事项

以下事项会影响多个页面和指标，应优先确认。若这些基础口径未确认，不建议先讨论单个图表颜色、排序或名称。

| 编号 | 必须确认事项 | 原型当前建议 | 为什么必须确认 | 学校反馈 |
|---|---|---|---|---|
| K-01 | 有效在籍学生范围 | 使用有效学籍状态；休学、保留学籍、交流生等需由学校明确 | 决定所有学生人数、比例和学院比较的分母 |  |
| K-02 | 课程通过与未通过标准 | 按学校成绩结果和百分制及格线识别；缓考、缺考、作弊、取消资格单独保留状态 | 决定挂科、通过率、学分取得和预警结果 |  |
| K-03 | GPA换算与计入范围 | 按课程绩点×学分加权；等级制、免修、补考和重修覆盖规则待学校确认 | 决定学生GPA、学院平均GPA和相邻学期画像 |  |
| K-04 | 重修、补考和成绩覆盖 | 首次、补考、重修分别统计；当前有效成绩使用学校认可的覆盖规则 | 决定三类通过率和学生当前课程欠账 |  |
| K-05 | 当前挂科与历史欠账 | 当前学期未通过和历史未解决课程分开统计 | 避免把已经重修通过的历史记录继续当作当前风险 |  |
| K-06 | 学生与培养方案绑定 | 生产系统使用正式“学生—方案版本—生效期”关系 | 决定每名学生应该完成哪些模块和课程 |  |
| K-07 | 培养方案模块完成规则 | 优先使用模块学分要求；学分要求为空或0时使用门数要求；两者均无时按逐门必修证据 | 决定培养方案完成度、必修缺口和毕业准备核查 |  |
| K-08 | 课程替代、免修和认定 | 只有正式生效的替代或认定结果才能消除课程缺口 | 决定缺修课程是否真实存在 |  |
| K-09 | 预警观察范围与等级 | 规则需明确适用学生、观察期、等级、证据和版本；规则变更后重新计算 | 决定当前有效预警、历史比较和优先核查 |  |
| K-10 | 课程趋势最小样本 | 原型默认每个课程学期单元至少30条有效成绩 | 防止小样本课程的未通过率剧烈波动被误判 |  |
| K-11 | 教室利用率分母 | 使用学校权威可用教室和可用时段，不由本平台人工维护 | 决定占用率能否用于跨楼宇和跨时段比较 |  |
| K-12 | 师资保障核查标准 | 单教师授课本身不算风险；结合教学班数、覆盖人次、课程重要性和替代资源核查 | 避免把正常授课安排误报为师资风险 |  |

### 建议的校内确认责任

| 事项 | 建议牵头岗位 | 建议协同岗位 |
|---|---|---|
| K-01、K-06、K-08 | 学籍与培养管理岗位 | 二级学院教学秘书 |
| K-02—K-05 | 成绩管理岗位 | 学院教学院长、教学秘书 |
| K-07 | 培养方案管理岗位 | 专业负责人 |
| K-09 | 教务处学业管理岗位 | 学院、辅导员或班主任代表 |
| K-10 | 教学质量管理岗位 | 学院课程负责人 |
| K-11 | 教室与排课管理岗位 | 信息化或资源管理部门 |
| K-12 | 教学运行管理岗位 | 学院教学院长、课程团队负责人 |

## 三、各业务模块重点讨论什么

### 1. 教学数据总览

学校重点确认：

1. 校领导和教务处打开首页时，最先要判断的3—5个问题是什么；
2. 学院横向比较采用学分加权平均分、学生平均GPA还是两者同时使用；
3. 学院偏离以全校均值、同类学院还是历史自身为参照；
4. 首页重点课程进入TOP10的依据是否认可；
5. 点击指标后，管理者希望下钻到学院、专业、课程还是学生名单。

### 2. 学业预警监控

学校重点确认：

1. 哪些预警规则属于正式规则，哪些只是候选发现；
2. 当前有效预警、历史预警、持续命中和本期新增分别如何定义；
3. 预警优先核查排序是否需要纳入风险等级、规则叠加和持续时长；
4. 校、院、辅导员、班主任和导师分别需要看到什么证据；
5. 预警结果是否只用于发现和核查，后续干预流程是否纳入学校本期建设范围。

### 3. 教学运行分析

学校重点确认：

1. 单门课程开课情况最需要比较的时段、年级、课程类别和承担学院；
2. 体育、思政、数学、英语等重点课程由哪个系统或部门维护标签；
3. 教室实际占用应包含课程、考试、自习及哪些其他活动；
4. 晚间是否默认纳入教室利用分析；
5. 调停课业务单据如何计数，调课原因有哪些学校标准分类；
6. 教师负荷只用于工作量观察，还是需要形成学校正式负荷标准。

### 4. 培养质量分析

学校重点确认：

1. 学生和培养方案的正式绑定方式；
2. 模块学分、门数、必修课程和课程组要求的优先级；
3. 专业准备度、学生学业进度和毕业准备核查分别服务什么管理动作；
4. 哪些培养方案缺口可以直接确认，哪些必须标记为候选核验；
5. 下一周期开课和重修资源接入后，希望怎样形成课程保障清单；
6. 毕业要求及指标点用于方案执行证据展示，不直接代替毕业审核或专业认证结论。

### 5. 师资保障分析

学校重点确认：

1. 哪些课程属于必须持续保障的重点课程；
2. 课程团队应包括负责人、主讲、实验、助教等哪些角色；
3. 高影响单点课程的教学班数和覆盖人次阈值；
4. 年龄、职称和接续风险使用哪个部门提供的规则；
5. 学院可以查看外院承担本院课程的哪些最小必要教师信息；
6. 核查结论只用于课程供给保障，不直接形成教师个人评价。

### 6. 学生成长与学业分析

学校重点确认：

1. 相邻学期画像变化同时使用GPA、未通过课程和取得学分是否合适；
2. “明显改善”“明显下降”的阈值；
3. 低年级首次受挫的观察年级和课程范围；
4. 辅导员、班主任、导师和学院管理者分别需要查看哪些学生证据；
5. 成长轨迹中历史成绩、挂科模式、预警记录和培养进度的时间范围；
6. 学生本人页面未来需要提供哪些提醒，但不扩展为学生工作管理系统。

## 四、生产数据接口确认

原型现有数据能够支撑主要业务路径演示。生产系统仍需把文件数据替换为结构化、版本化接口。学校建议按以下三类反馈。

### 1. 上线基础数据

| 数据 | 最低确认内容 | 建议来源 |
|---|---|---|
| 学籍与学生 | 稳定学号、学籍状态、年级、专业、行政班、生效时间 | 教务或学籍系统 |
| 组织与专业 | 稳定编码、层级、名称、有效期 | 组织主数据 |
| 课程主数据 | 课程编号、名称、学分、性质、类别、有效期 | 教务系统 |
| 成绩修读记录 | 学生、课程、学期、成绩、结果、修读类型、发布/作废状态 | 成绩系统 |
| 培养方案 | 方案版本、模块、课程组、学分/门数要求、建议学期 | 培养方案API |
| 学生方案绑定 | 学生、方案版本、生效期、变更原因 | 教务系统 |
| 课程替代与认定 | 原课程、替代课程、适用范围、审批状态、有效期 | 认定系统 |
| 教学任务 | 学期、课程、教学班、学院、教师、容量和选课人数 | 教务系统 |

### 2. 教学运行与资源数据

| 数据 | 最低确认内容 | 建议来源 |
|---|---|---|
| 课程日历/课表 | 日期、周次、星期、节次、教室、状态 | 排课系统 |
| 教室主数据 | 稳定编号、楼宇、容量、类型、可用状态、有效期 | 资源主数据 |
| 教室实际占用 | 占用类型、教室、日期、节次、关联业务、状态 | 教室或场地系统 |
| 调停课 | 单据、原课次、新课次、原因、状态、教师、影响范围 | 调课系统 |

### 3. 权限与师资保障数据

| 数据 | 最低确认内容 | 建议来源 |
|---|---|---|
| 教师与岗位 | 稳定工号、组织、职称、岗位、状态、有效期 | 人事系统 |
| 课程团队 | 课程、负责人、成员、角色、资格、有效期 | 教务或学院系统 |
| 辅导员/班主任带班 | 人员工号、行政班、关系类型、生效期 | 学工或教务系统 |
| 导师带生 | 导师工号、学生、关系类型、生效期 | 教务系统 |
| 统一身份认证 | 稳定认证主体、工号、协议、回调和生命周期状态 | 统一认证平台 |

每项接口请学校补充：责任系统、责任部门、接口方式、关键字段、更新频率、历史覆盖时间和异常数据处理责任。

## 五、数据权限确认

| 工作身份 | 建议详细数据范围 | 跨学院比较 | 学校反馈 |
|---|---|---|---|
| 校领导、教务处 | 全校授权范围 | 可查看全校聚合与明细 |  |
| 系统管理员 | 默认全校业务数据，同时拥有系统管理权限 | 可查看 |  |
| 二级学院 | 本学院学生、专业、课程和必要教学证据 | 指定页面只看其他学院聚合，不下钻学生 |  |
| 辅导员 | 有效关系内所带行政班学生 | 不提供 |  |
| 班主任 | 有效关系内所带行政班学生 | 不提供 |  |
| 导师 | 有效关系内所带学生 | 不提供 |  |

请学校同时确认：

1. 一人多角色时是否允许用户切换当前工作身份；

3. 学生本人是否纳入生产范围；
4. 哪些明细字段需要脱敏；
5. 导出、AI研判和证据下钻是否需要单独授权或加强审计。

## 六、学校分析方案确认

系统保留产品默认方案，学校只调整白名单参数和适用角色，不改变正式指标公式或数据权限。

| 分析方案 | 学校需要确认 | 业务责任部门/岗位 | 学校意见 |
|---|---|---|---|
| 学业预警优先核查 | 风险等级分值、叠加规则、持续时长和重点人数 |  |  |
| 毕业准备核查 | 必修缺口、候选缺口、影响规模和保障优先级 |  |  |
| 课程质量核查 | 最小样本、未通过率、持续偏高和波动阈值 |  |  |
| 师资保障核查 | 教学班数、覆盖人次、单点承担和结构关注阈值 |  |  |

每个校本方案还需确认发布人、审核人、生效时间、复核周期和变更理由模板。发布前应在真实授权数据上回放，比较默认方案和草稿方案产生的管理信号变化。

## 八、反馈后的处理方式

收到学校反馈后，项目组按以下顺序处理：

1. 将学校意见归并为“认可、修改、待讨论、数据不具备、不纳入”；
2. 先修订通用口径和正式指标定义，再调整页面名称、阈值和排序；
3. 形成学校版数据接口清单、权限矩阵和分析方案配置；
4. 对影响多个页面的修改进行跨模块一致性检查；
5. 输出新版需求确认书、生产开发任务清单和验收用例；
6. 所有未确认项继续标注边界，不用演示数据代替学校正式结论。

本清单用于快速反馈，不代替V0.12确认书中的完整指标计算逻辑。学校对具体指标有异议时，请在V0.12确认书相应指标行的“意见”列填写，并引用指标编号。
