# 培养质量分析 UE 深度走查与优化方案

> 版本：V1.1（已实施）
> 状态：已完成口径统一、四工作区改造、性能优化、自动化测试与浏览器回归
> 适用角色：校领导、教务处、教学研究部门、质量管理部门、二级学院及专业负责人
> 公共基线：`docs/93-教学管理分析UE公共契约.md`
> 指标基线：指标口径确认书专题四“培养方案执行与毕业准备核查”

## 1. 本模块应解决的管理问题

培养质量分析不应只是培养方案文档浏览器，也不应把全部课程记录简单相加后包装成“完成度”。本模块应帮助管理者回答四类问题：

1. 学生是否绑定了与年级、专业相符的培养方案，当前分析覆盖是否可信；
2. 方案中的总学分、模块学分、门数、必修和选择组规则是否被正确结构化；
3. 哪些学生存在有证据支持的必修、模块或总学分问题，哪些只是数据候选；
4. 已确认的学生课程需求能否得到后续开课、重修、替代和师资资源保障。

本模块不输出毕业审核或学位审核结论，不把课程平均分替代毕业要求达成度，不自动认定学生漏选，不把单一教师授课或不存在替代课程本身视为风险。

## 2. 当前数据事实

### 2.1 培养方案数据

- 已接入`53`个2022级培养方案；
- `53`个方案均有结构化课程表；
- `39`个方案已取得毕业最低总学分、毕业要求原文和模块学分规则；
- `38`个方案已取得必修最低学分，`37`个方案已取得选修最低学分；
- `52`个方案存在学生绑定记录；
- 当前方案原文来自Word表格临时提取，生产系统将改为教务系统结构化API。

### 2.2 人工智能学院样例

当前二级学院账号看到：

- 授权学生`692`人；
- 被现有逻辑视为“已绑定”的学生`353`人；
- 被视为“未绑定”的学生`339`人；
- 可选择培养方案`6`个。

进一步核查发现：

- 2022级学生`349`人，均已绑定2022级方案，真实适用年级绑定率为`100%`；
- 339名“未绑定”学生主要属于2018—2021级，而目前只接入2022级培养方案，不能把他们直接视为绑定异常；
- 另有4名2019—2020级学生被绑定到2022级方案，年级与方案适用年级不一致，应进入绑定核验而不是正式进度计算。

### 2.3 人工智能专业方案样例

2022级人工智能专业方案：

- 毕业最低学分`155.5`；
- 方案课程池`309`门、课程池记录学分合计`571`；
- 其中必修标记课程`64`门、课程记录学分`132.5`；
- 选修池`245`门、课程池记录学分`438.5`；
- 共`23`个课程模块、`15`条模块最低学分规则。

`571`是包含大量备选课程的课程池学分合计，不是学生应修学分，也不能作为学生完成率分母。

### 2.4 学生进度样例

当前页面将309门课程全部作为人工智能专业每名学生的分母，产生以下结果：

- 平均“课程完成率”约`23.4%`；
- 38名学生全部进入“待核验”；
- 单名学生可出现40—53门“到期待核验课程”。

这些结果主要由课程池、选择组和缺少个人选课/认定证据共同造成，不能直接反映学生真实培养进度。

## 3. 当前问题结论

### 3.1 P0：学生方案绑定分母错误

当前“未绑定已接入方案”使用全部授权学生作为分母，把方案源数据尚未覆盖的2018—2021级学生计入异常。

目标口径：

```text
应绑定学生
= 学生年级与专业存在已接入适用方案的学生

培养方案绑定率
= 正确绑定适用方案的学生数 ÷ 应绑定学生数
```

超出方案源数据覆盖年级的学生单独显示为“暂不在方案源覆盖范围”，不进入绑定率，也不进入绑定异常名单。

年级与方案版本不一致、专业与方案不一致或存在多方案冲突的学生进入“绑定待核验”。

### 3.2 P0：课程池被错误当作学生应修清单

当前进度接口以全部`curriculum_plan_course`记录作为每生分母。大量通识选修、专业选修和选择组课程只是可选课程池，不是每名学生都必须完成。

后续必须按已确认顺序评价模块：

1. 模块最低学分大于0：按学生在该模块取得的认可学分判断；
2. 学分为空或0、最低门数大于0：按完成门数判断；
3. 学分和门数都不存在：只核查模块内逐门必修课程；
4. “二选一、三选一”等选择组不能按全部必修课程处理，应解析最低完成门数；
5. 已审批替代、免修和认定计入完成证据，原课程与替代课程不得重复计入。

### 3.3 P0：四个工作区的“到期”口径不一致

- 管理总览和学业进度使用`is_overdue=1`；
- 毕业准备核查直接使用“建议学期小于等于8”；
- 状态构建器把所有学生的当前学习学期固定为第8学期；
- 一个口径使用“小于8”，另一个使用“小于等于8”。

目标口径：

```text
学生当前学习学期
= 根据当前业务学期、入学年级、休学复学和学籍异动计算

课程到期候选
= 建议修读学期早于学生当前学习学期
  且没有通过、认定或明确未通过证据
```

当前没有完整个人选课、缓修、免修和成绩同步状态，因此“到期”只能形成数据候选，不能称为漏选或明确缺修。

### 3.4 P0：明确未通过不等同仍然存在培养要求缺口

若学生在最低学分模块中挂过一门选修课，但已通过其他课程满足模块学分，该未通过记录不应继续构成培养方案缺口。

“明确需处理”应满足：

- 逐门必修课程当前仍未解决；或
- 模块最低学分/门数未达到，且存在明确未通过证据影响完成；或
- 有正式选课或审核数据证明学生应修未修。

历史挂科记录仍保留在学生成长轨迹，但不与当前培养要求缺口混用。

### 3.5 P0：课程保障优先级规则泛化

当前下列情况会普遍形成“需核查”：

- 一门课程仅有一名教师；
- 未发现课程替代关系；
- 当前接入教学任务中没有开课记录。

上述情况在高校教学中可能完全正常。课程保障优先级应改为：

```text
已确认修读需求
→ 下一周期是否有开课计划
→ 可用容量是否覆盖需求
→ 学生是否具备修读资格且时间、校区可参加
→ 资源不足时再核查教师团队与替代方案
```

在没有未来教学任务和重修资源时，只能显示“下一周期供给尚未接入/需确认”，不得输出供给不足或高风险结论。

单一教师只有同时满足“大规模或多班持续依赖、影响学生较多、缺少备份安排”等条件时，才作为辅助核查证据。

不存在替代课程只在课程停开、课程代码变更或已经确认无法正常供给时才有管理意义。

### 3.6 P1：页面筛选关系不清楚

- 顶部“方案查看条件”在毕业准备核查页仍显示，但该页完全不使用这些条件；
- 毕业准备页的“高年级重点核查”只改变学生名单，专业和课程表仍是全部范围；
- “重置”实际恢复高年级筛选，而不是清除条件；
- 学院账号仍提示“当前是全校管理总览”。

所有页面必须展示“已应用条件”，并明确条件作用范围。

### 3.7 P1：页面层级和平铺信息过多

- 总览首屏有7张指标卡；
- 方案详情有8张指标卡；
- 同时呈现饼图、模块汇总、模块要求、23个折叠模块和方案原文；
- 毕业准备连续显示3条大面积说明、5张卡、2个并列表、学生表和长口径说明；
- 概览使用弹窗，学生详情又叠加抽屉；专业画像和课程供给继续叠加弹窗。

管理者难以判断先看什么、先核查什么。

### 3.8 P1：正式表格未遵守公共契约

除两个已停用的旧达成度页面外，本模块主要正式表格都没有接入公共`DataTable`，缺少：

- 显示列配置；
- 列顺序；
- 显示数量上限；
- 行密度；
- 分页偏好；
- 恢复默认布局。

### 3.9 P1：加载和错误反馈不足

- 进入任意Tab都会顺序加载方案选项、管理总览和默认方案；
- 即使直接进入毕业准备页，也会预先计算隐藏的管理总览；
- 管理总览冷请求实测约`5.2秒`；
- 整页使用一个全局加载遮罩，局部更新会阻断整个模块；
- 学生证据和课程保障在请求完成前不打开弹窗，点击后缺少即时反馈；
- 抽屉或弹窗加载失败后没有内部重试入口。

### 3.10 P1：旧达成度路由仍可直接访问

系统仍保留：

- `/admin/curriculum/course-objectives/:id`
- `/admin/curriculum/graduate-requirements/:id`

其中“课程目标达成度”仍使用课程成绩和固定65%阈值计算，并且只硬编码两个专业，与当前已确认产品口径冲突。毕业要求旧页虽已隐藏雷达图，但仍是脱离当前方案选择的孤立页面。

## 4. 目标信息架构

一级模块继续使用“培养质量分析”，内部保留4个平级Tab：

1. **方案执行总览**
2. **方案结构与要求**
3. **学生进度核查**
4. **毕业准备与课程保障**

四个Tab的职责不得重叠：

| Tab | 核心问题 | 主要对象 |
|---|---|---|
| 方案执行总览 | 方案和学生绑定是否可信、哪些学院/专业需要优先核查 | 学院、专业、方案、学生群体 |
| 方案结构与要求 | 一个方案究竟要求学生完成什么 | 方案、模块、课程池、原文 |
| 学生进度核查 | 某方案学生的模块和课程证据进度如何 | 学生、模块、课程证据 |
| 毕业准备与课程保障 | 高年级已确认缺口需要配置哪些课程资源 | 高年级学生、缺口课程、下一周期供给 |

## 5. Tab一：方案执行总览

### 5.1 首屏管理结论

首屏先输出一条角色化结论，例如：

> 当前授权范围已接入6个2022级培养方案；2022级适用学生349人，正确绑定349人。发现4条跨年级绑定待核验记录。明确课程问题和数据候选需按证据等级分别处理。

学院角色显示“本院方案执行总览”，校级角色显示“全校方案执行总览”。

### 5.2 核心指标

建议保留5张卡：

| 指标 | 计算逻辑 | 是否下钻 |
|---|---|---|
| 已接入方案 | 当前授权范围可见的有效方案数 | 进入方案清单 |
| 可进行规则核查方案 | 同时有课程表、模块规则和总学分要求的方案数 | 查看缺失证据方案 |
| 适用学生绑定率 | 正确绑定人数÷应绑定人数 | 查看绑定待核验名单 |
| 明确培养要求问题学生 | 统一模块评价后存在已确认缺口的去重学生 | 查看学生名单 |
| 数据候选学生 | 因选课、认定、映射或到期证据不全需要核验的去重学生 | 查看候选名单 |

“无开课证据课程”和“单一教师覆盖课程”不再放在顶层指标卡。

### 5.3 管理表格

校级用户：

- 学院执行概览；
- 下钻后查看专业执行概览。

学院用户：

- 直接显示本院专业执行概览；
- 不重复显示只有一行的学院表，也不保留冗余学院列。

专业概览默认列：

1. 专业（必选、左固定）；
2. 适用年级；
3. 应绑定学生；
4. 正确绑定；
5. 绑定待核验；
6. 明确问题学生；
7. 数据候选学生；
8. 可核查方案；
9. 操作“核查”。

默认8个业务列，最多10个。

### 5.4 下钻

- 点击卡片或表格数字后打开名单抽屉；
- 抽屉顶部显示当前学院、专业、年级、方案和证据类型；
- 学生名单使用公共`DataTable`和服务端分页；
- 点击学生“证据”打开第二层抽屉；
- 关闭第二层回到原名单、分页和滚动位置。

## 6. Tab二：方案结构与要求

### 6.1 筛选

采用“学院—年级—专业—方案”四级草稿筛选，同一行显示：

- 学院角色的学院固定为只读范围标签；
- 校级用户可以选择学院；
- 选择条件只更新可选项；
- 点击“应用方案”后才加载方案详情；
- 提供真正清空或恢复默认的操作；
- 已应用方案写入URL并在返回时恢复。

### 6.2 核心指标

建议保留：

1. 毕业最低总学分；
2. 课程模块数；
3. 有明确规则模块数/全部模块数；
4. 课程池课程数；
5. 方案证据状态。

“课程池记录学分合计”不作为管理指标，可放入口径说明，明确它包含备选课程。

### 6.3 模块要求表

把“各模块学分与课程数”和“模块最低学分要求”合并为一张表：

| 默认列 | 说明 |
|---|---|
| 模块 | 必选 |
| 性质 | 必修、选修、实践或待核验 |
| 采用规则 | 最低学分、最低门数、逐门必修或不可判断 |
| 最低要求 | 例如“至少7学分”“至少1门” |
| 课程池 | 课程数 |
| 课程池记录学分 | 只描述可选范围 |
| 规则证据 | 原文、推导或待核验 |
| 操作 | “课程明细” |

默认7个业务列，最多9个。

点击“课程明细”后打开抽屉，只渲染当前模块课程，不在页面DOM中预先创建23张课程表。

### 6.4 培养目标和毕业要求

改为一个轻量“方案原文证据”区域：

- 培养目标条数；
- 毕业要求条数；
- 学位条件是否取得；
- 来源文件；
- “查看原文”抽屉。

不显示雷达图，不显示达成度，不使用课程平均分或通过率替代指标点评价。

旧课程目标和毕业要求路由改为兼容重定向，统一返回当前方案的“方案结构与要求”Tab。

## 7. Tab三：学生进度核查

### 7.1 进度计算底座

新增统一的学生模块状态，所有总览、进度和毕业准备接口共同使用：

```text
student_plan_course_status
→ student_plan_module_status
→ student_plan_progress_summary
```

学生模块状态至少包含：

- 方案版本；
- 模块；
- 采用规则；
- 目标学分或目标门数；
- 已认可学分或已完成门数；
- 是否达到；
- 明确缺口；
- 候选缺口；
- 规则来源；
- 数据证据状态；
- 计算版本和时间。

### 7.2 核心指标

建议使用：

1. 方案覆盖学生；
2. 模块规则可核查率；
3. 模块要求全部达到学生；
4. 存在明确问题学生；
5. 存在数据候选学生。

不再使用“已完成课程数÷309门课程池”的平均课程完成率。

### 7.3 学生表

默认列：

1. 学号（必选、左固定）；
2. 姓名（必选）；
3. 年级；
4. 已达到模块/可核查模块；
5. 已认可总学分；
6. 明确缺口；
7. 数据候选；
8. 证据状态；
9. 操作“详情”。

默认8个业务列，最多10个，服务端分页。

### 7.4 学生详情抽屉

默认打开“模块完成核查”，按管理顺序显示：

1. 未达到且证据明确；
2. 需要人工核验；
3. 已达到；
4. 暂不可计算。

详情内部Tab：

- 模块完成核查；
- 当前明确未解决课程；
- 数据候选课程；
- 全部课程证据。

抽屉内明确显示计算规则和来源，加载失败时提供重试。

CSV导出应说明是“当前筛选全部结果”还是“当前已加载结果”，不得静默导出被接口上限截断的数据。

## 8. Tab四：毕业准备与课程保障

### 8.1 使用范围

默认聚焦应届或高年级学生，不重复展示所有年级的一般进度。

只有以下事实进入管理优先队列：

- 统一模块评价后仍存在的明确必修或模块缺口；
- 已经确认的重修需求；
- 经过核验的应修未修；
- 下一周期供给、容量、资格或时间冲突证据。

缺少结果记录但没有选课和认定证据的对象进入独立候选区。

### 8.2 筛选

该Tab使用自己的管理筛选：

- 年级；
- 专业；
- 培养方案；
- 证据类型。

采用“草稿条件+应用筛选”。应用后同时影响指标、专业表、课程表和学生表，并显示已应用条件和清除入口。

顶部“方案查看条件”不在本Tab显示。

### 8.3 核心指标

建议5张卡：

1. 纳入毕业准备核查学生；
2. 明确培养要求问题学生；
3. 已确认重修需求学生；
4. 待补业务证据学生；
5. 下一周期供给待确认课程。

若没有未来教学任务，第5张卡显示灰色“未接入”，不显示正式0或风险数量。

### 8.4 课程保障表

默认列：

1. 课程（必选）；
2. 已确认需求学生；
3. 涉及专业；
4. 最近开课学期；
5. 历史教学班；
6. 下一周期计划；
7. 计划容量缺口；
8. 核查状态；
9. 操作“保障证据”。

未来开课计划未接入时，“下一周期计划”和“容量缺口”显示未接入，不通过历史数据倒推。

首页显示Top10并给出入选原因，完整清单单独分页。

### 8.5 证据抽屉和AI入口

- 学生“核查证据”和课程“保障证据”统一改为抽屉；
- 抽屉先显示确定性事实，再显示数据边界；
- 只有明确缺口或供给矛盾对象才显示AI研判入口；
- AI解释必须复用同一模块状态和课程供给事实，不得重新计算另一套结果；
- 不在页面顶部保留大面积AI说明。

## 9. 统一表格契约

本模块以下正式表格全部接入公共`DataTable`：

- 学院/专业执行概览；
- 方案和证据覆盖清单；
- 模块要求表；
- 学生进度表；
- 毕业准备专业表；
- 课程保障表；
- 毕业准备学生表。

抽屉内只用于单次证据核查的4—7列表格可以保持轻量。

所有学生名单必须服务端分页，并返回真实`total`。当前管理学生接口和方案进度接口先`LIMIT`再用结果长度充当总数的行为需要修正。

## 10. 加载、错误与性能方案

### 10.1 按Tab加载

- 方案执行总览只加载总览接口；
- 方案结构与要求首次进入才加载方案选项和当前方案；
- 学生进度首次进入才加载方案进度；
- 毕业准备首次进入才加载毕业准备摘要；
- 未激活Tab不请求；
- 已访问Tab按当前身份和筛选条件缓存。

### 10.2 页面反馈

- 页面结构300毫秒内出现；
- 每个Tab使用独立骨架，不使用整页遮罩；
- 条件更新保留旧结果并显示“正在按新条件更新”；
- 抽屉先打开再加载；
- 抽屉内部区分加载、失败、无数据和无权限，并提供重试。

### 10.3 后端性能

管理总览当前冷请求约`5.2秒`，应改为统一预聚合：

- 构建学生模块状态与学生方案摘要；
- 所有接口读取同一聚合，不重复扫描约74.7万条学生—方案课程状态；
- 查询索引包含规则版本、方案、学生、模块、状态和权限范围；
- 缓存键包含当前身份、数据范围、方案版本、计算版本和筛选；
- 方案结构、摘要、名单和详情分离；
- 目标：总览和进度常规请求2秒左右，主内容5秒内可用。

## 11. 权限与角色化呈现

- 校领导、教务处、教学研究和质量管理部门：查看授权的全校聚合与明细；
- 二级学院和专业负责人：只查看本学院学生、方案和课程需求明细；
- 跨院比较只提供授权聚合，不允许下钻其他学院学生；
- 学生、课程、方案、导出、AI研判和直接API请求均服务端重新鉴权；
- 学院身份隐藏锁定的学院筛选，页面语言改为“本院”；
- 无本模块业务权限的角色不显示入口。

## 12. 数据边界

当前可以可靠使用：

- 2022级53个培养方案课程表；
- 39个方案的总学分、毕业要求原文和模块要求；
- 2022级学生与方案绑定；
- 有效成绩、课程替代记录；
- 一个已接入学期的真实教学任务。

当前不足：

- 2021级及以前培养方案；
- 个人完整选课、退选、缓修、免修审核状态；
- 未来学期教学计划、重修班、容量和时间冲突；
- 完整课程组重复计入和跨模块抵扣规则；
- 毕业要求指标点—课程—评价环节—结果矩阵；
- 学位审核正式结构化规则。

数据不足时只输出候选或未接入状态，不使用假数据补齐结论。

## 17. 实施结果与生产交接

### 17.1 已完成实现

- 建立`student_plan_module_status`和`student_plan_progress_summary`两张统一预计算表，方案执行总览、学生进度与毕业准备复用同一模块评价事实。
- 方案适用范围按“年级＋专业”确定；方案源未覆盖者单列，年级或专业错配者进入绑定核验，不再参与正式进度计算。
- 模块评价执行“可信最低学分—最低门数/选择组—逐门必修—不可自动评价”顺序。对Word合并单元格造成的父级学分误继承增加可信性校验，要求学分超过叶子模块全部课程记录学分时自动回退。
- 学生当前学习学期改为依据入学年级和当前日期动态推导；当前学期本身不计为逾期。
- 课程替代只在正式审批和流程完成后计入，并按原方案课程学分抵扣，避免原课程和替代课程重复累计。
- 四个工作区按需加载；管理总览与课程瓶颈拆分请求，名单采用服务端真实总数分页，学生与课程证据在当前上下文抽屉打开。
- 所有正式表格接入公共`DataTable`，支持显示列、列顺序、显示上限、行密度和分页偏好。
- 旧课程目标达成度、毕业要求达成度和旧学业进度入口保留兼容重定向，不再暴露冲突口径页面。

### 17.2 当前数据边界

- 原型当前接入53个2022级培养方案；2021级及以前学生没有相应方案源时仅披露覆盖边界。
- 当前没有完整个人选课、缓修、免修和数据同步状态，到期缺结果只形成数据候选。
- 当前没有下一周期正式开课计划、重修班标识和可参加资格，课程保障只展示明确未通过必修课程及历史供给证据，未来供给统一标记“待确认”。
- 当前没有正式“毕业要求指标点—支撑课程—评价环节—实际结果”矩阵，只展示方案原文和证据状态，不计算达成度。
- Word方案解析只作为原型临时方案；生产系统必须从教务系统取得结构化、版本化方案及学生正式绑定。

### 17.3 生产实现要求

1. 将全量重建改为按成绩、方案、绑定和认定变更事件触发的增量离线任务，页面只读取版本化摘要。
2. 每次计算保存规则版本、数据批次、计算时间、方案版本和来源字段，支持学生、模块和课程三级追溯。
3. 方案调整、转专业、留级、休复学和跨模块抵扣必须由学校正式规则驱动，不能由前端或大模型临时决定。
4. 未来课程保障只有在接入正式教学计划、容量、校区、时间和修读资格后，才能计算供给覆盖率和按期完成风险。
5. 学院用户只能查看本院学生明细；跨学院比较只返回聚合结果，学生、导出、证据和直接API均需服务端重新鉴权。
