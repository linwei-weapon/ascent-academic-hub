## 4. 核心指标基线

以下结果来自分析库动态计算，不写死在测试中：

| 指标 | 基线值 | 当前解释 |
|---|---:|---|
| 在籍学生 | 12,670 | `dim_student` 总数 |
| 当前学期挂科学生 | 4,570 | 当前学期真实成绩中至少一门未通过的去重学生 |
| 当前挂科率 | 36.07% | 4,570 / 12,670 |
| 历史挂科学生 | 11,357 | 全历史真实成绩中至少一门未通过的去重学生 |
| 历史挂科经历率 | 89.64% | 11,357 / 12,670 |
| 真实成绩记录 | 640,239 | `fact_grade.source='real'` |
| 未通过成绩记录 | 38,798 | 真实成绩中 `is_pass=0` |
| 预警学生 | 3,532 | `fact_alert` 去重学生 |
| 预警覆盖率 | 27.88% | 3,532 / 12,670 |
| 预警事件 | 5,027 | 一名学生可命中多条规则 |
| 同课程重复挂科组合 | 1,496 | 学生×课程至少两条未通过记录 |

### 当前判断

1. 大屏显示值与数据库现有公式一致，不是前端计算错误。
2. 当前挂科率和历史挂科经历率在现有数据中客观偏高，不能仅以“接口一致”判定业务合理。
3. 下一步必须核查成绩记录中的补考、重修、缓考、缺考和重复导入，确认“挂科”应按原始尝试还是最终结果计算。
4. 历史挂科经历率适合描述“曾经挂过”，不适合作为当前风险指标；页面必须持续与当前挂科率分开展示。
5. 预警覆盖率 27.88% 偏高，需要逐条核查 R1/R2/R3/R4/R6 的阈值、时间窗和学生状态范围。

## 5. 已确认的数据质量异常

教学运行接口会排除“单教师单学期教学班数超过 200”的记录。当前学期共有 5 名教师命中，最高为 3,567 条教学班记录。这类数据应在 ETL 数据质量层标记，而不应长期只在 API 查询中静默过滤。

建议后续处理：

1. 在 ETL 中生成数据质量问题表；
2. 记录异常来源库、批次、教师、课程和影响行数；
3. 页面明确显示被排除数据量；
4. 修复源数据后允许重新计算，而不是永久依赖固定阈值。

## 6. 迭代顺序

1. 指标口径与成绩记录治理；
2. 全接口权限和数据范围回归；
3. 学业预警闭环；
4. 培养方案与选课合规；
5. 教学运行与排课优化；
6. 师资团队与学生画像；
7. 大屏、报表、规则发现和系统管理收口；
8. 性能、安全、全角色验收与交付。

## 7. 每模块完成定义

一个模块只有同时满足以下条件才标记“完成”：

- 需求和业务规则已确认；
- 数据来源与指标口径可追溯；
- 后端接口与权限检查完成；
- 前端完整流程可操作；
- 自动化数据核对通过；
- 浏览器回归通过；
- 文档与需求矩阵同步更新。
