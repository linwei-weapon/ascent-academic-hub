# 53 · 生产系统开发交接文档总纲

> 目标：让后续开发团队能够理解业务、识别原型边界，并据此完成生产系统设计和实施。  
> 原则：交接的是可验证的需求、数据合同和设计约束，不是要求直接把原型代码部署生产。

## 1. 产品定位与交接边界

当前系统属于业务与数据分析原型，主要验证：

- 高校学业分析场景是否成立。
- 指标和业务规则能否用现有数据计算。
- 管理端页面、下钻和解释方式是否可用。
- 生产系统需要接入哪些数据、权限和治理能力。

生产开发不得默认继承以下原型条件：

- SQLite 单库架构。
- 固定种子模拟业务数据。
- 演示账号和本地密码体系。
- 原型规模下的同步查询和单机 ETL。
- 为演示保留的空态、别名和兼容逻辑。

## 2. 已确认的产品决策

| 决策 | 当前结论 |
|---|---|
| 预警风险发现 | 保留，要求给出可解释证据 |
| 预警后续处置闭环 | 暂缓，是否纳入产品尚未决定 |
| 成绩与挂科口径 | P0，先建立原始尝试和最终有效结果两层模型 |
| 学生成长轨迹 | P0，覆盖成绩、选课、课程缺口和低年级受挫事件 |
| 培养方案建议 | P0，识别应选未选、应重修及毕业/学位影响 |
| 教师排课偏好 | 仅根据真实历史排课结果推断，不由教师主动填报 |
| 模拟数据 | 可用于原型演示，不得作为生产结果或训练标签 |
| 学生端 | 先定义建议卡片和 API，是否建设独立学生端待决策 |
| LLM | 当前关闭；启用前必须完成匿名化、模型选型和输出审查 |

## 3. 生产交接包目录

### A. 产品与需求

1. 产品定位和范围说明。
2. 用户角色、任务和使用场景。
3. 模块 PRD 和页面规格。
4. 业务规则与待决策清单。
5. 原型能力、生产能力和暂缓能力对照表。
6. 需求变更及高校访谈记录。

### B. 数据与指标

1. 学校数据资产和缺口清单。
2. 源系统数据字典、代码表和样例。
3. 生产概念模型、逻辑模型和物理模型。
4. 数据血缘和增量同步规则。
5. 数据质量规则与责任人。
6. 指标字典、公式版本和生效时间。
7. 脱敏、保留和访问审计规则。

### C. 技术设计

1. 总体架构和部署拓扑。
2. 前后端模块划分。
3. 业务库、分析库、缓存和文件服务设计。
4. ETL/ELT、调度、重试和补数方案。
5. 统一身份、RBAC 和数据范围权限。
6. API 契约、错误码和版本策略。
7. 安全、监控、备份和灾难恢复。
8. 架构决策记录（ADR）。

### D. 实现与验证

1. 原型代码说明和生产重构提示。
2. 算法公式、SQL 基线和伪代码。
3. 单元、契约、口径、权限、性能和浏览器测试。
4. 需求追踪矩阵。
5. 数据对账和用户验收方案。
6. 部署、回滚、运维和故障处理手册。

## 5. 每个模块必须形成的开发规格

每个生产模块至少包含：

1. 业务目标和不解决的问题。
2. 使用角色和数据可见范围。
3. 页面、流程、筛选、下钻和异常状态。
4. 输入数据、关联键、更新频率和质量前提。
5. 指标公式、算法规则、版本和边界条件。
6. API 请求、响应、错误码和幂等要求。
7. 真实、派生、人工配置数据的展示标识。
8. 验收样例和自动化测试。
9. 原型映射和生产重构注意事项。

## 6. 需求追踪矩阵规范

生产交接必须建立以下链路：

```text
需求编号
→ PRD 条目
→ 原型页面/生产页面
→ API
→ 数据集与字段
→ 指标或业务规则
→ 权限规则
→ 测试用例
→ 验收结果
```

建议使用稳定编号：

- `GRD-*`：成绩与有效结果。
- `GROW-*`：学生成长轨迹。
- `PLAN-*`：培养方案与课程缺口。
- `COURSE-*`：课程开设和课程日历。
- `ROOM-*`：教室资源。
- `FAC-*`：师资和课程团队。
- `AUTH-*`：身份、角色和数据权限。
- `NFR-*`：性能、安全和运维。

## 7. 生产目标架构需要明确的事项

后续技术团队必须在详细设计阶段作出并记录以下决策：

- 业务库与分析库是否分离。
- 学校源系统采用接口、CDC、文件还是数据库视图同步。
- 学生课程状态采用实时计算、批处理还是混合方式。
- 指标计算的版本、重算和历史回溯机制。
- 统一身份认证协议及账号映射。
- RBAC 与学院/专业/班级/教学班数据范围组合方式。
- 报表导出、异步任务和大文件存储。
- 高可用、备份、RPO/RTO、日志留存和审计周期。
- 性能目标、并发用户、数据规模和刷新时效。

上述数值需要由学校和开发团队确认，不在原型阶段虚构生产容量指标。

## 8. 核心算法交接要求

以下规则不能只保留在代码中：

### 8.1 最终有效成绩

- 输入：全部成绩尝试和正式状态代码。
- 输出：每名学生每门课程当前有效结果及历史尝试。
- 必须说明补考、重修、作废、更正、课程等价的优先级。
- 提供学校确认的样例和反例。

### 8.2 培养方案差异

- 方案要求减去已通过、在修、已认定和等价课程。
- 区分应选未选、尚未到建议学期、未通过待重修和规则例外。
- 输出对毕业和学位要求的影响证据。

### 8.3 学生成长与建议

- 以学期为时间轴记录学业事件。
- “大一挂科导致后续困难”只能作为待验证假设，不直接作为因果结论。
- 建议必须返回依据、可用课程资源和人工核验提示。

### 8.4 排课偏好与课程团队风险

- 排课偏好只使用真实历史课程日历，并返回样本量和稳定性。
- 团队风险用于课程资源规划，不直接形成教师绩效结论。

## 9. 权限与隐私交接要求

生产系统需明确：

- 学生本人仅查看自己的记录和建议。
- 辅导员查看负责班级的成长记录。
- 当前任课教师仅查看与授课任务相关的必要信息。
- 学院和专业管理者按组织范围查看汇总和授权明细。
- 学校管理者的个人明细访问进入安全审计。
- 姓名、学号等字段按角色脱敏。
- 导出权限与页面查看权限分别控制。
- 组织和教学关系均需带生效时间，避免历史越权。

## 10. 非功能性交接清单

- 容量：学生、成绩、教学班、课程日历历史规模预测。
- 性能：页面、聚合查询、导出和批量计算目标。
- 可用性：服务等级、降级和故障恢复。
- 数据时效：各数据域刷新频率和延迟提示。
- 安全：SSO、密钥、传输加密、审计和漏洞修复。
- 运维：日志、指标、链路追踪、告警和运行手册。
- 数据治理：质量监控、补数、重算、血缘和责任人。
- 兼容性：浏览器、分辨率和校内网络环境。

## 11. 分阶段开发路线

### 阶段 0：数据与交接基线（当前）

- 完成数据缺口清单和学校取数模板。
- 建立交接文档目录、需求编号和决策日志。
- 标记原型中的真实、派生、模拟和暂缓能力。

### 阶段 1：核心学业数据模型

- 成绩尝试、最终有效成绩和课程等价。
- 版本化培养方案和学生课程状态。
- 数据质量、血缘和重算机制。

### 阶段 2：学生成长与课程建议

- 成长时间轴和低年级受挫队列。
- 应选未选、待重修和毕业影响。
- 管理端及学生建议 API。

### 阶段 3：课程、资源与师资分析

- 单门课程画像和标准课程日历。
- 体育、思政等课程时段热力图。
- 消费上游教室可用资源主数据并分析，不建设资源维护功能。
- 教师历史排课偏好和课程团队风险。

### 阶段 4：生产工程化

- SSO、权限、审计和隐私。
- 增量同步、性能、监控和备份恢复。
- 全角色验收、数据对账、部署和回滚。

预警后续处置闭环不进入上述必做阶段，待产品范围决策后单独立项。

## 12. 交接完成定义

生产开发团队在不依赖原作者口头解释的情况下，应能够：

- 说清每个模块做什么和不做什么。
- 找到每项需求的数据来源、公式和权限规则。
- 用脱敏样例复现核心计算结果。
- 区分可复用原型设计和必须重构的实现。
- 建立开发任务、估算依赖并编写测试。
- 完成环境部署、数据同步、回滚和故障处置设计。
- 识别所有待学校确认或缺少数据的事项。
