## 0. 项目一句话定位

一个面向高校教务的**学业数据分析 BI 平台**（只读看板，不干预业务数据），服务校领导 / 教务处 / 二级学院等 **10 类角色**，基于脱敏真实教务数据，做到**生产演示级**效果。

---

## 1. 现状（基线）

**工程**：`平台管理端-0618/平台管理端-0618/`
- 技术栈：Vue 3 + Vite 7 + TypeScript + Element Plus + Pinia + ECharts + Tailwind
- 路由：hash 模式，**26 个页面**（见 `src/router/index.ts`）
- 权限：按 10 类角色做路由 + 菜单映射（`src/config/permissions.ts`、`src/store/role.ts`）
- **数据现状（待改造）**：
  - 一半页面走 `fetch('/api/admin/...')`，mock 写死在 `vite.config.ts` 中间件里 —— **仅 dev 生效，build 后无接口**
  - 另一半页面数据**内联硬编码**在组件里
  - **没有真正的后端**
- 视觉现状：最朴素的 Element Plus 蓝（深色侧边栏 `#1E3A5F` + 白色内容区）

**角色清单（10 类）**：校领导、教务处处长、教务处运行科、教务处教研科、教务处实践科、质量办/评估中心、二级学院院长、二级学院教学秘书、辅导员、系主任。

**页面分组**：数据大屏（含学院/专业/课程/学生五级下钻）、预警查看、教学运行分析、培养质量分析、师资结构分析、学生学业分析、实践教学分析、报表中心、学校管理、数据同步、系统设置。

## 3. 关键决策（已拍板）

| 决策项 | 选择 |
|---|---|
| 后端技术栈 | **Python FastAPI + pandas/SQL**（适配大体量 Excel ETL + 聚合计算） |
| 演示数据策略 | **真实历史 + 模拟新学期(2025-2026)增量**，让看板像活系统 |
| 推进方式 | **按阶段顺序全流程做** |
| 视觉风格 | **现代浅色 SaaS 后台**（清爽、留白足、专业） |
| 登录与鉴权 | **完整登录 + 鉴权**；权限模型改为 **RBAC 可配置**（用户→角色→菜单/页面权限后台可配），弃用原型写死的 10 角色硬映射 |
| 演示环境 | **本机一键启动脚本**（同时拉起 FastAPI + 前端） |
| 缺口策略 | 真实数据凑不齐前端指标时，**逐个拉出来给用户确认**（补数 or 调整前端需求），不擅自决定。作为阶段1 评审关卡 |

**目标架构**：
```
Vue3 前端(现代浅色 SaaS)
   ↓ HTTP
FastAPI 接口层(角色数据权限过滤)
   ↓
分析库(SQLite/Postgres：维表 + 事实表 + 预聚合表)
   ↑
pandas ETL  ←  脱敏真实 Excel + 模拟新学期增量
```

### 防脱节机制（贯穿全程的三道锁）

核心思想：**所有"对齐"动作都在阶段1 完成，后面阶段只按图施工**。

1. **指标血缘表**（阶段1）→ 锁住"前端指标 ↔ 数据字段"。每行=一个前端指标，列出：页面/指标/口径公式/依赖字段/真实数据是否支持/缺口对策。**红色缺口在阶段1 暴露，逐个给用户确认对策。**
2. **API 契约**（阶段1 技术方案）→ 锁住"后端 ↔ 前端"。接口字段直接对应前端组件数据形状，契约先行。
3. **逐页规格书**（阶段1）→ 既是开发图纸，又是阶段5 验收清单。

做法：勘探与逐页规格**穿插进行**——先列 26 页要显示什么 → 形成指标需求清单 → 带清单去勘探 → 边勘探边填血缘表。

### 数据链路（5 环节，贯穿阶段1→2）

```
①勘探 → ②建模 → ③采集 → ④加工/ETL → ⑤入库 → 接口/前端
```

| 环节 | 做什么 | 产出 | 所在阶段 |
|---|---|---|---|
| ① 勘探 profiling | 摸清每个 Excel 字段含义/枚举/行数/脏数据/关联键 | **数据字典.md + 质量报告** | 阶段1（现在） |
| ② 建模 modeling | 设计分析库：维表+事实表+预聚合表 | 技术方案.md 的库表设计 | 阶段1 |
| ③ 采集 extract | 流式读原始 Excel（大文件分块） | ETL 脚本 extract | 阶段2 |
| ④ 加工 transform | 清洗+关联（选课↔课程↔成绩）+聚合（算指标） | ETL 脚本 transform | 阶段2 |
| ⑤ 入库 load | 写入分析库 SQLite | ETL load + 分析库文件 | 阶段2 |

**数据字典解决的问题**：①消除字段歧义 ②验证关联键能否 join ③摸清数据质量底数 ④验证指标口径有无数据支撑。它是数据层的"接口契约"，避免前端/后端/ETL 三方各猜一套导致返工。

**重要原则**：阶段1 只"看不动"——只读抽样、只出文档与设计图，**不读 236MB 全量、不写库、不跑全量 ETL**。设计要改时成本最低。
