# 学业预警闭环改造设计

## 1. 改造目标

将当前“ETL 生成预警＋管理者查看列表”升级为：风险计算、责任人分派、通知、跟进、复核、解除和审计完整闭环。

## 2. 目标流程

1. 预警引擎按批次计算候选风险；
2. 相同学生、规则和风险窗口进行幂等合并；
3. 根据学院、班级、课程和角色分派责任人；
4. 生成站内通知记录；
5. 责任人确认、联系、约谈或制定帮扶措施；
6. 下一批次重新计算风险；
7. 达到解除条件后进入待复核；
8. 复核通过后关闭，完整保留历史。

## 3. 状态模型

| 状态 | 含义 | 允许操作 |
|---|---|---|
| `new` | 新识别，尚未分派 | 自动/人工分派 |
| `assigned` | 已分派责任人 | 通知、转派 |
| `notified` | 责任人已收到 | 确认、联系学生 |
| `contacted` | 已联系学生 | 记录沟通结果 |
| `supporting` | 帮扶中 | 添加措施和阶段记录 |
| `review_pending` | 风险指标已改善，等待复核 | 通过或退回 |
| `resolved` | 已解除 | 查看历史 |
| `closed` | 无效、误报或不再适用 | 查看关闭原因 |

状态不能再由 ETL 随机生成。预警计算结果和人工处理状态必须分表保存。

## 4. 推荐数据模型

### `alert_event`

保存每个学生每条规则在一个风险窗口中的预警事件：

- `event_id`
- `student_id`
- `rule_id`
- `severity`
- `risk_window`
- `trigger_value_json`
- `trigger_detail`
- `first_detected_at`
- `last_detected_at`
- `engine_batch_id`
- `status`
- `source`

唯一约束：`student_id + rule_id + risk_window`。

### `alert_assignee`

- `event_id`
- `assignee_username`
- `assignee_role`
- `assignment_reason`
- `assigned_at`
- `is_primary`

### `alert_notification`

- `notification_id`
- `event_id`
- `recipient`
- `channel`
- `sent_at`
- `read_at`
- `delivery_status`

第一期只实现站内通知，短信、邮件和企业微信作为后续连接器。

### `alert_followup`

- `followup_id`
- `event_id`
- `operator`
- `action_type`
- `content`
- `next_action_at`
- `created_at`

### `alert_status_history`

- `event_id`
- `from_status`
- `to_status`
- `operator`
- `reason`
- `changed_at`

### `alert_engine_batch`

- `batch_id`
- `semester_id`
- `started_at`
- `finished_at`
- `data_version`
- `rule_version`
- `student_count`
- `event_count`
- `status`

## 5. 责任人分派规则

| 场景 | 主责任人 | 抄送/可见 |
|---|---|---|
| 学生综合学业风险 | 辅导员 | 学院教学秘书、学院负责人 |
| 单门课程集中风险 | 任课教师 | 开课学院教学负责人、学生辅导员 |
| 学分或培养方案风险 | 学院教学秘书 | 专业负责人、辅导员 |
| 高退学/延毕风险 | 学院负责人 | 教务处、辅导员、教学秘书 |

任课教师只能看到与本人授课关系相关的必要学生信息，不能借推送入口查看全院学生。

## 6. 新规则规划

| 规则 | 定位 | 建议等级 |
|---|---|---|
| R5 大一学业风险 | 入学前两学期出现未解决挂科 | 关注/提醒 |
| R7 反复挂同一课程 | 同一课程未通过不少于 2 次 | 警告 |
| R8 毕业进度风险 | 预计毕业学期前学分或必修模块缺口过大 | 严重 |

新增规则前必须先解决考试性质、最终通过状态和培养方案覆盖问题。

## 7. API 改造

### 查询

- `GET /api/admin/alerts`：以学生/事件为主体分页，返回规则证据、责任人和跟进状态；
- `GET /api/admin/alerts/{event_id}`：事件详情；
- `GET /api/admin/students/{student_id}/risk-timeline`：逐学期风险轨迹；
- `GET /api/admin/alerts/inbox`：当前用户待处理预警；
- `GET /api/admin/alerts/statistics`：学生数、事件数、处理时效、解除率。

### 写操作

- `POST /api/admin/alerts/{event_id}/assign`
- `POST /api/admin/alerts/{event_id}/followups`
- `PUT /api/admin/alerts/{event_id}/status`
- `POST /api/admin/alerts/{event_id}/review`

所有写操作写平台管理库，不回写教务源库，并记录操作审计。

## 8. 页面改造

### 预警总览

- 待处理、处理中、待复核、已解除四组指标；
- 按学生去重的风险列表；
- 规则证据标签；
- 主责任人和最后跟进时间；
- 超期未处理提示；
- 批量分派与导出。

### 学生风险档案

- 基本信息与当前结论；
- GPA、学分、挂科和预警逐学期轨迹；
- 未解决课程清单；
- 反复挂科时间线；
- 任课教师和开课学院溯源；
- 责任人与跟进记录；
- 状态流转历史。

### 我的待办

面向辅导员、任课教师和教学秘书，只展示与本人职责相关的事件。

## 9. 分步实施

1. 修正成绩最终状态和预警计算口径；
2. 新建事件、责任人、跟进和历史表；
3. 将现有 `fact_alert` 迁移为初始事件；
4. 增加事件查询和状态写接口；
5. 重构预警总览和学生风险详情；
6. 增加“我的待办”和角色数据范围；
7. 增加 R5、R7、R8；
8. 完成全角色回归和处理时效报表。

## 10. 第一开发批次建议

第一批只做最小完整闭环：

- 事件表；
- 主责任人；
- 跟进记录；
- 状态历史；
- 预警详情；
- 辅导员和管理员两类角色；
- 站内待办；
- 不接入外部消息渠道。

完成该批次后，再扩展任课教师推送和新规则，风险更可控。
