# 教学运行分析 UE 深度走查与优化方案

> 版本：V1.0
> 模块：教学管理分析 / 教学运行分析
> 状态：六项产品决策已确认；T1—T7已完成，T8验收与文档收口中
> 共同基线：`docs/93-教学管理分析UE公共契约.md`
> 走查日期：2026年7月24日

## 1. 模块定位

教学运行分析不应只是把课程、教室、教师和调课统计放到六个 Tab 中，而应帮助教务处、二级学院教学管理人员和排课人员依次回答：

1. 当前学期教学供给是否按计划形成；
2. 哪些课程存在班额、教师覆盖或单班集中供给线索；
3. 重点课程的星期、时段和晚间安排是否过度集中；
4. 教室实际占用在哪些楼宇和时段形成压力；
5. 教师任务分配是否存在需要排除数据异常后再核查的集中现象；
6. 调停课是否集中于特定学院、教师、原因或月份；
7. 多学期课程结果是否提示下一轮开课、重修或教学资源需要提前准备。

本模块只提供事实分析、优先级和证据核查，不自动排课，不认定教师超负荷，不评价教师教学质量，不替代调课审批，也不维护学校业务主数据。

## 2. 本次走查范围

本次按二级学院院长身份、人工智能学院明细范围进行真实页面操作，并联合检查了：

- 课程总览；
- 教室利用率；
- 调课记录；
- 教师负荷；
- 课程排课分析；
- 课程质量核查；
- 统一学期切换和 Tab 懒加载；
- 课程、楼宇、教师和课程结果下钻；
- 前端筛选、加载、空状态和错误状态；
- V1 与 V2 数据库的实际覆盖学期；
- 后端权限、指标计算、异常排除和数据来源说明；
- 业务表格与 UE 公共契约的差距。

## 3. 已确认的正面基础

- 六个工作区已经统一归入一个一级业务页面，没有重复侧栏入口。
- Tab 路由可以复制和刷新，并保留旧专题兼容重定向。
- 教室实际占用已接入49,911条记录、172间已观测教室和124个日期。
- 教室热力图已经改为固定四色分段，不再使用可拖动颜色范围。
- 开课供给已具备TOP10、完整清单和课程核查抽屉。
- 调停课原因保留原文，并用可解释关键词规则进行语义分类。
- 教师负荷已经提供课程构成证据抽屉，并声明排名不等同于超负荷认定。
- 课程结果已拆分首次、补考和重修通过率。
- 部分表格已经使用公共 `DataTable`，具备列设置、顺序调整和密度控制基础。

这些基础可以保留，但当前仍存在会直接影响管理判断的口径、权限和交互问题。

## 4. 真实走查证据

### 4.1 数据域的实际覆盖学期不同

| 数据域 | 当前覆盖 |
|---|---|
| V1教学任务 `fact_lesson` | 2021-2022-2 至 2025-2026-2，共9个学期 |
| 实际教室占用 `fact_room_occupancy` | 仅2025-2026-2 |
| 调停课 `fact_schedule_change` | 2021-2022-2 至 2025-2026-2，共9个学期 |
| V1教师负荷 `agg_teacher_load` | 2021-2022-2 至 2025-2026-2，共9个学期 |
| V2结构化教学任务 `teaching_lesson` | 仅2023-2024-1，1,593个教学班、742门课程 |
| V2课程日历 `course_meeting` | 仅2023-2024-1，3,784条排课片段 |
| V2成绩修读记录 `grade_attempt` | 2018-2019-1 至 2025-2026-2 |

当前页面顶部统一显示“2025-2026-2”，但课程供给和排课策略的V2接口只能提供2023-2024-1，课程结果又是多学期窗口。一个统一学期标签无法真实表达六个工作区的时间范围。

### 4.2 课程总览出现同页口径冲突

二级学院身份进入2025-2026-2时，同页出现：

- “V2真实教学任务已关联0门课程”；
- “人工智能学院26门课程、110个教学班”；
- 真实原因不是学院没有课程，而是V2开课接口只允许全校身份访问。

页面同时提供顶部统一学期、页内学期和学年，共七项筛选条件，且多数条件改变后立即请求。用户无法判断：

- 顶部学期和页内学期谁生效；
- “26门”和“0门”是否属于同一数据源、同一学期；
- 课程TOP10、学院规模和四个指标是否受同一组条件影响。

### 4.3 二级学院可以进入两个没有数据权限的工作区

下列V2接口使用 `require_v2_all_reader`，仅允许全校范围身份：

- `/api/v2/courses/offerings`；
- `/api/v2/topics/schedule-strategy`；
- `/api/v2/topics/course-quality`；
- `/api/v2/topics/course-quality/{course_id}/detail`。

二级学院菜单仍显示“课程排课分析”和“课程质量核查”。进入后：

- 排课分析长期停留在“加载中”、0和No Data；
- 课程质量加载结束后显示0门、0人次和空表；
- 页面只出现短暂错误消息，没有持久的无权限说明；
- 用户会误以为本学院没有数据。

这是服务端权限语义和前端菜单/空状态不一致，不是普通空数据问题。

### 4.4 教师负荷包含已识别异常数据

2025-2026-2教学任务已经识别5名“单教师单学期教学班数超过200”的异常教师，并在课程统计中排除了5,248条记录；教师负荷却没有应用同一排除规则。

实际页面出现：

- 人工智能学院人均学时1,278；
- 某教师11,330学时、252个教学班、108门课程；
- 全校最大记录为92,078学时、3,567个教学班；
- 全校有85名教师超过当前“280学时”阈值。

页面随后将教师标为“AI重点”“过载”，并把各职称显示为“达标”。在数据异常未排除、学校工作量办法未配置、合讲拆分和减免规则未接入前，这些结论没有管理可信度。

### 4.5 调停课来源说明与实际加工不一致

调停课记录由真实 `course_changes` 数据转换形成，原始原因文本和事件来源可以作为真实证据；但以下字段是原型规则推导，不是审批系统原始事实：

- 学时按2、4、6小时等规则归档；
- `hours<=4` 被推导为“自动审核”；
- 审核时间被固定推导为0.6天或2.2天。

页面却同时写着：

- 数据来源是调停课记录表；
- 当前记录为固定种子构造数据；
- 院系自动审核0%、教务审核100%、平均审核时间2.2天。

真实事件和推导字段被混在一起，用户无法判断哪些数字可用于正式管理。

### 4.6 教室占用加载期间先显示正式0值

教室页首次加载约5秒后才显示49,911条实际占用记录，加载过程中顶部先显示：

- 实际占用记录0；
- 已观测教室0；
- 最高时段负荷0%；
- 晚间占用记录0。

虽然页面存在加载遮罩，但正式0值仍在背景可见，容易形成“先无数据、后突然有数据”的闪烁。当前教室页面展示的是“已观测教室范围内的实际占用强度”，不是学校正式教室利用率，Tab名称“教室利用率”仍可能造成误读。

### 4.7 已访问Tab会在学期变化时同时重载

父页面用 `contentKey` 重建所有已经访问过的组件。用户访问多个Tab后再切换学期，会同时触发课程、教室、调课、负荷、排课和课程结果请求。

结果是：

- 当前Tab的局部筛选会丢失；
- 未显示的已访问Tab也重新执行高成本查询；
- V2无权限请求会再次失败；
- 教室占用等慢查询叠加，用户感觉整页卡顿；
- 不符合“只加载当前Tab、已访问Tab按条件缓存”的公共契约。

### 4.8 表格和详情交互不统一

- 课程TOP10、调课学院表、调课教师表和课程质量主表使用公共 `DataTable`；
- 课程完整清单、楼宇表、教师负荷三个表、排课课程表仍使用普通 `el-table`；
- 普通表格不能自定义列、调整顺序或恢复默认布局；
- 课程完整清单打开详情时形成两层抽屉，但没有明确“返回课程清单”；
- 课程质量点击“查看学期变化”后滚动到长页面底部，用户离开原名单位置；
- 教师负荷和调停课抽屉中的“查看教师完整档案”直接跳到师资模块，没有保留返回来源。

## 5. 根因判断

当前问题主要来自五个结构性原因：

1. 父页面把不同覆盖周期的数据域强行包装成一个统一学期；
2. V1业务接口已支持学院范围，V2课程和排课接口仍只有全校权限；
3. 同一异常排除规则没有在课程、教师负荷和AI研判中统一复用；
4. 真实字段、规则推导字段和原型构造字段没有形成统一证据等级；
5. 六个Tab分别演进，缺少统一的加载、错误、表格和详情契约。

因此不能只调整卡片样式或文案，必须先修复数据上下文和权限，再改页面呈现。

## 6. 建议目标信息架构

六个Tab继续保留，不增加侧栏子菜单，建议按教学运行过程重新排序并改名：

1. **开课供给**：当前教学任务、课程供给规模和重点核查课程；
2. **排课结构**：星期、时段、重点课程和晚间安排；
3. **教室占用**：实际占用时序、活动构成和楼宇压力；
4. **教师负荷**：排除异常后观察任务集中和课程构成；
5. **调停课分析**：事件规模、原因、教师和月份集中；
6. **课程结果**：多学期首次、补考、重修结果及资源准备线索。

建议不新增单独“运行总览”Tab。开课供给作为默认入口，在首屏增加一条有限的“当前运行关注摘要”，只显示本模块最需要进一步核查的3—5件事，并链接到对应Tab。

## 7. 统一分析上下文方案

### 7.1 建立数据可用性清单

新增教学运行上下文接口，按数据域返回：

- 可用学期；
- 默认学期；
- 数据截止时间；
- 数据来源；
- 证据等级；
- 当前身份的明细范围；
- 是否支持跨学院聚合比较；
- 当前学期不可用时的建议可用学期。

### 7.2 单学期与多学期窗口分开

- 开课供给、排课结构、教室占用、教师负荷、调停课使用单学期上下文；
- 课程结果使用起止学期窗口，不受顶部单学期直接控制；
- 进入课程结果Tab时，顶部上下文明确改为“结果观察期：起始学期—结束学期”；
- 不允许在2025-2026-2页面静默调用2023-2024-1的教学任务后仍标成当前学期。

### 7.3 不可用学期的处理

当所选学期不具备某数据域时：

- 保留页面结构；
- 显示“当前学期未接入该数据域”；
- 展示最近可用学期和数据来源；
- 提供“切换到2023-2024-1”等明确操作；
- 不显示正式0值；
- 不静默回退到另一个学期。

### 7.4 不同Tab使用不同范围语义

| Tab | 二级学院明细范围 | 可见跨学院信息 |
|---|---|---|
| 开课供给 | 本学院开设或承担的课程、教学班 | 其他学院聚合供给规模 |
| 排课结构 | 本学院开课任务和课程排课片段 | 全校时段基线及学院聚合比较 |
| 教室占用 | 默认显示全校共享空间聚合，不显示其他学院人员明细 | 楼宇与时段聚合 |
| 教师负荷 | 本学院教师和课程构成 | 其他学院聚合分布，不下钻教师 |
| 调停课分析 | 本学院调停课及教师原因明细 | 其他学院调课率聚合 |
| 课程结果 | 默认按开课/责任学院管理课程结果 | 可增加“影响本院学生”聚合视角，不混入默认口径 |

教室占用页的上下文应显示“资源范围：全校共享教室聚合”，不能继续显示“明细范围：人工智能学院”后又给出全校楼宇。

## 8. 各工作区改造方案

### 8.1 开课供给

首屏依次呈现：

1. 当前学期、开课责任范围、数据截止时间和覆盖状态；
2. 当前运行关注摘要；
3. 四个核心指标；
4. 开课保障关注TOP10；
5. 学院供给聚合比较；
6. 课程和班额结构；
7. 完整课程清单入口；
8. 数据质量与使用边界。

建议四个指标：

| 指标 | 计算逻辑 | 管理用途 |
|---|---|---|
| 开课课程数 | 当前学期、当前责任范围内去重课程数 | 判断供给规模 |
| 教学班数 | 当前范围内有效教学任务数 | 估算任务和排课规模 |
| 选课/任务学生人次 | 各教学班有效选课人数之和 | 判断资源影响规模 |
| 需关注课程数 | 命中已版本化供给规则的去重课程数 | 安排课程供给核查 |

调整要求：

- 当前学期以V1真实教学任务作为原型主事实，V2只在实际覆盖学期展示；
- V1和V2不能在同一选定学期下分别给出两个相互冲突的课程数；
- 七项筛选改为“草稿条件＋应用筛选”，页内删除重复学期选择；
- TOP10必须返回入选原因和命中阈值，默认按受影响学生规模优先；
- “单一教师多班覆盖”只作为任务集中线索，不等同团队风险；
- 数据质量只保留只读排除说明和证据，不在业务页面维护处置状态。

### 8.2 排课结构

建议核心指标：

- 有排课证据的教学班数；
- 排课片段数；
- 高峰时段及占比；
- 晚间排课片段及占比；
- 重点课程覆盖数。

调整要求：

- V2排课接口按当前工作身份应用开课组织范围；
- 全校身份看全校，学院身份看本院明细并可对照全校聚合基线；
- 体育、思政、数学、英语继续作为首批重点课程，但生产系统改用课程主数据标签；
- 热力图改为固定分段，不使用可拖动连续色域；
- “峰值占比”只说明集中，不自动判断冲突或不合理；
- 课程组“查看课程”进入核查抽屉，继续显示该组筛选、学期和返回路径；
- 未来排课优化所需的教师可用时间、学生冲突和正式可用教室数据未接入时，不生成可执行排课建议。

### 8.3 教室占用

建议把Tab和页面统一命名为“教室占用”，核心指标保留：

- 实际占用记录；
- 已观测教室；
- 最高时段观测负荷；
- 晚间占用记录。

调整要求：

- 全部用“观测负荷/实际占用强度”，不写“全校教室利用率”；
- 首次加载显示骨架，数据返回前不显示0；
- 楼宇和晚间开关只刷新图表、指标和楼宇表，不阻塞整个模块；
- 当前固定四色热力图保留，拖动能力继续禁用；
- 楼宇抽屉显示日期覆盖、观测教室、占用记录、重叠和待映射证据；
- 慢查询改为预聚合或数据批次完成后生成学期汇总，缓存键必须包含数据版本、范围、学期、楼宇和晚间开关。

### 8.4 教师负荷

在学校工作量办法、合讲拆分、减免规则和完整教师状态尚未确认前，统一使用“负荷核查线索”，不使用“过载认定”和“达标”。

建议核心指标：

| 指标 | 计算逻辑 | 管理用途 |
|---|---|---|
| 有效授课教师数 | 排除已确认数据异常后，有有效教学任务的去重教师数 | 判断实际师资投入规模 |
| 教师学时中位数 | 有效授课教师总学时的中位数 | 减少极端值对平均数影响 |
| 教师学时P90 | 90%教师不超过的学时值 | 判断任务集中上沿 |
| 高负荷核查人数 | 超过学校已确认阈值，或超过统计分位阈值的教师数 | 形成有限核查队列 |
| 已排除异常教师数 | 当前计算中因数据质量问题未计入的教师数 | 说明结论可信边界 |

调整要求：

- 课程统计、教师负荷、学院比较和AI研判复用同一异常排除函数；
- 异常数据未修复前不进入人均学时、TOP10和学院比较；
- 教授、副教授“上课率”只有在完整在岗名册、岗位状态和学校阈值确认后才展示；
- 职称表改为“授课教师数、中位学时、P90学时、课程数和证据覆盖”，删除未经确认的“达标”；
- TOP10入选原因必须说明相对中位数/P90、课程数、教学班数和学生覆盖；
- 教师核查默认在当前抽屉完成；如保留完整档案，必须携带来源路径并返回原筛选和滚动位置。

### 8.5 调停课分析

建议区分三类字段：

1. **源事实**：事件类型、教师、学院、原始原因、申请时间、影响学生数等；
2. **规则推导**：语义分类、原因集中度；
3. **当前不具备**：真实审批方式、审批耗时、补课完成情况。

建议核心指标：

- 调课事件数；
- 停课事件数；

## 12. AI入口调整

普通Tab不再平铺“生成当前重点”作为默认主操作。AI只在以下场景出现：

- 已由确定性规则形成的有限优先课程；
- 排除数据异常后的高负荷教师核查抽屉；
- 高频调停课且原因集中的教师或学院；
- 高峰教室时段或高负荷楼宇；
- 多学期持续异常且影响范围较大的课程。

AI结果必须复用页面同一口径和权限，披露数据源、学期、范围、阈值、规则版本和边界。AI不得把供给线索解释为课程质量问题，不得把负荷线索解释为教师评价，不得把调课频次解释为责任认定。

- 教室共享资源范围有单独说明；
- 直接调用V2接口不能绕过身份范围；
- 不适用的辅导员、班主任和导师默认不显示本模块入口。

### 15.3 交互

- 六个Tab路由、筛选、滚动和返回状态可恢复；
- 切换学期不同时重载所有已访问Tab；
- 数据返回前不显示正式0；
- 无权限、无数据、未接入和接口失败状态可以区分；
- 所有详情优先在当前页面抽屉打开；
- 课程和教师跨模块入口携带明确返回来源；
- 所有正式表格支持列设置、顺序和显示上限。

### 15.4 性能

- 300毫秒内出现结构或加载反馈；
- 常规摘要目标2秒左右呈现；
- 常规主内容目标5秒内可用；
- 教室占用首次查询不重复执行高成本聚合；
- TOP与完整清单不在首屏同时加载；
- 未激活Tab无业务请求。

## 16. 已确认的产品决策

以下六点已确认，并作为T1—T8实施约束：

1. 六个Tab改为“开课供给、排课结构、教室占用、教师负荷、调停课分析、课程结果”，并按此顺序排列；
2. 课程结果对二级学院默认使用“本学院开设/负责课程”口径，“影响本院学生”作为独立聚合视角；
3. 教室占用对学院角色显示全校共享资源聚合，但不暴露其他学院人员或课程明细；
4. 在学校正式工作量办法未配置前，教师负荷不显示“过载认定”和“达标”，只显示核查线索；
5. 调停课页面删除规则推导形成的审批比例和审核时间，保留真实事件、原因分类和影响范围；
6. 课程结果使用独立多学期窗口，不受顶部单学期直接控制。

后续实施不得自行改变上述口径；确需调整时应先更新本方案并重新确认。
