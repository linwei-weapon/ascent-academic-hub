# 学生成长与学业分析 UE 深度走查与优化方案

> 文档状态：已确认；阶段 A—E 已实施并通过自动化、五类身份浏览器、客户口径文档及模块 Git 收口
> 适用模块：教学管理分析 / 学生成长与学业分析
> 依据：`docs/93-教学管理分析UE公共契约.md`
> 走查日期：2026-07-24

## 1. 本轮目标与边界

本轮不是继续增加学生画像图表，而是把“学生成长与学业分析”收口为一个能够回答以下管理问题的工作区：

1. 当前范围内有多少学生具备可比较的连续学期成绩证据。
2. 哪些学生正在改善，哪些学生出现了明确恶化、连续受挫或低年级首次受挫。
3. 问题主要集中在哪个学院、专业、年级或行政班。
4. 每名进入关注队列的学生为什么被识别，原始成绩、挂科、培养方案和预警证据是什么。
5. 校级、学院、辅导员、班主任和导师如何在各自权限内完成“发现—定位—核查证据”，而不是在多个页面之间跳转。

本模块坚持以下边界：

- 分析学生学业变化与成长证据，不扩展为学生工作管理系统。
- 不在本模块中执行预警规则、干预任务或处置闭环；预警记录仅作为学生成长证据。
- 不以单一 GPA、单次挂科或不透明综合分数评价学生。
- 不把历史上曾经挂科但已经通过的课程继续呈现为当前未解决风险。
- 不使用模拟毕业率、模拟学位获得率形成正式管理结论。
- AI 只对少量需要综合研判的学生提供辅助解释，不能逐行生成套话，也不能扩大数据权限。
- 培养方案完成情况复用“培养质量分析”的可信口径，不在本模块维护第二套学分计算。

## 2. 走查范围与方法

本轮已完成以下检查：

- 以二级学院身份走查学生成长总览、画像迁移、学生名单和学生证据抽屉。
- 以辅导员身份走查“我的班级/学生”、班级展开和学生详情路径。
- 以导师身份走查菜单入口、本人所带学生范围和学生详情路径。
- 检查校级、学院、辅导员、班主任和导师对应的后端数据范围实现。
- 核对主分析页、学生名单、角色工作区、学生档案、培养方案进度等前后端计算。
- 使用现有真实成绩数据复核 GPA、挂科、学分、迁移分组和连续受挫规模。
- 测量主要分析接口的冷启动与缓存响应表现。
- 按公共 UE 契约检查筛选、加载、状态保持、表格、抽屉、返回和列配置行为。

## 3. 当前可保留的能力

现有实现具备以下可复用基础：

- 已具备学院、专业、年级、行政班、学期等多维筛选能力。
- 已具备相邻学期 GPA 与挂科变化的迁移分析雏形。
- 学生名单已使用公共 `DataTable`，具备分页和列配置基础。
- 学生名单的详情使用抽屉呈现，能够在不离开名单的情况下查看学期变化、挂科和预警记录。
- 辅导员、班主任和导师的人员关系数据已经接入，后端能够形成班级或导师学生范围。
- 学院范围能够在服务端限制到本学院学生，直接接口未简单依赖菜单隐藏。
- 主分析接口已经具备按权限和筛选条件缓存的基础。

这些能力应在改造时保留，但必须统一指标口径、角色入口和证据链。

## 4. 深度走查发现

### 4.1 P0：GPA 使用简单平均，与已确认的学分加权口径不一致

当前主分析、学生名单和学生详情多处使用：

```text
学生 GPA = AVG(课程绩点)
```

已确认的正式口径应为：

```text
学生学期 GPA =
Σ（课程绩点 × 课程学分）
÷
Σ（纳入 GPA 计算的课程学分）
```

真实数据复核结果：

- 全体学生简单平均 GPA 约为 2.583，学分加权 GPA 约为 2.575。
- 2,270 名学生的累计简单平均与学分加权结果相差不低于 0.1。
- 学生—学期层面的平均绝对差约为 0.113。
- 29,771 条学生—学期记录的差值不低于 0.1。
- 对最近两个实际学期进行迁移分类时，约 1,318 名学生的“改善/稳定/恶化/混合”分类会因 GPA 口径修正而改变，约占可比较学生的 12.9%。

这不是显示精度问题，而是会改变管理关注名单的 P0 口径问题。改造时必须：

1. 建立统一的学生学期加权 GPA 计算服务或汇总事实。
2. 主分析、学生名单、学生抽屉、角色工作区和 AI 证据全部复用同一结果。
3. 明确哪些课程和成绩状态纳入 GPA，补考、重修和重复修读采用学校确认的有效成绩规则。
4. 对缺少学分的课程单独披露，不静默按相同权重计算。

### 4.2 P0：“挂科率”在不同页面代表三个不同概念

当前页面至少存在以下三种同名指标：

| 位置 | 当前实际含义 | 主要问题 |
|---|---|---|
| 学生成长总览 | 未通过成绩记录数 / 成绩记录总数 | 是课程记录未通过率，不是学生挂科率 |
| 我的班级/学生顶部 | 历史上曾有真实挂科记录的学生数 / 当前范围学生数 | 把已解决的历史挂科永久计入 |
| 班级展开行 | 当前学期未通过课程门数 | 与顶部的历史口径直接冲突 |

浏览器复核发现：

- 某辅导员范围顶部显示挂科率 95.5%，但三个班级的当前学期挂科均为 0 门。
- 某导师只带 1 名学生，顶部显示挂科率 100%，该生当前学期挂科为 0 门。

建议不再使用无修饰的“挂科率”，统一拆分为：

```text
本学期未通过课程记录率 =
本学期未通过课程记录数
÷
本学期有效成绩记录数
```

```text
本学期未通过学生率 =
本学期至少有 1 门未通过课程的学生数
÷
本学期具有有效成绩的学生数
```

```text
历史受挫学生数 =
历史上至少出现过 1 门未通过课程的学生数
```

页面必须显示时间范围、分子和分母。角色工作区优先使用“本学期未通过学生率”，并与班级、学生行内证据保持一致。

### 4.3 P0：已获学分可能因重复通过记录被重复累计

当前部分学生档案和分析逻辑直接汇总所有通过记录：

```text
已获学分 = SUM(所有 is_pass = 1 的成绩记录学分)
```

真实数据中：

- 6,236 个“学生—课程”组合存在多条通过记录。
- 若直接累加，将多出 6,713 条通过成绩记录所对应的学分。

培养质量模块已有按课程去重并考虑替代、认定和培养方案范围的处理逻辑。本模块不应继续独立计算，应复用培养质量的可信服务：

1. 同一课程采用学校确认的有效通过结果。
2. 课程替代、学分认定和方案课程范围使用统一规则。
3. “培养方案完成度”只有在学生—方案绑定和证据覆盖满足条件时才输出。
4. 数据证据不足时显示“待核验/暂不可正式计算”，不以简单累计学分替代。

### 4.4 P0：迁移名单看不到导致学生入选的变化证据

从“相邻学期画像迁移”点击“恶化”后进入学生名单，当前默认列主要展示：

- 当前或筛选期 GPA；
- 当前或筛选期未通过课程数；
- 基础组织信息。

列表没有直接展示：

- 起始学期 GPA；
- 目标学期 GPA；
- GPA 变化值；
- 起始学期与目标学期挂科门数；
- 触发“恶化”的具体规则。

实测某学生在名单中显示 GPA 3.12、未通过 0 门，打开抽屉后才能看到最新学期 GPA 2.75、上一学期 GPA 3.50、下降 0.75。名单与抽屉使用的时间范围和 GPA 算法不同，用户无法判断该学生为什么属于恶化名单。

改造后的迁移下钻必须采用同一学期对、同一加权 GPA 和同一分组规则，名单直接展示：

```text
上一学期 GPA → 本学期 GPA（变化值）
上一学期未通过门数 → 本学期未通过门数（变化值）
进入队列的触发原因
```

名单默认按透明的管理优先证据排序，不能继续按 GPA 从高到低排序。

### 4.5 P1：首屏以描述性统计为主，没有形成管理注意力队列

当前首屏包含六个 KPI、GPA 档位、年级 GPA、学分分布、历史挂科模式、课程 TOP10 和迁移图。管理者看到的是大量平铺结果，但不能迅速回答：

- 最近两个学期有多少学生可以比较。
- 恶化是否扩大。
- 哪些学院、专业或班级问题最集中。
- 哪些学生需要现在核查，而不是历史上曾经出现过问题。
- 进入名单后应核查什么证据。

现有“毕业率、学位获得率”来自演示或模拟毕业事实，不应作为正式绿色管理 KPI。历史挂科模式把已经解决和当前未解决混在一起，规模过大，不能直接形成工作优先级。

### 4.6 P1：全局筛选器过多，且对各指标并非同等生效

当前总览同时放置年级、学院、专业、行政班、学期、学年、重修标识、课程性质八个条件，且大部分选择后立即重新请求整个页面。

存在以下问题：

- 学期与学年同时存在，时间语义竞争。
- 预警率使用当前有效预警，不随所选历史学期变化。
- 历史学分分布并不完整响应学期、重修或课程性质筛选。
- “重修”“课程性质”只适用于成绩或课程证据，不应改变所有顶层管理指标。
- 二级学院用户仍看到“全部学院”占位和全校候选项，虽然服务端会限制范围，但界面暗示可以选择其他学院。
- 每次选择立即触发耗时计算，用户难以一次完成多个条件。
- 筛选状态没有完整写入 URL，刷新、分享和下钻返回后可能丢失。

筛选应改为“管理范围”和“局部证据条件”两层：

- 全局范围：学院、专业、年级、行政班、比较起始学期、比较目标学期。
- 局部证据：课程性质、是否重修、课程、挂科状态。
- 受限范围预填并锁定，候选值只返回有权限的范围。
- 三个以上条件采用“调整条件—应用范围”模式，不逐项刷新。
- 显示当前已应用范围摘要，并提供明确的“清除本次筛选”。

### 4.7 P1：角色入口重复，页面没有按照管理任务自适应

当前菜单同时存在：

- 学生成长与学业分析；
- 我的班级/学生。

实际体验：

- 导师同时看到两个入口，不清楚两者差异。
- 辅导员和班主任主要进入“我的班级/学生”，与主模块形成两套交互。
- 学院用户仍能看到“我的班级/学生”，但接口返回空页面，属于无意义入口。
- “我的班级/学生”点击学生会跳转到完整学生档案，与主名单使用抽屉的交互不一致。

建议收口为唯一二级菜单“学生成长与学业分析”，根据当前工作身份呈现不同工作区：

| 当前工作身份 | 默认工作区 |
|---|---|
| 校领导、教务处、系统管理员 | 全校成长与变化总览 |
| 二级学院 | 本学院成长与变化总览 |
| 辅导员、班主任 | 我的班级 |
| 导师 | 我的学生 |

旧地址 `/admin/students/my` 保留兼容重定向，不再维护独立产品入口。

### 4.8 P1：“我的班级/学生”使用长展开表，难以形成日常核查路径

当前班级卡片点击后一次性展开班内全部学生，使用原始表格：

- 无分页；
- 无搜索和排序；
- 无公共列配置；
- 多个班级连续展开后页面很长；
- 学生详情直接跳走；
- 班级排序没有体现管理关注程度。

建议：

- 班级按当前学期未通过学生、恶化学生、当前预警学生等透明证据排序。
- 点击班级后在当前页面的名单区或抽屉中打开分页学生表。
- 学生详情使用全模块共享的“学生学业证据抽屉”。
- 导师只带少量学生时直接展示学生队列，不先显示无意义班级卡片。

### 4.9 P1：学生档案没有区分历史受挫与当前未解决问题

当前挂科分析会汇总全部历史失败记录，即使学生后来已经通过同一课程，仍容易被理解为当前问题。预警记录、挂科记录和培养方案缺口也没有在“为什么关注该学生”的结构下组织。

改造后的学生证据必须区分：

- 历史受挫：曾经未通过，但后续已有有效通过或替代认定。
- 当前未解决：最新有效结果仍未通过，且没有替代或认定证据。
- 重复未解决：同一课程出现至少两次未通过，最新有效结果仍未通过。
- 当前有效预警与历史已解除预警。
- 培养方案明确缺口、候选缺口和证据不足。

“查看完整学生档案”可以作为抽屉内次级入口，但不能代替本次核查所需证据。

### 4.10 P1：主接口过重，整页加载放大等待体感

当前 `/api/admin/students/analysis` 在一个请求中计算所有卡片、图表、挂科模式、课程列表和迁移结果。未命中缓存时会读取大范围：

- 全体通过学分汇总；
- 全体挂科记录；
- 相邻学期成绩；
- 课程未通过率；
- 当前预警。

本地实测：

- 全校未命中缓存请求约 6.75 秒。
- 缓存命中约 15 毫秒。
- 新的辅导员或导师权限范围约 1.05—1.15 秒。

页面使用整页 `v-loading`，已有内容也会被遮挡；选择任一筛选条件都会重新计算全部内容。因此用户会感到页面反复刷新或系统无响应。

### 4.11 P2：描述性图表与其他模块重复，管理用途不清楚

- 课程未通过 TOP10 与教学运行分析存在重复；若保留，应改为“对学生成长变化影响较大的课程证据”，而不是重新做课程质量排名。
- GPA 档位使用固定阈值但没有学校确认依据，不宜称为“学生画像”。
- 年级 GPA 柱状图只能描述平均水平，不能解释是学生结构、课程难度还是学期变化。
- 学分分布在没有统一培养方案绑定和去重规则前，容易形成错误结论。

这些图表不能全部保留在首屏，应服务于明确管理问题或下移到证据层。

## 5. 目标产品定位

模块名称保持“学生成长与学业分析”，页面内部根据角色显示对应标题：

- 校级：全校学生成长与学业变化。
- 学院：本学院学生成长与学业变化。
- 辅导员/班主任：我的班级学业关注。
- 导师：我的学生学业关注。

模块不再以“给每名学生做画像”为中心，而以“识别真实变化、组织管理注意力、提供可核查证据”为中心。

## 6. 目标管理流程

### 6.1 校级用户

```text
选择两个实际学期
  → 判断可比较学生覆盖是否充分
  → 查看改善、恶化和连续受挫规模
  → 按学院比较问题规模与变化
  → 下钻学院/专业/班级
  → 打开学生证据抽屉
  → 核查进入队列的具体原因和原始证据
```

校级用户的价值是发现哪些学院或专业的变化需要说明，而不是逐一浏览全校学生。

### 6.2 二级学院用户

```text
进入本学院范围
  → 查看本院与学校聚合基准的差异
  → 定位专业、年级和行政班
  → 查看本院优先关注学生
  → 核查学期变化、未解决课程和预警证据
```

学院可以看到学校聚合基准，但不能下钻其他学院学生明细。

### 6.3 辅导员和班主任

```text
进入我的班级
  → 查看各班当前学期成绩覆盖与关注规模
  → 选择一个班级
  → 查看本班恶化、首次受挫、连续受挫和当前预警学生
  → 打开学生证据抽屉
```

### 6.4 导师

```text
进入我的学生
  → 直接查看所带学生的当前状态与变化
  → 打开学生证据抽屉
  → 了解为什么需要关注以及哪些事实仍待核验
```

## 7. 目标页面结构

### 7.1 校级和学院级

建议采用一个页面、三个任务区，不增加新的侧栏子菜单：

1. 成长概览。
2. 组织变化与关注分组。
3. 学生证据名单。

学生详情在同页抽屉中打开。

### 7.2 首屏管理指标

建议保留最多五个顶层指标：

| 指标 | 建议口径 | 管理意义 |
|---|---|---|
| 可比较学生 | 两个目标学期均有有效 GPA 或挂科证据的学生数；同时显示占范围学生比例 | 判断变化结论覆盖是否充分 |
| 明确改善学生 | GPA 明显上升或挂科门数下降，且未出现反向变化的学生数/率 | 判断积极变化规模 |
| 明确恶化学生 | GPA 明显下降或挂科门数上升，且未出现反向改善的学生数/率 | 判断需要核查的新增压力 |
| 连续受挫学生 | 最近两个实际学期均有至少一门未通过课程的学生数/率 | 发现问题是否持续 |
| 低年级首次受挫学生 | 低年级学生在目标学期首次出现可观测未通过记录的人数 | 支持尽早关注大一受挫问题 |

“重复未解决课程学生”作为首屏关注提示或替换指标，由最终实现时依据页面空间确认。

每张卡片必须显示：

- 时间范围；
- 分子/分母；
- 是否允许下钻；
- 指标解释；
- 数据边界；
- 当前筛选是否对其生效。

### 7.3 相邻学期变化规则

规则不采用不透明综合分数。建议初始规则：

```text
GPA 变化 = 目标学期加权 GPA - 起始学期加权 GPA
挂科变化 = 目标学期未通过课程门数 - 起始学期未通过课程门数
```

```text
明确改善：
GPA 变化 ≥ 学校确认阈值，且挂科门数未增加
或
挂科门数减少，且 GPA 未明显下降
```

```text
明确恶化：
GPA 变化 ≤ -学校确认阈值，且挂科门数未减少
或
挂科门数增加，且 GPA 未明显上升
```

```text
混合变化：
GPA 与挂科变化方向相反
```

```text
基本稳定：
不满足上述条件
```

GPA 阈值应进入“指标与口径管理”，原型可暂用已存在阈值，但页面必须显示规则版本和阈值，不能隐藏。

### 7.4 管理关注分组

建议提供四类可重叠的真实证据分组：

1. 明确恶化。
2. 连续受挫。
3. 低年级首次受挫。
4. 重复未解决。

“重复未解决”建议定义为：

```text
同一学生、同一标准课程至少出现两次未通过，
且最新有效修读结果仍未通过，
且无有效课程替代或学分认定证据。
```

分组可以重叠，页面应显示“学生可能同时属于多个分组”，不把分组数量相加后解释为唯一学生总数。

### 7.5 组织比较表

校级按学院、学院按专业或行政班比较。默认列建议为：

- 组织名称；
- 范围学生数；
- 可比较学生数与覆盖率；
- 明确恶化学生数与比例；
- 连续受挫学生数与比例；
- 低年级首次受挫学生数；
- 重复未解决学生数；
- 当前有效预警学生数；
- 核查操作。

学院用户可以看到学校中位数或分位位置等聚合基准，但不显示其他学院学生明细。

### 7.6 学生关注名单

默认必显列：

- 姓名；
- 学号；
- 学院/专业/班级；
- 起始 GPA → 目标 GPA；
- GPA 变化；
- 起始未通过门数 → 目标未通过门数；
- 触发原因；
- 当前未解决/重复未解决课程；
- 当前有效预警；
- 详情。

默认排序采用透明优先级：

1. 同时命中连续受挫和重复未解决；
2. 低年级首次受挫；
3. 明确恶化且挂科增加；
4. 仅 GPA 明显下降；
5. 其他。

页面显示排序规则。不得使用未披露的“综合风险分”。

表格遵守公共 UE 契约：

- 默认业务列控制在 8—10 列。
- 姓名/学号、触发原因、详情为不可隐藏列。
- 用户可调整可选列和顺序。
- 可见业务列上限建议 10 列。
- 保存用户偏好和表格版本；公共契约升级时安全迁移。

### 7.7 学生学业证据抽屉

抽屉按以下顺序组织：

1. **为什么出现在这里**：触发分组、阈值、事实值和数据时间。
2. **相邻学期变化**：加权 GPA、修读学分、未通过门数的起点、终点和变化。
3. **当前未解决课程**：最新有效结果、修读次数、历史变化、是否存在替代或认定。
4. **历史受挫与恢复**：已解决课程与恢复证据，避免只呈现负面记录。
5. **培养方案进度**：复用培养质量模块结果，并显示证据覆盖。
6. **预警记录**：当前有效预警和历史已解除预警分开。
7. **证据来源与边界**：数据表、更新时间、规则版本、缺失数据。

AI 研判入口只在证据抽屉内对复合情况提供，输出必须引用上述具体证据，不在学生列表逐行平铺。

## 10. 数据与接口改造建议

### 10.1 统一学生学期事实

建议通过可重复执行的 ETL 或迁移形成统一汇总事实，例如：

```text
agg_student_term_growth
```

至少包含：

- student_id；
- semester；
- weighted_gpa；
- gpa_credits；
- attempted_course_count；
- passed_course_count；
- failed_course_count；
- failed_credits；
- term_earned_credits；
- first_observed_fail_flag；
- grade_coverage_status；
- source_updated_at。

同时建立“学生—课程有效结果”服务或汇总，用于：

- 同一课程多次修读的有效结果；
- 当前未解决；
- 历史已解决；
- 重复未解决；
- 替代和认定。

### 10.2 接口拆分

不再用一个请求加载整页，建议拆分为：

- `GET /students/growth/overview`
- `GET /students/growth/organizations`
- `GET /students/growth/groups`
- `GET /students/growth/priority-list`
- `GET /students/growth/student/{student_id}`
- `GET /students/growth/my-scope`

其中：

- 概览、组织比较、名单独立加载和重试。
- 名单服务端分页、排序和过滤。
- 学生证据按打开抽屉时加载。
- 课程历史、培养方案和预警证据分区懒加载。
- 缓存键包含权限范围、当前身份、学期对和已应用筛选。

### 10.3 性能目标

- 概览缓存命中：300ms 内。
- 概览常规冷请求：2 秒内。
- 组织比较和首屏名单：2 秒内。
- 学生基础证据抽屉：500ms 内；超出时先显示已返回分区。
- 任一局部请求失败不影响其他区域继续使用。
- 避免对与当前权限无关的全校学生先做学分或历史成绩聚合。

## 15. 需要确认的产品决策

以下五点已于 2026-07-24 确认：

1. 是否同意将两个菜单收口为一个“学生成长与学业分析”，按当前工作身份展示不同工作区。
2. 是否同意首屏使用“可比较、明确改善、明确恶化、连续受挫、低年级首次受挫”五类管理指标，移除模拟毕业率和学位率。
3. 是否同意关注分组允许重叠，并在页面明确披露，不将其相加作为唯一学生总数。
4. 是否同意列表不使用不透明综合风险分，按公开的触发证据排序。
5. 相邻学期 GPA 明显变化阈值，是暂沿用原型阈值并标记“待学校确认”，还是在本轮实施前由你指定统一阈值。

## 16. 本轮结论

当前模块已经具备成绩、学生关系、迁移、挂科和预警等数据基础，可以支撑真实的学生成长分析，但尚不能直接按现状作为管理决策页面使用。主要原因不是功能数量不足，而是：

- 核心 GPA、挂科率和学分口径存在冲突；
- 学生为何进入关注名单缺少直接证据；
- 校级、学院、班级和导师使用两套入口与交互；
- 描述性图表多于管理优先级；
- 单一重接口和整页刷新放大了等待体感。

建议按“先统一口径，再收口角色入口，再重构首屏和证据抽屉，最后做性能与文档收口”的顺序实施。只有阶段 A 的 P0 口径通过后，后续页面和 AI 研判才有可信基础。
