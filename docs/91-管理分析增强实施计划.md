## 0. 已确认决策（2026-07-22 用户确认）

1. 课程类别"公共必修"用培养方案模块 + V1 `dim_course.category` 合并推导。

## 1. 现状要点（探查结论，不再复述过程）

- **通过率两套口径并存**：V1 `agg_course_term`（首次/最终通过率，按学生-课程首末次）与 V2 课程质量专题（成绩记录未通过率，不区分类型）。V2 `grade_attempt.attempt_type` 已完备区分 regular(35.4万)/retake(1.2万)/makeup(3851)。V2 无公共必修类别字段。
- **导师链路代码就绪、账号未接**：`mentor` 角色已定义，`staff_student_scope` 有 100 导师 ↔ 180 学生真实关系（另有 80 班主任 ↔ 2331 学生），`deps.py` 的 `staff_relation` 范围解析、`student.detail` 权限、菜单授权均已就绪；但 `sys_user_staff` 0 行、无导师账号，预警分派硬编码第一个 counselor（`alert_assignee` 5577 行全挂一人，settings.py:720-721 同样逻辑）。
- **学生个人页已存在**：`student/Detail.vue` + `GET /api/admin/student/{sid}`（GPA轨迹/挂科/学分完成率/成绩/预警史），学生级范围校验已支持 staff_relation。
- **ETL 手动跑批无监控**：`data_batch` 台账（17 行，含文件哈希/行数/质检）已存在但无 API；`metric_definition` 表已建 0 行；`sys_kpi_config` 只覆盖总览 8 指标；`data.refresh_mode` 参数为占位。
- **预测全规则**：无 sklearn 依赖；LLM 禁区含"不预测未来数据"（本计划修订为"不编造预测，仅解释统计/模型输出"）。
- **表格无标准控件**：38 个页面裸用 el-table，无公共组件、无列配置、无偏好存储。

## 2. 任务分解

### M1 课程通过率三分层 + 公共必修关注

**目标**：首次/补考/重修三个通过率统一走 V2 `grade_attempt`；公共必修课单独成组重点关注。

- [ ] 聚合层：`code/backend/etl/aggregate.py`（或 V2 聚合脚本）新增按 attempt_type 拆分的 first/makeup/retake pass rate，落 agg 表；公共必修类别推导（培养方案模块 + V1 `dim_course.category` 合并）落 `agg_course_offering`。
- [ ] 接口：`code/backend/api/routers/v2.py` 课程质量专题返回三分层通过率与课程类别分组；总览 KPI（`dashboard.py`）口径对齐。
- [ ] 前端：`reports/CourseQuality.vue` 增加三分层展示与"公共必修重点关注"区（低于阈值置顶）；总览/学生分析相关 KPI 卡片同步。
- [ ] 指标层登记：三个通过率 + 公共必修口径录入指标管理（见 M4 指标层合并，M1 先行写 `sys_kpi_config`）。
- [ ] AI 同步：`skills/course_quality.py` 信号口径与 `ai.py` 工作区基线同步为新口径。
- **验收**：同一课程三率加总逻辑自洽（首修未通过者进入补考/重修链路）；公共必修组可筛选可排序；189+ 测试与生产构建通过。

### M2 预警多角色参与（导师接通 + 分派改造）

**目标**：导师可登录、按所带学生看到预警；新事件按学生关系分派。

- [ ] 账号接通：迁移脚本从 `dim_staff`（staff_type=mentor/class_adviser）+ `staff_student_scope` 生成演示账号（`sys_user` + `sys_user_role` + `sys_user_staff` 工号映射），初始密码遵循现有演示约定。
- [ ] 分派改造：`code/scripts/migrate_alert_workflow.py` 与 `settings.py:720-806` 的"取第一个 counselor"改为：按事件学生反查有效 `staff_student_scope`，辅导员为主责任人、班主任/导师为协同责任人（`alert_assignee` 多行）；无关系命中时回退学院教学秘书。
- [ ] 存量事件：提供一次性回填脚本，把存量 5577 条按学生关系重挂（保留原责任人记录备查）。
- [ ] 权限：`permission_catalog.py` 核查 mentor/class_adviser 的事件跟进动作；`alert.event.manage_all` 仍仅 dean。
- **验收**：导师登录只见所带 180 名学生中命中的预警；新事件分派到该生三类关系人；两个不同导师的事件互不可见；越权访问 404/403。

### M3 三视角学生学业呈现

**目标**：辅导员/班主任/导师按身份获得对应首屏群体视图，个体下钻共用现有学生详情页。

- [ ] 后端：`students.py` 新增"我的班级/我的学生"群体画像接口（按当前身份范围聚合：GPA 分布、挂科率、通过率、学分进度分布、未处置预警数）；导师视角按所带学生组聚合。
- [ ] 前端：学生成长与学业分析（或预警工作区）增加身份感知的群体视图入口；导师"我的学生"列表 + 聚合卡；下钻复用 `student/Detail.vue`。
- [ ] 准入：菜单与路由守卫按角色放行；服务端仍按 scope 二次鉴权。
- **验收**：三类身份各自登录首屏呈现对应视图；导师跨班级学生聚合正确；学生详情页三类身份均可正常下钻且范围隔离。

### M4 ETL 采集监控 + 数据分层收口

**目标**：系统管理新增「数据采集监控」；逻辑四层（贴源/事实/聚合/指标）写进文档并以 `metric_definition` 登记新指标。

- [ ] `etl_run` 表（迁移脚本）：run_id/任务/起止/耗时/成败/行数对账/校验结果；现有跑批脚本改为结果落库（替代只打印控制台）。

- [ ] 前端：系统管理新增「数据采集监控」页（菜单迁移脚本，参照 `migrate_system_management.py` 模式）：上次采集时间、批次台账、运行历史、手动触发、采集频率配置展示（落 `sys_system_parameter`，原型期不做内建调度器，定时由学校数据交换平台触发）。

- **验收**：监控页展示真实批次与运行记录；手动触发一次成绩采集可在页面看到新 run 记录；M1 三个通过率口径可在指标管理查到。

### M5 预警后续轨迹（一期：同类轨迹分布）

## 3. 实施顺序与依赖

```
M1（指标层先行，供 M4/M5 引用口径）
M2（账号接通）→ M3（三视角依赖 M2 账号）
M4（独立，可与 M1/M2 并行）
M5（依赖 M2 的预警数据链路，不依赖 M3）
M6（独立，最后做，避免与 M1-M5 前端改动冲突）
```

## 4. 边界与纪律（沿用 AGENTS.md）

- 指标改动必须三处同步：后端计算、前端展示、指标口径登记/文档。
- 系统不做自动处置；分派是工作流动作，不构成"自动执行预警处置"。
- AI 不发明指标、不输出库外数字；预测一期仅历史统计分布并固定披露口径。
- 演示账号与真实关系保留 source 标识；权限范围缺失默认拒绝。
- 数据库结构变化一律迁移脚本，可重复执行。
