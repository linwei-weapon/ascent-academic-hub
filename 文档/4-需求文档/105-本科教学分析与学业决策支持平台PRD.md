## 2. 产品概述

### 2.1 定位

本科教学分析与学业决策支持平台是一个教学数据消费、分析和挖掘平台。系统从教务相关数据源读取学籍、成绩、培养方案、课程、教学任务、排课、教室占用和师资数据，经过清洗、归并和指标计算后，向管理者呈现分析结果。

系统不替代教务系统。成绩录入、排课发布、培养方案维护、教室管理、业务审批仍在教务系统完成，平台只做读取和分析，不回写教务源库。

### 2.2 两类业务能力

平台提供两类业务能力，服务不同的使用场景：

1. 教学管理分析：预设页面、管理视角、指标维度、图表表格和证据下钻。管理者按固定入口查看事实分析结果，从汇总数字逐级下钻到学院、专业、课程、学生名单和学生证据。
2. AI管理决策：管理专家 Skill、管理事件卡片、自然语言研判。系统把平台指标组织成决策简报和专家问策对话，承载学校个性化的管理方法。AI 负责理解和解释，不发明指标，不生成无数据依据的结论。

两类能力共用同一套指标和数据，不存在两套口径。AI 管理决策中的每个数字都可以回到教学管理分析的页面或明细核查。

一个典型配合使用方式：教务处老师在决策简报中看到"某学院首次通过率连续两学期下降"的要情，点"问专家"追问原因和涉及课程，再点要情中的数字直达该数字代表的学生和课程明细清单；后续核查和规则调整回到教学管理分析的预设页面完成。

### 2.3 目标用户与角色

| 角色 | 主要使用内容 | 数据范围 |
|---|---|---|
| 校领导 | 决策简报、教学数据总览、各专题全校视角 | 全校 |
| 教务处管理者 | 全部模块全校视角、跨学院比较、规则与口径核查 | 全校 |
| 二级学院教学管理者 | 本学院明细数据、跨学院聚合对比 | 本学院明细；他院仅聚合对比，不可下钻他院学生 |
| 辅导员 | 学业预警监控、所带班级学生成长分析 | 按有效"人员—行政班"关系所带班级学生 |
| 班主任 | 所带行政班的班级视图、学生详情 | 按有效"人员—行政班"关系所带班级学生 |
| 导师 | "我的学生"视图、学生详情、所带学生预警 | 按有效"导师—学生"关系所带学生 |
| 系统管理员 | 系统管理、全校业务数据 | 全校（明确授权角色，不属于权限缺失回退） |

一人多角色时使用"当前工作身份"切换，切换后所有页面按当前身份的数据范围呈现。所有后端接口按当前身份和实际授权做服务端校验。

### 2.4 菜单结构

一级菜单固定为三项：教学管理分析、AI管理决策、系统管理。

教学管理分析下含六个二级模块：

1. 教学数据总览
2. 学业预警监控
3. 教学运行分析
4. 培养质量分析
5. 师资保障分析
6. 学生成长与学业分析

AI管理决策下含两个二级模块：管理要情（决策简报）、决策研判（专家问策）。决策模拟并入决策研判，不单独作为菜单。

"我的班级/我的学生"页按当前工作身份呈现，归在学生成长与学业分析入口下。预警规则配置和规则自发现位于"学业预警监控"工作区内，不迁回系统管理。系统管理包含账号管理、角色与功能权限、菜单管理、数据权限、指标与口径管理、分析方案管理、审计日志、系统参数和数据采集监控九个入口。

## 3. 术语

以下术语在本文中使用，完整术语表见确认书附录B。

| 术语 | 含义 |
|---|---|
| 人数 | 按学生或教师稳定ID去重后的自然人数 |
| 人次 | 同一个人在不同课程、不同教学班或不同事件中可重复累计；人次不等于人数 |
| 首次/补考/重修 | 课程修读尝试的三种类型，对应成绩数据中的 attempt_type；首次通过率、补考通过率、重修通过率分别计算 |
| 当前未解决课程 | 学生曾未通过、且截至统计时点从未形成认可通过结果的课程；不等同于"历史挂过科" |
| 明确缺口 | 依据完整培养方案、成绩和替代证据能够确认的毕业准备缺口 |
| 候选缺口 | 因方案绑定、课程归属、替代或结果证据不足而需要人工核验的疑似缺口；不计入正式不达标结论 |
| 同类轨迹分布 | 对历史上处于相同预警状态的学生群体，统计其后续学期结果的历史分布；是统计事实，不构成对个体的预测 |

## 4. 功能需求

本章按学校已经确认的优先级组织：

- **P0生产基础与高价值主线**：成绩与挂科口径治理、学生成长轨迹、学生与培养方案执行、生产数据与权限底座、开发交接文档；
- **P1核心管理分析**：学业风险识别与证据核查、教学数据总览、教学运行分析、师资保障分析；
- **P2差异化能力**：AI管理要情、专家研判和学校分析方案，在P0、P1正式口径稳定后接入生产运行。

预警后续干预是否形成完整业务闭环尚未作出产品决定，不作为P0建设和验收范围；本PRD只要求预警识别、历史比较、证据核查和已有记录呈现。

### 4.0 P0-基础：成绩与挂科口径、系统治理及生产交接

#### 建设目标

先形成全平台唯一的成绩、挂科、学分、培养方案和权限真值，使学生成长、预警、课程质量、毕业准备及AI研判引用同一结果；同时向生产开发团队交付可直接实施的数据契约、接口、迁移、权限和验收资料。

#### 功能与交付要求

| 编号 | 功能或交付要求 | 状态 |
|---|---|---|
| FR-基础-01 | 建立有效成绩统一判定，区分首次修读、补考、重修、缓考、缺考、作废、更正和发布状态；特殊状态由学校确认后版本化 | 原型已具备，学校口径待确认 |
| FR-基础-02 | 分开计算成绩记录未通过率、当前学期挂科学生率、历史挂科经历和当前未解决课程，不得以同一“挂科率”名称混用 | 原型已具备 |
| FR-基础-03 | 学分加权平均分、学生GPA、首次/补考/重修通过率和课程有效结果必须共用正式计算服务和指标登记，不在页面重复计算 | 原型已具备 |
| FR-基础-04 | 系统管理提供指标与口径管理、数据采集监控和分析方案管理，并保留账号、功能权限、数据权限、菜单、审计和系统参数能力 | 原型已具备 |
| FR-基础-05 | 所有接口按当前工作身份在服务端重新鉴权；学校、学院、班级和导师范围使用统一权限上下文，AI不得扩大权限 | 原型已具备 |
| FR-基础-06 | 生产交接必须包含需求与指标真值、数据字典、数据库结构、API契约、权限矩阵、迁移脚本、部署手册、测试用例、已知边界和版本记录 | 原型交接基线已具备 |
| FR-基础-07 | 真实、推导和演示数据保留来源标识；数据缺失时披露边界，不用演示数据伪装学校正式结论 | 原型已具备 |

#### P0完成定义

1. 同一成绩或挂科指标在总览、课程、学生、预警、培养和AI页面使用同一指标编号、计算结果和数据截止时间；
2. 学校完成特殊成绩状态、GPA、重修覆盖和课程替代规则确认，未确认项有明确边界；
3. 生产开发人员无需研读原型全部代码，即可从正式交接入口获得数据、接口、权限、部署和验收材料；
4. 直接URL、API、导出、AI研判和证据下钻均通过服务端权限验证。

### 4.1 P0-主线：学生成长与学业分析

#### 模块目标

让管理者和带学生的老师回答三个问题：某个学生现在学业状态怎么样、为什么；某个群体（班级、年级、专业、学院）的学生分布怎么样；我直接负责的学生有哪些需要关注。

#### 目标用户

辅导员、班主任、导师（带学生的一线角色）；学院和教务处（管理与核查角色）。

典型使用场景：辅导员开学初查看"我的班级"群体画像，发现某班未解决课程集中在少数几名学生身上，逐一点进学生详情核查，确定本学期的重点关注名单。

#### 功能点

| 编号 | 功能描述 | 状态 |
|---|---|---|
| FR-学业-01 | 用户可以按学院、专业、年级、班级筛选学生列表，列表展示GPA、学分完成率、当前未解决课程数、当前预警状态等关键字段 | 原型已具备 |
| FR-学业-02 | 用户可以从任意学生名单点击进入学生详情页，查看学期GPA轨迹（D-01）、挂科与未解决课程、学分完成进度、成绩明细、历次预警记录（D-11） | 原型已具备 |
| FR-学业-03 | 系统提供群体画像视图，用户可以查看所选群体的GPA分布、当前挂科学生率、三类通过率、学分进度分布和当前有效预警学生数 | 原型已具备 |
| FR-学业-04 | 辅导员和班主任登录后，"我的班级"视图按当前身份的数据范围聚合呈现所带班级学生群体画像；一期两类角色共用同一视图结构，仅范围数据源不同 | 原型已具备（M3） |
| FR-学业-05 | 导师登录后，"我的学生"视图展示所带学生列表和聚合卡片，支持跨行政班聚合 | 原型已具备（M2/M3） |
| FR-学业-06 | 系统提供学业画像迁移标识：综合GPA变化、未通过课程数变化和未通过学分变化，把学生标为改善、稳定、下降等可解释状态（D-06），不用单一GPA判定 | 原型已具备 |
| FR-学业-07 | 用户可以在学生详情中查看重复困难课程清单（D-10），补考与重修记录分开展示 | 原型已具备 |
| FR-学业-08 | 主要表格支持列显示/隐藏、列顺序和每页行数的自定义，设置按用户和页面保存 | 原型已具备（M6） |

#### 核心指标

学期GPA（D-01）、GPA变化（D-02）、学期未通过课程数（D-03）、学业画像迁移（D-06）、首次挂科学期（D-09）、重复困难课程（D-10）、历史预警记录（D-11）、培养方案完成进度（D-12）、当前未解决课程数（G-09）、当前未解决学生数（G-10）。

#### 交互要点

1. 学生列表到学生详情是统一下钻路径，各模块（预警、培养、总览）点击学生均进入同一详情页。
2. 群体画像的每个分布图支持点击区间过滤出对应学生名单。
3. 学生详情页展示数据截止时间和口径说明入口。

#### 数据范围与权限

1. 辅导员、班主任、导师只能看到与本人存在有效关系的学生，关系来自"人员—行政班"和"导师—学生"映射数据。
2. 学院角色看到本学院学生；校领导和教务处看到全校。
3. 越权访问学生详情由服务端拒绝，返回无权限而非空数据。

#### 边界与约束

1. 学业画像迁移是基于历史事实的状态标识，不构成对学生未来的预测。
2. 学生建议类内容由确定性证据模板生成，每条建议必须能说明原因、数据来源和适用边界；无证据不生成强结论。
3. 系统不对学生贴标签，所有状态描述附口径说明。

### 4.2 P0-主线：培养质量分析（含毕业准备核查）

#### 模块目标

让教务处和学院回答：学生是否绑定了正确的培养方案，各课程模块是否按要求完成，哪些学生存在必修课、模块学分或门数缺口，未来课程供给能否支持学生按期完成学业。

#### 目标用户

教务处、二级学院教学管理者；辅导员和导师在学生详情中查看所带学生的培养进度部分。

典型使用场景：毕业年级学期初，学院教学管理者跑一遍毕业准备核查，把明确缺口学生按缺口课程汇总，发现某门必修课卡住 40 人且下一学期无开课计划，据此向教务处申请增开教学任务。

#### 功能点

| 编号 | 功能描述 | 状态 |
|---|---|---|
| FR-培养-01 | 系统提供培养方案绑定情况视图，用户可以查看方案绑定率（P-01）和未绑定学生名单；无方案学生不被默认为完成或有风险 | 原型已具备 |
| FR-培养-02 | 用户可以查看各培养方案模块的完成情况，模块判定按确认书4.2节顺序执行：有学分要求按认可学分（P-05），无学分要求有门数要求按门数（P-06），两者皆无按必修属性逐门核查（P-07） | 原型已具备 |
| FR-培养-03 | 系统提供毕业准备核查，用户可以查看每名学生的总学分完成率（P-04）、总学分缺口（P-10）、进度学分缺口（P-11）和各模块缺口（P-12） | 原型已具备 |
| FR-培养-04 | 系统将缺口分为明确缺口和候选缺口（P-13）两类分开展示：明确缺口进入优先核查名单（P-14），候选缺口进入待人工核验队列（P-15），不直接称为明确缺修 | 原型已具备 |
| FR-培养-05 | 用户可以查看应修未修课程（P-08）和未通过必修课程（P-09），系统区分"未选""未修"和"数据未到" | 原型已具备 |
| FR-培养-06 | 系统提供课程保障视角：按课程汇总缺口涉及学生数（P-18）、下一周期课程供给覆盖率（P-19）和重修资源覆盖率（P-20），帮助学院确定开课和重修资源优先级 | 原型已具备 |
| FR-培养-07 | 毕业准备结论按总学分、模块要求、必修课程、当前欠账、剩余学期分项呈现（P-16），不给出不可解释的单一分数 | 原型已具备 |

#### 核心指标

培养方案绑定率（P-01）、总学分完成率（P-04）、模块学分完成率（P-05）、必修课程完成率（P-07）、总学分缺口（P-10）、进度学分缺口（P-11）、候选缺口（P-13）、明确需处理学生数（P-14）、待核验学生数（P-15）、关键缺口课程涉及学生数（P-18）、课程供给覆盖率（P-19）、重修资源覆盖率（P-20）。

#### 交互要点

1. 毕业准备核查支持"学生视角"（某学生还差什么）和"课程视角"（某门课卡住多少人）双向查询。
2. 明确缺口和候选缺口在列表中用不同标识区分，候选缺口附"缺少什么证据"的说明。
3. 缺口清单支持导出，导出内容与服务端权限一致。

#### 数据范围与权限

按第 6 章权限矩阵执行。学院角色核查本学院学生；跨学院页面只呈现聚合对比。

#### 边界与约束

1. 课程替代、免修和校外课程认定只有在正式审批有效后才抵扣（确认书4.2节）。
2. 毕业要求和指标点可用于分析课程支撑与执行证据，其主观评价结果不直接作为学生毕业评审条件。
3. 数据不完整时系统标记"待核验"，不把未知解释为正常或异常。

### 4.3 P1-学业风险：学业预警监控

#### 模块目标

从学校真实数据中发现需要优先核查的学生，支持规则配置、规则自发现、当前风险与历史预警比较、命中证据和同类轨迹参考，特别关注低年级首次或连续受挫的学生。

#### 目标用户

辅导员、班主任和导师（按职责查看所带学生）、学院教学管理者（核查本院风险）、教务处（规则和全校风险治理）。

典型使用场景：成绩发布后系统跑出新一批预警，某低年级学生命中"必修课程未通过"严重级事件；有权限的辅导员、班主任、导师或学院管理者打开预警详情查看命中证据、历史预警和同类轨迹分布，再进入学生档案了解成长过程。是否在平台内继续承载分派和干预闭环，由学校另行确认。

#### 功能点

| 编号 | 功能描述 | 状态 |
|---|---|---|
| FR-预警-01 | 系统按预警规则定期扫描成绩、学分和培养进度数据，生成预警事件；规则含GPA持续下降（A-09）、近期未解决课程累计（A-10）、学分缺口（A-11）、必修课程未通过（A-12）、学籍风险组合（A-13）等，阈值分提醒、警告、严重三级 | 原型已具备 |
| FR-预警-02 | 用户可以在预警队列中按等级、学院、规则、学期筛选当前有效预警事件，查看当前预警学生数（A-01）和预警事件数（A-02）；同一学生命中多规则人数只计一次 | 原型已具备 |
| FR-预警-03 | 系统按有效人员关系控制预警可见范围，使辅导员、班主任和导师能查看职责范围内学生；无有效范围不得回退全校 | 原型已具备 |
| FR-预警-04 | 学生档案能够呈现已有预警和跟进历史；新的分派、状态流转和干预闭环不作为当前优先建设及验收要求 | 原型兼容已有记录，生产范围待确认 |
| FR-预警-05 | 用户可以在预警详情中查看命中证据：触发该预警的具体成绩、学分、课程记录，以及该生历次预警历史（规则版本保留） | 原型已具备 |
| FR-预警-06 | 预警详情内嵌"同类轨迹分布"卡：按预警规则、等级、发生时学期分桶，展示历史同类学生下一学期的解除率、升级率、GPA变化分布等统计；卡片固定标注"历史统计分布，不构成个体预测" | 原型已具备（M5） |
| FR-预警-07 | 用户可以查看新增预警学生数（A-04）、连续预警学生数（A-05）、多规则叠加人数（A-07），识别新发、持续和叠加风险 | 原型已具备 |
| FR-预警-08 | 教务处可以在预警工作区配置规则与阈值，查看规则命中率（A-16）和规则重叠率（A-17）；规则自发现提供候选组合（A-18），经人工审批后才成为正式规则，不自动发布 | 原型已具备 |
| FR-预警-09 | 预警规则配置和规则自发现位于"学业预警监控"工作区内，不迁入系统管理 | 已确认产品决策 |

#### 核心指标

当前预警学生数（A-01）、预警事件数（A-02）、严重/警告/提醒人数（A-03）、新增预警学生数（A-04）、连续预警学生数（A-05）、多规则叠加人数（A-07）、低年级首次受挫人数（A-14）、低年级受挫后持续困难率（A-15）、规则命中率（A-16）、规则自发现候选（A-18）。

#### 交互要点

1. 预警队列默认按"严重优先、新发优先"排序。
2. 从预警事件可一键进入学生详情页，上下文保留。
3. 预警生成时间、规则版本、命中证据在详情中固定展示，供事后复核。

#### 数据范围与权限

1. 辅导员、班主任、导师只看到所带学生的预警事件；两个不同导师的事件互不可见。
2. 预警详情、学生档案和证据下钻均按当前角色及人员关系控制；校级管理角色按正式授权查看全校。
3. 预警数据属于敏感数据，访问记录进入审计。

#### 边界与约束

1. 预警识别和证据核查不等于干预闭环。系统不自动联系学生、开班、认定课程或改变管理状态。
2. "本期未命中"不自动等于问题已解决（确认书 A-08 边界）。
3. 同类轨迹分布是历史统计，不作为个体预测依据；一期不建设个体风险预测模型。
4. 不使用模拟状态冒充真实"已处理""已解决"记录。

### 4.4 P1-教学数据总览

#### 模块目标

让校领导、教务处和学院快速判断学生总体学业表现，发现学院、专业、年级之间的显著差异，确定是否需要进入专题核查。

#### 目标用户

校领导、教务处（全校视角）；二级学院（本院视角加跨院对比）。

典型使用场景：新学期第一次处务会前，教务处老师打开全校概览，看到本期未通过学生率较上学期上升，从学院横向对比定位到差异最大的两个学院，再下钻到专业和课程确定核查专题。

#### 功能点

| 编号 | 功能描述 | 状态 |
|---|---|---|
| FR-总览-01 | 系统提供全校概览页，展示在籍学生数（O-01）、有效成绩学生数（O-02）、未通过学生数与未通过学生率（O-08、O-10）、当前预警学生数与预警率（O-13、O-14）等KPI | 原型已具备 |
| FR-总览-02 | 系统提供学院概览页，学院角色默认进入本院视图 | 原型已具备 |
| FR-总览-03 | 总览KPI采用课程通过率三分层口径：首次通过率（G-05）、补考通过率（G-13）、重修通过率（G-16）分别展示，不混为一个"通过率" | 原型已具备（M1） |
| FR-总览-04 | 系统提供学院横向对比，展示学院指标值与全校同口径指标的差异（O-17）和学期变化（O-18）；对比页面同时显示排名但不形成简单优劣结论 | 原型已具备 |
| FR-总览-05 | 用户可以从总览逐级下钻：学校—学院—专业—年级/课程—学生名单—学生证据 | 原型已具备 |

#### 核心指标

O-01 至 O-18 全套概览指标，G-05/G-13/G-16 三分层通过率。

#### 交互要点

1. 每个KPI卡片标注数据截止时间和口径说明入口。
2. 无数据、数据未接入和真实为0三种情况在页面上区分展示。

#### 数据范围与权限

学院角色在横向对比页可看到其他学院的聚合指标，但不能从对比页下钻到其他学院学生明细；点击他院明细由服务端拒绝。

#### 边界与约束

1. 横向比较用于确定核查优先级，不用于脱离学生基础、课程结构和培养方案差异对学院作简单评价。
2. 样本范围或规则版本变化时，学期变化指标不得直接比较（O-18 边界）。

### 4.5 P1-教学运行分析

教务处、二级学院教学管理者。

| FR-运行-01 | 系统提供课程质量分析：课程未通过率（C-04）按首次、补考、重修三层分别统计（对应G-05、G-13、G-16），用户可以发现未通过率持续偏高课程（C-07）和显著波动课程（C-08） | 原型已具备（M1） |

1. 课程质量指标用于发现问题线索，不能脱离课程类型、学生基础、考核方式直接评价教师个人。
2. 教师调课TOP10（S-05）只用于管理核查，不作绩效排名。
3. 平台不维护教室主数据和可用教室数量，正式利用率分母依赖权威资源系统数据。

3. "历史实际排课分布"反映真实排课结果，不等同于教师主动申报的偏好，不作为个人主观意愿结论。

### 4.7 P2-AI管理决策

#### 模块目标

把平台指标和分析结果组织成管理者可直接消费的形式：一份按管理价值排序的决策简报，和一组可以自然语言追问的领域专家。AI 负责理解问题、组织证据和解释口径，所有数字来自平台已计算指标。

#### 目标用户

校领导、教务处、二级学院教学管理者。

典型使用场景：校领导早晨打开决策简报，看到"毕业年级明确缺口集中在三门公共必修课"的要情，点"问专家"追问缺口构成和课程供给情况，再点要情中的学生数直达明细清单，把清单转给相关学院核查；对结论有疑问时打开查证页核对口径和数据时间。

#### 功能点

| 编号 | 功能描述 | 状态 |
|---|---|---|
| FR-AI-01 | 系统提供决策简报：首屏呈现按管理价值排序的Top3管理要情（第1条默认展开，其余折叠），每条要情含结论、关键数字、影响范围和来源；同一信号在单页只出现一次 | 原型已具备 |
| FR-AI-02 | 每条要情提供三个动作入口："问专家"（携带上下文进入专家对话）、"查证"（新窗口打开依据核验页）、"核查清单"（可复制的下钻清单） | 原型已具备 |
| FR-AI-03 | 系统提供四位专家问策：毕业缺口专家、课程质量专家、预警优先级专家、师资结构专家。用户以自然语言提问，专家基于对应专题的平台数据回答 | 原型已具备 |
| FR-AI-04 | 专家问策界面为纯对话主窗口，右侧固定展示本轮回答引用的数据要素与依据卡；回答中的依据以编号标注，可点击核验 | 原型已具备 |
| FR-AI-05 | 回答和依据卡中的人数类可下钻数字，点击后在新标签页直达该数字代表的业务明细清单（如具体学生名单）；明细与查证分工：查证回答"可信吗"，明细回答"都是谁" | 原型已具备 |
| FR-AI-06 | 系统提供查证页：展示结论的统计口径、数据来源、数据时间和规则版本；口径说明分两层，业务用户看到人话口径，管理员可看到技术口径 | 原型已具备 |
| FR-AI-07 | 超出专家领域或超出用户数据权限的问题，系统明确拒答并指引到正确的专家或功能入口，不编造回答 | 原型已具备 |
| FR-AI-08 | 专家会话按用户隔离保存，用户可以回看历史会话 | 原型已具备 |

#### 核心指标

AI 管理决策不新增指标，全部引用各专题既有指标编号。

#### 交互要点

1. 决策简报每次打开按当前数据重新生成，标注数据截止时间。
2. 明细清单页服务端按当前用户身份鉴权，越权访问返回无权限。
3. AI 重要结论必须包含分析范围、数据时间、事实来源、规则版本、证据入口和适用边界六要素。

#### 数据范围与权限

AI 不扩大数据权限。专家问策和明细下钻的可见数据与用户身份一致；自然语言提问不能绕过角色、组织、班级或导师关系限制。

#### 边界与约束（AI 使用边界六条）

1. AI 不做闭环交办：不生成"已交办""已处理"状态，不替代人工工作流。
2. AI 不预测个体学生结果；同类轨迹分布只作历史统计解读。
3. AI 不发明指标、不输出数据库中不存在的数字。
4. AI 不做成绩计算、毕业判定等正式认定，正式结论以预设计算为准。
5. AI 不执行任何写操作：不修改预警状态、不改规则、不回写任何业务数据。
6. AI 建议不替代学校制度和人工决策，重要结论附证据入口供核查。

其中对P0最关键的数据和治理基础：

1. 成绩尝试数据必须能区分首次、补考、重修和特殊状态（缓考、缺考等），是三分层通过率和当前未解决口径的基础。
2. 学生与培养方案必须有正式绑定关系，否则毕业准备核查只能出候选结论。
3. "人员—行政班"和"导师—学生"关系数据是一线角色数据权限的依据。
4. 每个数据源必须登记责任系统、稳定业务键、有效期、更新频率和批次证据，支撑开发交接和问题追溯。

### 5.2 数据架构

平台数据按四层组织：贴源层（原始接入数据，保留来源标识）→ 事实层（清洗归并后的业务事实）→ 聚合层（按维度预计算的统计结果）→ 指标层（登记口径的正式指标）。分层约定和指标登记要求见《数据架构分层与指标登记规范》（docs/92），表结构见《数据库表结构设计文档》（docs/06）。新指标必须先在指标层登记口径，再进入计算和展示。

### 5.3 采集频率与监控

1. 各数据域的更新频率由学校数据交换方案确定，本期系统提供手动触发采集的管理能力，内建定时调度待学校数据交换平台对接方案明确后建设。
2. 系统提供数据采集监控页：展示上次采集时间、批次台账（含文件哈希、行数、质检结果）和运行历史，支持手动触发指定采集任务（限系统管理员）。
3. 真实数据、推导数据和演示数据必须保留来源（source）标识；数据不足时页面披露边界，不用假数据伪装正式结论。

## 6. 权限需求

### 6.1 角色×范围矩阵

| 角色 | 数据范围 | 学生名单 | 预警与跟进 | 跨学院内容 |
|---|---|---|---|---|
| 校领导 | 全校 | 可见 | 可见 | 全校聚合与对比 |
| 教务处 | 全校 | 可见 | 可见并可管理全部事件 | 全校聚合与对比 |
| 二级学院 | 本学院明细 | 本学院学生 | 本学院学生事件 | 仅聚合对比，不可下钻他院学生 |
| 辅导员 | 有效"人员—行政班"关系所带班级学生 | 所带班级学生 | 主责跟进所带学生事件 | 无 |
| 班主任 | 有效"人员—行政班"关系所带班级学生 | 所带班级学生 | 协同跟进所带学生事件 | 无 |
| 导师 | 有效"导师—学生"关系所带学生 | 所带学生 | 协同跟进所带学生事件 | 无 |
| 系统管理员 | 全校业务数据 + 系统管理 | 可见 | 可见 | 全校 |

### 6.2 鉴权原则

1. 所有数据范围过滤在服务端执行。菜单隐藏不是安全边界，详情、导出、AI研判、证据链接和直接API请求都必须在服务端重新鉴权。
2. 权限范围缺失时默认拒绝或返回空范围，不回退为全校。系统管理员是明确授权的全校角色，不属于缺失映射回退。
3. 跨学院比较与学院明细使用不同权限语义："能比较"不等于"能下钻"。
4. 一人多角色通过"当前工作身份"切换，所有接口按当前身份校验。
5. AI 不扩大数据权限，自然语言不能绕过角色、组织、班级或导师关系限制。

### 6.3 审计

学生敏感信息、预警事件、年龄接续类数据的访问和导出行为记录审计日志，包含操作人、时间、对象和动作。审计功能本身的页面需求随系统管理部分后续补充。

## 7. 非功能需求

### 7.1 性能

1. 在万级学生规模、百万级成绩记录的数据量下，主要分析页面（总览、各专题首屏、学生列表）的常规查询应在秒级返回；学生详情、预警详情等单对象页面应更快。
2. 聚合类指标通过聚合层预计算保证响应，不靠页面端实时汇总大表。

### 7.2 可追溯

1. 每个重要指标页面披露：指标口径编号、数据截止时间、规则版本（涉及预警规则时）、样本范围。
2. 指标定义、数据批次、规则版本和权限范围可追溯；批次台账含文件哈希和行数对账。
3. 真实、推导、演示数据保留来源标识，页面可区分。

### 7.3 可解释

1. 重要结论附证据入口：汇总数字可下钻到名单，名单可下钻到个体证据。
2. AI 结论必须包含分析范围、数据时间、事实来源、规则版本、证据入口和适用边界。
3. 复合状态（如学业画像迁移）能解释构成原因，不展示不可解释的单一分数。

### 7.4 数据安全与合规

1. 学生敏感信息、预警记录、教师年龄和职称等人事字段按最小必要原则展示：页面只展示完成当前管理动作所需的字段。
2. 调课原因等非结构化文本在分类和展示前做敏感信息脱敏，原文保留在受限存储中（S-06 边界）。
3. 近退休依赖等涉及个人人事信息的分析严格授权，访问全程审计（FR-师资-03 权限要求）。
4. 演示数据与真实数据隔离标识，演示账号不进入正式统计。

## 8. 边界与不做的事

1. 平台只消费、分析和挖掘教务数据，不回写教务源库，不维护学校业务主数据。
2. 系统不做预警自动处置：不自动联系学生、不自动开班、不自动认定课程、不自动更新处置状态。
3. 本期不做学生端。学生本人视角的建议内容在分角色建议边界中保留设计（确认书10.3节），学生端页面另行立项。
4. 系统管理属于生产基础能力，按4.0节纳入P0；平台只维护访问、口径、采集证据和分析配置，不维护学校业务主数据。
5. 平台不扩展为学生工作管理系统，不承载请假、评奖、处分等学工业务。
6. AI 使用边界六条见4.7节，适用于所有AI功能。

## 9. 验收标准

### 9.1 P0成绩与挂科口径、生产交接

1. 抽取同一批学生与课程样本，对总览、学生、课程、预警和培养页面的成绩人数、未通过学生、首次/补考/重修结果进行对账，指标编号和结果一致。
2. 缓考、缺考、作弊/违纪、作废、更正、免修、补考和重修均按学校确认的状态矩阵进入分子、分母、GPA和预警；未确认状态不得静默归为通过或未通过。
3. 指标与口径管理能够查看公式、数据来源、粒度、版本和页面引用；修改学校分析阈值不得改变正式指标公式。
4. 开发团队可依据需求、数据字典、数据库结构、API、权限矩阵、迁移、部署、测试和已知边界文档完成生产实施拆分。

### 9.2 P0学生成长与学业分析

1. 辅导员登录后，"我的班级"视图只展示与本人存在有效人员—行政班关系的班级学生；筛选出任一学生进入详情页，可见GPA轨迹、未解决课程、学分进度和预警史。
2. 导师A和导师B分别登录，"我的学生"列表互不重叠（按各自导师—学生关系）；导师A直接访问导师B所带学生的详情地址，服务端返回无权限。
3. 学生在某学期GPA下降且未通过课程数增加时，学业画像迁移标识为下降类状态，并能展开查看构成该判断的三项指标变化。
4. 学生列表的列自定义（隐藏某列、调整顺序）刷新页面后保留，且不影响其他页面的表格设置。

### 9.3 P0培养质量分析

1. 给定一名已绑定有效培养方案的学生，毕业准备核查展示总学分完成率、各模块完成情况和分项缺口；模块有学分要求时按学分判定，无学分要求有门数要求时按门数判定。
2. 给定一名方案绑定证据不完整的学生，其疑似缺口出现在候选缺口队列而非明确缺口名单，并附缺少证据的说明。
3. 教务处用户可以切换到课程视角，查看某门必修课的缺口涉及学生数及名单；学院用户只能看到本学院学生。
4. 未绑定方案的学生不出现在正式毕业准备结论中，单独列入未绑定名单。

### 9.4 P1学业预警监控

1. 一名学生同时命中两条预警规则时，当前预警学生数只计1人，预警事件数计2条。
2. 辅导员、班主任和导师分别登录，只能看到有效关系范围内学生的预警；直接访问范围外学生或预警详情时服务端拒绝。
3. 任一严重级预警的详情页可见同类轨迹分布卡，卡片标注"历史统计分布，不构成个体预测"，分布数字与底层统计对账一致。
4. 预警详情固定展示生成时间、规则版本和命中证据；修改规则阈值后，新事件按新版本标记，历史事件规则版本不变。
5. 学生档案能够显示历史预警记录；未确认建设干预闭环时，验收不要求新的分派、处置或状态流转能力。

## 10. 优先级与里程碑建议

实施顺序按P0 → P1 → P2组织，原型是否已经具备不改变生产建设依赖：

1. **P0-口径与成长主线**：先完成成绩与挂科口径治理、学生成长轨迹、学生与培养方案执行、生产数据接口、统一权限底座、系统治理和开发交接文档。P0是其他分析和AI可以进入生产验收的前提。
2. **P1-核心管理分析**：建设学业风险识别与历史比较、教学数据总览、教学运行分析和师资保障分析。学业预警当前只验收识别、比较和证据核查；是否建设分派与干预闭环另行作产品决策。
3. **P2-AI管理决策**：在P0、P1正式指标和权限稳定后，接入管理要情、专家研判和学校分析方案。AI全部引用既有指标与证据，不另建冲突口径。

P0内部可以并行，但正式数据契约、指标真值和权限契约必须先于页面个性化开发冻结；任一模块上线前，其引用指标须在指标层登记并通过样本对账。

## 11. 待确认问题清单

以下问题需学校确认后方可作为生产正式口径，来源为确认书各专题的待确认事项：

1. 平台正式名称是否采用"本科教学分析与学业决策支持平台"（确认书第2节）。
2. 通用统计约定：休学、保留学籍、交流生、延期毕业生是否计入在籍学生数；当前学期、学年、历史观察期的具体时间口径（确认书第4节）。
3. 特殊成绩状态处理表：缓考、缺考、作弊/违纪、取消考试资格、成绩未录入、作废/更正前记录、免修/免考、补考、重修、课程替代，各自是否进入有效结果分母、是否视为未通过、是否影响GPA、是否影响预警（确认书专题二表格，全平台口径基础）。
4. GPA 转换表、课程纳入范围和重修覆盖规则（G-05、G-06 相关）。
5. 预警规则阈值表：GPA持续下降、近期未解决课程累计、学分缺口、必修课程未通过、学籍风险组合五条规则的适用范围和提醒/警告/严重三级阈值（确认书专题三表格）。
6. 连续预警的连续期数 N（A-05）；GPA 持续下降的期数分级（A-09）。
7. 学生与培养方案的正式绑定键，以及转专业、年级变化、留级学生的绑定规则（P-01 相关）。
8. 课程替代、免修、校外成绩和跨模块课程的抵扣顺序（确认书4.4节）。
9. "建议修读学期"是否具有管理约束意义（P-11 相关）。
10. 学位条件是否进入本平台；若进入，是否可提供结构化、可计算的正式规则（确认书4.4节）。
11. 课程质量分析的可比学期最低样本量（原型30）、持续偏高阈值（原型15%）、影响面阈值（原型50人次）、重修压力阈值（原型30人次）是否调整（C-01、C-07、C-10、C-12）。
12. 公共必修课的正式课程标签来源，及课程类别分类规则（C-15、T-10 相关）。
13. 教室可用主数据和有效期的权威来源部门；晚间时段是否默认纳入占用分析（R-02、R-09）。
14. 调课业务数据由哪个系统提供，调课原因分类是否允许使用 AI 辅助及脱敏要求（S-06）。
15. 教师职称、岗位、年龄段和退休政策的合规数据能否提供，责任部门和授权范围（F-07、F-11、F-13）。
16. 高影响单点课程的影响面阈值（原型100人次）；课程影响因素在学校确认前分别披露，不合成不可解释的课程影响指数。
17. 18个数据域各自的正式责任部门和更新频率（确认书第12节表格待填列）。
18. 各角色权限范围表的学校意见列（确认书第13节），特别是专业负责人/系部和任课教师两个角色本期是否纳入。
19. 数据交换方式：学校数据交换平台能否提供接口或定时推送，决定采集监控是否需要内建调度器。
20. 确认书第15、16、17节的管理场景补充、新增指标建议和总体确认，需学校填写后回填本文。
