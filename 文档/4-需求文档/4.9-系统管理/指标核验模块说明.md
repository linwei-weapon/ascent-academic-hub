## 1. 当前用途与操作路径

产品经理、交付经理和客户围绕教学数据总览的业务指标核对开发结果。需求原文随指标展开，页面层级、菜单、身份权限和一般交互条款不再作为主清单任务。

1. 进入系统管理→指标核验，默认展示总览首页18个指标场景；按业务页面、分类或名称查找。
2. 点击业务指标，查看中文公式、组成值、106出处及待明确问题。分子分母、规则输入和共用成绩证据放在指标内部。
3. 在同一详情查看贴源层→事实层→应用层。选择记录数、明细或可执行复算，填写本次范围；“读取可选值”提供真实数据库候选，保留手工输入。
4. 切换“真实结果对照与记录”。已保存的贴源/事实层单值复算可点“带入复算值”，同时带入指标值、已登记的分子分母或组成值、范围、学期、批次和来源；会替换未保存草稿并清空应用实值。补充真实统计截至时点和独立取得的应用实际值，再比较差异。榜单、分布及多行结果继续按对象手工填写。服务端计算差异，核验人选择符合、有差异或条件不足。
5. 保存后可刷新回看双方值、差异、条件及证据。返回清单保留分类和检索条件，列表显示当前身份最近记录的状态。

三层关系和SQL始终关联业务指标及106出处。更改查询范围或修改已有核对条件会清空本次结果/证据选择；首次补填原为空白的条件不会误清空带入值，防止误用旧结果。历史记录保留原范围，不自动适用于当前数据。当前支持SQL复算值带入与人工实际值核对，尚未自动读取并验证所有业务页面实际值。

## 3. 数据与结果如何理解

| 层级 | 当前连接及职责 |
| --- | --- |
| 贴源层 | 测试环境 `edu_source` 的MySQL贴源镜像；也支持显式配置Oracle原库连接。源表与字段以对应数据库真实结构核对，只读，禁止写入 |
| 事实层 | 测试环境 `edu_analytics_v3` 内ACT事实数据；核对实际字段、来源、过滤和粒度 |
| 应用层 | 同一分析库内聚合表、指标查询结果及SYS治理数据；B字典用于分类解释，SYS定义行数不能当作业务指标值 |

三层可能具有不同粒度，记录数不应强求相等。界面区分：

- **匹配记录数**：记录数SQL对完整条件范围返回的`matched_records`。
- **已返回明细行数**：页面默认最多展示50行，服务端上限100行，不代表完整记录数。
- **指标结果、分子与分母**：已具备执行依据的复算可以生成计算证据；143条受限复算模板仍显示SQL和原因，页面不能执行。应用物理对象能读到原值，也不等于已证明页面采用同一单位、刷新批次和范围。

记录数与明细分别执行，不保证两次查询共用同一数据快照。核对时应绑定相同组织、学期、数据批次及时间点；需要严格快照一致时，须先补充相应执行能力。源库快照与分析库批次无法对应、实际表字段缺失或历史规则版本不明时，应记录“条件不足”。

查询失败会显示原因，不产生成功记录数或自动通过结论。SQL文档和数据库实际结构不同，服务端拒绝查询并返回缺失项。`/health`正常只表示服务进程可用；配置字段完整、RDS白名单已放通或TCP端口连接成功，都不表示数据库认证、授权或SQL执行通过。

## 4. 权限与核验记录

本原型沿用114环境登录，通过既有`/api/auth/me`校验令牌和`X-Active-Identity`。具备定义查阅/管理或系统管理能力的身份可以查阅目录；数据库执行、结构核对和核验记录仅向同时具有**系统管理权限与全校明细范围**的当前身份开放。

核验意见不是跨用户共享工作流。记录仅按**当前用户＋当前工作身份＋当前需求**查询和引用，最多读取最近100条。切换工作身份后不能引用另一身份的执行证据；其他用户也不能引用或查看这些个人核验记录。

刷新页面后，核对记录仍可展开查看原证据的数据层、参数、时间、记录数、SQL版本和定义是否变化。历史列表包含最近100条执行摘要，以及当前可见核对记录引用的更早摘要。需求、指标或SQL发生变化时，原判断保留，但旧证据标记为过期，不能用于新的“符合”结论。

持久化仅写入分析库内两张专用表：

- `sys_metric_verification_execution`：需求、指标、查询ID、SQL版本及校验值、参数、执行时间、耗时、汇总结果和明细摘要哈希；不复制完整学生明细数据。
- `sys_metric_verification_record`：人工判断、意见、引用证据、创建人及工作身份。

新核对记录绑定“指标＋场景＋范围＋时点＋定义版本”。手工取得真实值可以不引用内部SQL，但“符合”必须具有双方值、单位、来源、时间、范围和比较规则；没有取得的值保留为空，不能补0。引用内部证据时，服务端检查身份、场景、指标关联、SQL版本和公共筛选参数；不能引用另一场景、旧版本或不同学期证据。

“带入复算值”调用 `POST /api/admin/metric-verification/comparisons/from-execution`，只传需求、场景和执行编号。后端从当前用户/身份的持久化证据读取结果，校验当前定义、SQL版本、执行成功、非截断且恰好一行，以及当前主指标关联；不接受前端提交的复算数值。记录数、明细、其他指标、应用参考和失效查询不能带入。空结果保持空，不补0。保存时按 `expectedExecutionId` 再次核对每个绑定组成项、单位、值、范围和来源，并自动关联原执行；修改带入值、删减分子分母或跨身份引用会被拒绝。手工附加比较项仍可填写。查询时间保留为取数时间，不能自动替代业务统计截至时点。

差异由服务端以十进制计算，文本结果按内容/顺序比较，不自动形成验收判断。选择“精确一致”时有差异不能存为符合；其他已说明的显示精度规则由核验人判断。待明确口径不能保存为计算链路符合，页面显示核对必须注明范围。完整三层结论还须从贴源输入开始并记录对应快照/批次依据。

新比较信息作为版本2的JSON保存于原专用表，不增加业务表或数据库迁移。旧列表格式记录仍可读取，因缺场景和结构化对照仅作历史意见。列表近期状态只覆盖当前用户/身份最近100条，不作为全项目验收进度或跨用户共享台账。

## 8. 已完成分析与发现的数据条件

已按106完成当前75项定义、113个页面场景、225个层级位置及744条SQL登记；登记完成不代表原文缺失口径已确认。学院TOP6和核查流程以106为准；优先核查TOP1采用用户确认的`max(学院挂科学生率－全校同口径率,0)×学院有效成绩学生数`，使用未四舍五入值排序。对106不同场景中的不同公式保留场景说明，不强行合并。

分析中发现以下真实问题，已写入对应指标与SQL的边界和阻止原因：

1. 源表`ZAI_JI=1`为9,990人，`HAS_XUE_JI=1 AND IN_SCHOOL=1`为9,991人，两者不能直接等同；ACT缺少同等在籍标记，历史学期还缺对应学籍快照。
2. 事实成绩3,434,801条，`attempt_type`全部为空、`is_retake`大量为空；首次/补考分类不能靠推测补齐。源作废状态、特殊成绩映射及最新结果覆盖规则仍需业务证据。
3. 46,007条预警的`rule_id`与规则表主键不匹配，`rule_code`能唯一关联；历史规则版本和批次仍不能由当前规则倒推。核查“已解决”不直接等于学业风险解除。
4. 25项指标找到应用物理对象，50项提供事实参考查询；全部应用结果与实际页面的单位、范围、刷新绑定仍需独立证明。11项无独立源结果，继续追溯其输入，不虚构贴源表。
5. 培养方案约束、替代认定和课程状态仍缺完整可验证规则。相关输入可查，不能把输入记录数当完成度。

以上是核验分析的结果，不以修改测试库业务数据来消除差异。产品经理可在页面按实际证据记录“有差异”或“条件不足”；只有完成同范围、同时间和同口径对照后才记录“符合”。本次真实登录回归使用系统管理员账号；其他身份隔离由后端测试覆盖，尚未用多组真实测试账号逐一浏览器复验。

### 11.10 最小操作与结果对照方案（已实现人工核对路径）

目标是让用户围绕一个业务指标完成理解和核对，技术证据随指标展开。

1. **找到指标。**默认展示“教学数据总览—首页”的指标，按规模、核心学业、修读通过、学院比较、GPA分布、重点对象分组；下钻指标放在对应页面分类。支持按名称/页面别名搜索。一个指标在多个场景使用时展示场景入口，不重复维护公式，也不返回十多条全文需求让用户再挑。
2. **看懂当前口径。**点击指标即看到业务含义、中文公式、组成值、106出处和待明确问题；编号及原文长段落作为辅助展开。三层关系入口与“查看SQL及记录数”在这一详情首屏可见，始终关联当前指标和需求出处。
3. **确定核对范围。**先选中文组织、学期、课程或学生，继承当前场景；只显示相关条件。批次/快照放在数据依据中，不能对应时明确提示。切换场景、范围或定义版本后，旧结果和旧判断不继续显示为本次有效。
4. **直接对照结果。**同一区域展示应用实际值、需求复算值、差异及组成值。应用值可读取已证实映射的应用对象，或由核验人录入真实页面观察值；手工值保留页面、时间和范围依据。事实复算始终标为需求参考值，不能复制到实际值一栏。
5. **按需查证并记录判断。**在同一指标详情展开贴源层→事实层→应用层的来源、关联键、加工条件、SQL及真实记录数。核验人选择符合、有差异或条件不足，并保存本次比较依据；返回时保留分类、筛选和位置。暂不增加审批、工单或代码执行过程分析。

#### 11.10.1 结果区的最少信息

| 区域 | 必须能看到的内容 |
| --- | --- |
| 本次条件 | 指标与场景、粒度/单位、组织/对象、学期/统计时点、可对应的数据批次；不适用的条件不展示 |
| 应用实际 | 真实观察值或成员/档位结果、来源页面或应用对象、获取时间；没有取得时直接显示“未取得应用实际值” |
| 需求复算 | 按106及已确认决定计算的值、分子分母/组成值、复算起算层及输入证据、SQL与参数；受限时显示具体原因 |
| 差异 | 实际−复算的差值，或不一致的成员/顺序/档位；比率差按百分点。显示精度与比较规则分别标明 |
| 查询证据 | 每层SQL、完整匹配记录数、已返回明细数、粒度与执行时间；未执行、失败、无独立来源分别说明，不能放演示成功数 |
| 判断 | 符合/有差异/条件不足、实际核对的环节、观察说明及所引用的本次证据；可回看版本和过期原因 |

核对记录以一次“指标＋场景＋范围＋时点＋版本”的比较为单位。用户不必额外创建验收任务。应用层没有独立存储结果时先说明实际值如何取得；引用SYS指标定义或事实参考查询不代表已经取得业务页面结果。

#### 11.10.2 最小比较规则

- 人数、人次、门数及成员集合按对应粒度比较；复合结果逐个比较必要组成值。分子分母均不一致而百分比恰好相等，不能判整项符合。
- 比率、均分、GPA保留计算精度和页面显示精度；只有页面观察值时按已明确的显示规则核对，不能声称验证了未显示小数。容差未定义时保留差异待判断，不擅定统一误差阈值。
- 榜单比较候选条件、成员和顺序；分布比较各档人数、占比与合计；趋势比较学期、点值与变化。仅总数相同不能判整体符合。
- 无数据、分母为0、未取得、查询失败分别呈现；不补0，不以SQL执行成功自动判符合。
- 源与事实批次不一致、关键口径未定、应用值缺失时，说明影响范围并记录条件不足；三层记录数因粒度不同无需相等。
- 结论注明覆盖的环节。只做事实复算与应用值对照，可以判断该事实输入下计算与展示是否一致；未核对贴源选取和事实加工时，不能据此宣称完整数据链路符合。完整链路结论需补相应层间依据，确无独立来源的层说明不适用原因，不强造结果。仅核对页面显示时也保留这一范围。
- 手工核验可先使用真实页面值和有参数/时间依据的查询结果；自动核对需在口径、映射和比较规则明确后启用。两种方式都保留证据，不能用演示状态代替结果。

交互实现时，首屏优先放业务名称、含义、当前缺口与结果，技术长文本按需展开；窄视口采用纵向排列，避免依赖横向滚动才能找到指标入口。实现后的最小走查样本为首页四项核心指标，逐一验证查找、范围切换、三层入口、真实值对照和回看记录；这只是交互验证样本，不代表其余指标或数据库验证已完成。

### 13.1 唯一目标与职责边界

**本Skill为应用层真正的业务指标建立可验证的闭环：需求口径→三层数据来源与加工→可执行SQL→独立核算→应用实际结果对照→证据与人工判断→需求变更后的再验证。**结构化成果保存到数据库，由现有“指标核验”模块消费。

应用层业务指标是业务需要交付或使用的结果，例如人数、比例、均值、排名、分布、趋势和具有管理含义的结果集合；不能因为字段存在、组件出现或某表前缀是SYS/AGG，就认定它是业务指标。首个范围仅为106教学数据总览：

| 对象 | 处理方式 |
| --- | --- |
| 106明确要求的业务结果 | 建立正式指标定义、来源映射、查询及核验办法 |
| 分子分母、筛选条件、字典、源字段、事实字段、计算中间量 | 作为指标的组成或依赖；只有需求把它作为独立业务结果时，才单独建指标 |
| 原型或系统中观察到的本指标 | 可辅助辨认业务含义、范围、单位和实际值；缺需求依据的结果先列候选，不自动扩张正式目录 |
| 其他页面、原型布局、导航、控件、跳转、交互流程、页面验收 | 不属于Skill输入分析范围和产出，不生成页面清单、线框或改版任务 |
| 指标核验模块自身的页面与权限 | 作为消费端既有能力及接入条件；Skill不重建设计、不自动授予权限 |

原型/系统界面是**可选证据**，不是必填输入或页面设计任务。只读取与目标业务指标有关的信息；演示值不能用于真实结果对照。即使不提供任何界面，需求和数据库材料也应足以开展指标定义与三层映射；实值可以来自已查明的应用结果表、视图或真实查询。

缺数据库材料可先提取业务指标，明确映射未完成。数据库不可访问时继续文档分析，实库检查标not_run。连接和认证由已有服务配置及当前授权身份提供，Skill不要求获取生产代码，不读取或展示密码/令牌。

核心包不含pages、scenes、布局和页面规则，也不要求AI生成旧系统requirements实体。需求依据通过metrics.definition.evidenceRefs关联原文；同口径结果跨界面复用同一个指标，只有公式、对象、时间语义等业务口径不同才建立独立变体。业务要求的单位、精度、排名并列规则属于definition，继续保留。

**指标最低内容：**业务用途、定义、公式、分子分母/组成、粒度、维度、对象范围、时间、筛选、去重/最终成绩选择、空值与零分母、精度及比较规则。内部依赖不能为凑指标数变成主指标；也不能删除106明确要求独立使用的组成指标。

**业务依赖与变更范围：**definition.ruleRefs为稳定ruleId数组，引用sharedRules中同名定义字段的规则内容；definition.metricRefs每项含metricId/appliesTo/parameterBindings，表示确实使用另一个已登记业务指标的结果。appliesTo定位本指标的组成或公式用途；parameterBindings每项为`{targetParameter,sourceParameter,literalValue}`，后两者只选一个，明确被引用参数与本指标参数/固定值的对应。范围、粒度或时间不能对齐时保留问题，不强行复用。两者没有依赖时为空数组；局部规则继续留在本指标中，共用规则正文只存一处，消费时展开，局部与共用内容冲突须处理，不能静默覆盖。内部组成量不必升格为指标；同名、同表或同一需求章节不自动建立业务依赖。首版引用仅限本模块，反向引用和传递影响由脚本计算，不另存一套关系表。

规则改变时先求引用闭包，再由Skill结合原文检查有无漏登记关系，形成changeSet.impactReview：changedRuleIds、reviewedMetricIds、affectedMetricIds、unaffectedMetricIds、unresolvedMetricIds及依据。已有引用只能证明已登记关系，不能证明清单绝无遗漏；无法界定影响时复核本模块清单，未决指标不得被宣布不受影响。受影响SQL、定义及证据一起处理；已有授权包含必要依赖时继续，否则保存草稿并列出范围冲突。服务拒绝带有未处理引用方的共用规则生效，避免只更新比例却留下旧分子分母。派生签名、影响清单和兼容关联由程序生成或校验，不让产品经理填写。

verificationPlan固定包含queriesByLayer（各层queryIds及缺口）、caseIds、comparison（结果形状、比较维度、可比条件、实值取得方式）及closureStatus。closureStatus仅为分析时摘要，服务结合真实执行和人工记录计算当前核验状态，不接受Skill自报闭环。

**三层结构：**lineage.nodes记录节点id、layer、role、对象类型、逻辑名称、字段和粒度。processing.steps记录id/kind/inputNodeIds/outputNodeId/dependsOn/definitionFields/fieldMappings/join/physicalPredicate及依据；步骤类型限filter/join/map/deduplicate/aggregate/calculate/rank/bucket/select_result。关系箭头由步骤派生，不独立维护一套公式与过滤条件，不建设通用SQL编译语言。

**物理绑定结构：**节点的physicalBindings为数组，每项固定含id/environmentId/connectionRef/dialect/schema/objectName/fieldMap/status/evidenceRefs。fieldMap为逻辑字段→物理列名；status为design_only/observed/drifted。示意绑定不证明物理存在。虚拟节点无物理表时为空数组并明确virtual_result，物理表未查明时为null并关联缺口。首版每条查询使用一个已配置连接，跨库连接或跨方言计算不得伪装成已受支持。

**查询物理依赖：**dependencies每项含bindingId和columns，columns为该SQL实际使用的物理列名；由节点绑定确定表及连接。SQL中用到的表字段必须登记，不能只检查登记的几列而忽略SQL还引用了其他对象。无法可靠解析或核对的复杂SQL保留人工技术确认，不宣称自动语义证明。

**未知和引用：**未知为null，已知没有为空数组，不适用有理由。影响计算的未知项关联具体问题，非关键文档元信息缺失不制造产品经理任务。ID稳定；指标、节点、绑定、步骤、查询、问题及证据引用均校验，循环和悬空引用拒绝导入。缺SQL为null且不可执行，不能用占位SQL获得“完整”状态。

正式入库采用完整模块快照，但**AI只修改本轮指标及其必要依赖，脚本负责从基线保留未受影响对象、组装和检查完整包**。没有显式退役指令的指标不得删除；未授权范围的业务变化拒绝发布并列出差异。续跑遇新基线先重整合受影响分支，不让AI重新生成整个模块。

### 13.5 分析过程与产品经理答复

正常调用由Skill完成准备、分析、检查和本次授权范围内的保存，产品经理不操作JSON和子命令。有问题时只暂停受影响分支；答复后可继续本次执行，跨会话则显式再次调用Skill读取检查点，不创建后台任务。

| 阶段 | 必要动作与输出 |
| --- | --- |
| 定边界 | 读取需求、设计、已确认决定和基线，冻结输入；列出本轮业务指标范围 |
| 拆指标 | 识别应用业务结果、组成和依赖；按业务口径合并/拆分，登记需求覆盖 |
| 追来源 | 从结果逆查应用承载、事实、源及字典；建立物理绑定、粒度和加工步骤 |
| 建查询 | 生成三层查询、记录数口径、参数、结果契约和验证办法；未知计算保持阻断 |
| 解疑问 | 查证后只对会改变结果的歧义提问，已有明确决定直接复用 |
| 验证与交付 | 组装并离线校验快照→保存草稿→当次取证并留存→独立核算与结果比较→回读并按授权生效；由核验模块完成实值对照 |

问题模板：[mapping-question.template.json](../../../code/metric-verification/contracts/mapping-question.template.json)。每个问题包含业务标题、出处、受影响指标、不同解释及后果、可选建议、阻断范围和责任角色。一次优先问1—3个高影响问题；字段枚举由数据负责人/开发核实，不让产品经理猜字段。已回答但不够明确时继续保留问题，超时不视为同意。

O-23中“先取最后有效成绩再排除空GP”和“先排除空GP再取最后一条”会改变学生集合；可用明确标注的假设数据说明差异。该示例不预先确定规则。产品经理可选项、自定义或defer；只答“按106”而原文未解决歧义时不能关闭问题。

#### 会话和离线答复的落库顺序

1. pendingAnswers保存submissionId、questionId/contextHash、rawAnswer、choiceId或customAnswer、scope、effectiveFrom、opinionSourceRef；不填伪造answerId。submissionId仅用于同一答复重试，不承担任务状态。
2. publish先提交**含问题的完整草稿包**。服务保存问题和待同步原答复，但pendingAnswers不被当成正式决定，也不放开相关SQL。
3. 脚本按该草稿中的答复调用回答接口；服务检查当前身份、原意见来源、上下文及范围，返回真实answerId。重复submissionId且内容相同返回原答复；内容不同拒绝。代录保留真实代录人和原意见来源，不冒充产品经理身份。
4. Skill/脚本将已认可答复转成decisions引用，移除已同步pendingAnswers，校验受影响规则和SQL，生成**新的packageId**并保存最终包。草稿与最终包不可混用同一幂等键。服务未能确认来源时保留待处理状态，不重新强迫用户作出已有决定。
5. 在线模块回答已经有answerId时直接从第4步衔接。执行中断从草稿revisionId和submissionId恢复，脚本查询已存答复，不重复提交确认；全过程由Skill编排。
6. 最终包生效时复查head、contextHash及最新有效answerId，成功后问题标resolved并记录appliedRevisionId。回答改变或基线变化则继续受影响分析；其余部分保持。

状态为open/answered/deferred/resolved/superseded。answered只表示答复已入库，resolved表示规则已落实到生效版本。问题表的新答复不能被旧包覆盖；版本保留当时决定。明确业务规则不等于数据库字段、SQL或应用结果已验证。

### 13.6 SQL与现有执行器的衔接

每条查询含id/metricId/layer/connectionRef/dialect/kind/purpose/version/sql/sqlChecksum/parameters/dependencies/stepIds/resultContract/prerequisiteQuestionIds。kind为count/detail/calculate；purpose为input_count/input_detail/expected_value/application_actual/reference。每个适用层有查询或具体不可查询原因；不机械生成“三层×三类”，但不能用一条事实查询掩盖源层和应用层缺口。

源→事实的历史加工依赖与当前SQL步骤分开。服务按stepIds、实际字段和相关问题开放查询；上游源枚举未确认不一律阻断已知事实记录的读取，但必须披露上游尚未验证。

| 新契约→现有执行器 | 确定的适配规则 |
| --- | --- |
| physicalBindings+dependencies→requiredColumns | 按bindingId解析物理表，将columns合并为`{表名:[物理列名]}`；绑定须匹配当前环境、连接及默认schema。依赖缺失或存在不支持的跨库查询则阻断，不能空清单执行 |
| 定义/问题/技术条件→executionApproval | 服务检查本条查询涉及的已确认口径、绑定、只读SQL和参数；满足时派生documented，否则blocked及原因。忽略AI上传的“已批准”；count/detail只看自身前置条件 |
| kind=count→recordCount | 首版count固定返回单行非负整数列matched_records，并在resultContract声明semanticRole=matched_records；沿用现有读取规则，不新增任意计数字段解释器 |
| resultContract→带入复算值 | scalar按semanticRole识别值及分子分母，expectedKey保留实际列名；兼容旧candidate_metric_value，无需全量重命名旧SQL |
| parameters.optionSource→参数选项 | 使用受检的bindingId/valueColumn及可选labelSource；直接由服务构造限定取值查询，复用options.py的只读、限量和名称映射。新查询不依赖正则猜别名；旧查询可在迁移时补结构 |
| SQL正文→load_sql | 从版本包读取；sqlFile只作迁移校验/导出，缺SQL仍可查阅缺口；实际执行不读取另一份可编辑SQL |

optionSource为null或`{bindingId,valueColumn,labelSource}`；labelSource为null或`{bindingId,keyColumn,labelColumn}`。这些列必须存在于已登记绑定，服务不接受任意选项SQL。学生标识不批量枚举；维度显示业务名称，无法取得名称时说明缺口。参数字段name/label/type/required/defaultPolicy/default与SQL占位符严格一致；默认值不能把未选范围放大成全校。

结果契约包含shape(scalar/ranking/distribution/series/collection)、rowKey、ordering、completeness和columns；每列key/label/dataType/unit/semanticRole/nullMeaning。比例区分0—1、0—100及百分点；单值保留组成数；零分母、没有记录、查询失败分别表示。聚合返回1行不等于输入1条。detail的总数引用同条件count查询，总数与明细分别带参数、批次和时点；不能证明一致时不合并为同一快照。不同层粒度的数量不要求相等。

首次限定执行不要求已有运行成功记录。定义及所需映射明确、离线检查通过、参数及授权具备时可取得首条证据，执行前显示尚未实库验证；技术成功不生成业务“符合”。只读校验、参数绑定、超时、限行、schema核对继续由现有服务实施。遇结构缺失、权限拒绝或持续超时，停止该项并继续独立工作。

**草稿验证顺序：**先做离线validate，再以save_draft登记新SQL；随后对该草稿版本做限定实库检查，取得证据后再决定生效。现有`POST /queries/{queryId}/execute`已支持mappingRevisionId和executionUse=definition_validation；服务只允许同时具备映射维护与现有SQL执行权限的身份验证草稿，仍校验该SQL口径、绑定和只读条件。仅因物理绑定尚未观察而阻断的查询，可以在该路径中经实时schema核对取得首条证据；业务问题未落实时继续阻断，不自动批准普通业务复算。草稿不要求已是head，但必须记录版本及用途；期间head改变，生效时仍检查基线冲突。普通业务核验使用executionUse=verification并遵守当前版本检查。

**定义核算样本与业务验收分开：**definition_validation证据只证明登记SQL在该限定样本上的核算情况。即使独立核算一致、该包已经生效、语义签名没有变化，也不能直接带入业务对照或引用为“符合”的依据。前端禁用这类证据并提示“定义核算样本，另行执行同范围业务复算”，服务端同时拒绝自动带入及用于符合判断。需要业务验收时，用当前生效版本按本次业务范围重新执行verification复算，再与独立应用实值比较。若核算结论写入新包，使用新的packageId并保留原执行ID，不覆盖原证据。

analyze_only不提交映射包或答复。该模式需要检查尚未登记的新SQL时，先完成离线分析并报告“实库检查未运行”，不能为了验证而隐式保存草稿；已有登记查询可在单独明确的执行授权范围内验证并沿用服务的执行记录机制。save_draft允许保存和验证草稿，不允许自动切换head。

### 13.7 独立核算和应用结果对照

核算模板：[mapping-validation-case.template.json](../../../code/metric-verification/contracts/mapping-validation-case.template.json)。首版使用限定真实样本进行独立核算，不建设通用合成数据测试引擎。

#### 当次留存与独立核算

历史批次不能稳定重取时，先取样本、等待人工核算、再查询实时库可能读到两份数据。因此调整为**当次一致性取证并保存→只提供输入进行独立核算→保存预期→读取已留存SQL结果并比较**。独立性的顺序要求是“先形成预期，再获知被测结果”，不要求人工核算必须早于SQL的物理执行时刻。

| 步骤 | 必要动作与证据 |
| --- | --- |
| 确定完整小范围 | 选择可由登记SQL明确限定的业务对象、组织和时间；登记samplePlan.inputDatasets中的原始明细queryId及对应countQueryId。这里的count统计筛选前输入，不复用有效成绩数冒充原始数；补齐参与关联、过滤、去重的必要维度和字典值 |
| 同次取数 | 服务在一个已核实支持一致性读取的只读连接/短事务中，读取原始输入、各输入记录数和被测SQL结果；使用同一范围、参数及已登记SQL。输入行数与同条件count相符，所有必要输入完整，才形成可用样本。业务规则对该样本不适用或不能用原SQL限定时先完善查询/样本方案 |
| 立即保存 | 结束只读事务后，将输入和被测输出一并保存到现有execution记录的专用证据字段，校验回读；写入失败不返回可用于核验的证据引用。按13.8控制范围和体积，不为等待人工操作保持数据库事务 |
| 独立核算 | 首先只返回留存输入、原口径、单位和样本边界；服务暂不返回被测输出。依据这些固定输入逐项核算有效性、去重、组成和结果，保存方法、推导、依据及核算人/时间，然后取得被测输出。不能从输出回填预期；若已看过结果，披露这一事实，不能标为本轮独立核算通过 |
| 比较与复核 | 对照留存的预期和SQL结果，保存差异与判断；以后从该证据重新核算，不重新查询实时库覆盖原值。修改预期保留原记录及原因；需要新的独立验证时重新取证 |

这只验证**指定环节、限定样本**。当前留存核算限同指标、同一MySQL连接和方言，服务检查依赖对象为InnoDB基础表、核对schema，并使用只读一致性事务；Oracle可做已具备条件的普通技术查询，不进入首版留存核算路径。每个输入集及被测结果最多50行，整份证据最多1 MiB，输入配置可以进一步收紧体积。原始输入范围不得预先套用正在验证的有效性筛选；缺必要输入、超限、截断或一致性无法确认时返回具体原因，不生成计算通过结论。缩小范围必须维持业务含义，例如排名仍需覆盖所声明候选集合；不能将全校排名任意缩成几个学生后声称验证了全校TOP。

数据留存分两级：SQL口径核算保存完整小样本的输入与输出；应用对照保存实际核对的结果及上下文。日常浏览SQL不自动留存全量明细，核验也不复制全库。学生原始明细不进入共享映射包、聊天报告或Git；包内只保存授权校验后的evidenceRef及摘要。模板中的retainedEvidenceTemplate仅说明服务存储格式，不属于MappingPackage。

validationCases/validations在共享包中只保留方法、状态、摘要与引用；真实expected.rows、execution.actualRows及原始数据行保存于服务证据/核验记录，发布包中保持null，通过授权接口取得。模板可展示字段形状与合成算例，不能将真实学生行嵌入说明样例绕过此约定。

源、事实、应用跨连接读取时，分别保存各自证据和取数区间；不承诺跨库原子快照。同一数据库事务也只能证明同时读取，不能证明源→事实ETL已对齐。没有可核实的加工对应关系或业务时点时，仅核验已具备条件的环节，对其他环节记录条件不足；不把三层取数时间接近视为口径或批次一致。批次号如实际存在可作为业务上下文，但不承担以后重取历史的职责。

同类规则可共用核算方法，但每项需登记覆盖关系，特殊口径需专门用例。样例中的合成学生集合仅用于解释规则，标记explanation_only和countsForSqlValidation=false；它不证明SQL、114数据或应用正确。未来需要直接对合成样例执行SQL时，再补隔离表和方言适配。此项后置不取消真实小样本核算。

**应用实值：**actualBinding声明table/view/result_query/manual_observation、已知物理对象或证据、取值方式和可比条件。Skill根据需求生成的SQL属于expected/reference；不能复制到两侧冒充应用实现。没有独立结果表时可用同条件真实系统观察；原型演示值不可用，未找到实值来源则业务核验未闭环。

比较条件包括对象/组织、时段、口径版本、可核实的业务数据时点、单位及精度；采集时间单独保存，不能代替业务截至时点。SQL取得的实值保存当次结果；人工观察保存实际值/核对行、单位、筛选和身份范围、来源定位及观察时间，必要图片仅通过受控证据入口引用。既有record.evidence_json保存该次观察；只留URL或一句“已看过”不足以复核。不同时间读取且无法证明可比时允许记录差异，判断为条件不足。容差必须有需求依据，不能为消除差异临时设置。

单值首版自动带入；排名人工核对成员、顺序、值及并列规则；分布核对分组边界、数量和总体；趋势/集合核对时间或对象键。多行自动带入后置。超过既有对照行上限或结果截断时明确抽样范围，不能标全量通过；不要求把大量明细重新抄成一张表。现有核验记录保存实际核对项、来源和必要证据，不能仅凭一句“已看过”生成符合判断。

### 13.8 数据库、版本和消费模块职责

服务将映射保存到配置分析库的SYS专用表，本项目配置目标为114的edu_analytics_v3；不写edu_source、ACT或AGG业务表。映射生效后以数据库版本为业务定义来源，本地JSON用于交换、导出和首次迁移。表结构由现有`code/backend/metric_verification/migrate.py`幂等创建；普通publish不自动建表。

| 已实现的表结构 | 职责与关键字段 |
| --- | --- |
| sys_metric_mapping_revision | revision_id、作用域project/module/environment、package_id（作用域内唯一）、analysis_id、base_revision_id、schema_version、package_hash、package_json、validation_json、bindings_json、created_by/at；不可变映射包及服务派生的兼容关联 |
| sys_metric_mapping_head | 作用域联合主键、revision_id、lock_version、updated_by/at；当前版本指针 |

不增加run/event表。包保存输入、检查点和简要过程；过程不建立独立进度看板。已生效快照不随新答复修改；后续真实查询与核验分别追加到既有execution/record，增补mapping_revision_id和相关签名。旧记录不倒填为已验证的新版本证据。

#### 最小核算证据的存储与读取

现有`sys_metric_verification_execution`已增加可空`evidence_json`字段保存一次取证的固定输入与SQL输出，增加可空`independent_expectation_json`保存揭示输出前提交的独立核算；execution和record均增加mapping_revision_id。普通查询证据字段可为空，原有result_json摘要继续兼容。`evidence.py`负责取证、完整性、独立预期及揭示；`store.py`负责执行和核验记录存取。旧记录只有摘要时明确提示没有可重算输入，不从实时业务表补填为历史证据。

| 证据字段 | 固定内容及用途 |
| --- | --- |
| id/executionId/mappingRevisionId/metricId/caseId/environmentId | evidenceRef使用服务返回的执行ID；定位原定义、样本方案和执行，不能由AI伪造已存引用 |
| capture | 连接引用、采集起止时间、一致性方式及其核实依据；业务时间和实际存在的批次保留在参数中 |
| scope | 组织/对象、业务时间和样本边界；覆盖为bounded_sample或complete_result，不根据返回行数推定全量 |
| datasets | 每个原始或必要关联数据集的角色、提取/计数查询ID与SQL正文/哈希、参数、字段类型、完整记录数及实际行；保留判断所需原值和稳定关联键 |
| testedResult | 被测查询的SQL正文/哈希、参数、字段、实际行及完整性，不能仅保存最终比例而丢弃分子分母 |
| integrity | 服务生成的内容哈希、字节数、持久化时间和回读结果；按规范JSON计算固定证据正文，排除integrity本身、独立预期及响应展示状态，避免自引用；原始内容本身用于重新核算 |

小数用精确字符串并带字段类型，日期保留时区或已知本地时间语义，NULL与空字符串分开；只保存本次核算所需字段，不默认复制姓名、联系方式等无关列。执行每数据集行数上限和整份证据字节上限，超限不得用截断数据生成通过结论。证据正文与哈希以不可变内容为准；独立预期单独写入一次，相同提交重试返回原内容，不同内容拒绝覆盖，后续更正通过新的核验记录保留原因。

证据由后端返回不透明引用，不接受客户端文件路径；读取时沿用执行记录的本人、当前工作身份、当前数据范围校验，访问映射定义不等于可访问其学生明细。映射包只能引用证据，不能携带真实样本行。留存至少覆盖关联核验记录的有效期，首版不自动清理已引用证据；未来若依法或按项目要求删除，关联记录须显示“原始证据不可复核”，不能继续用于新的符合判断。此处不另设团队共享验收或留存管理页面。

独立核算流程扩展既有执行入口：`POST /queries/{queryId}/execute`带mappingRevisionId、executionUse=definition_validation及validationCaseId时，由服务从版本包解析原始输入/计数查询并完成取证，不接收临时SQL。初次响应只含evidenceRef、输入与完整性信息，result_json、列表、自动带入及其他读取入口均不提前泄露该次被测值。新增`GET /executions/{executionId}/evidence`读取授权证据，以及`POST /executions/{executionId}/independent-expectation`保存模板expected中的方法、推导、输入证据哈希、结果和原依据；作者与时间由服务确认，保存成功后才返回被测输出。expected保存与输出揭示状态由服务判断，不能接受AI自报独立性。若核算人员已通过其他渠道看过结果，应声明并标为普通复核，不能宣称技术流程证明了人的独立性。

应用实值查询使用executionUse=verification；服务对登记purpose=application_actual的结果执行当次留存，datasets可为空、caseId可为null，完整性不足时只能按实际覆盖范围记录。该路径直接返回实值，不要求独立预期提交；结果类型和来源由查询登记确定，不能把expected/reference伪装为application_actual。人工实值通过既有记录保存接口留存，继续支持无SQL执行权限的人工核对。

SQL事务完成后才写核验专用表；保存或回读失败时报告evidence_unavailable，不返回已留存状态。没有可用留存条件仍可整理映射或保存技术执行摘要，不能报告独立计算验证通过。消费端从上述接口回看原始依据，正常用户只需执行核算、确认口径与记录判断，不操作存储结构。

**两个有明确用途的校验：**packageHash用规范JSON（键排序、UTF-8、数组顺序保留、有限数字）对完整提交包计算，服务回执不在包内；用于幂等内容核对和回读。指标语义签名及SQL哈希用于判断证据是否仍适用，不能由整个包哈希代替。取消额外包级contentHash；来源证据的contentHash仍保留。

语义签名按固定字段取定义公式、范围、过滤、去重、时间、单位、比较精度、物理关联，并递归纳入ruleRefs所指规则正文及metricRefs所指指标语义与参数对应；循环或悬空引用拒绝。名称润色、原文行号及过程时间不单独使计算证据失效。SQL文本或参数变化使相关查询证据失效，首版不做SQL语义等价证明。依照13.4完成影响复核后，仅相关证据失去对新口径的适用性，历史证据内容保持不变；未处理的影响不能通过激活检查。原文变化仍需重审依据，不能凭签名未变跳过。历史样本证据可说明当时规则，不能因为语义签名未变就将旧业务值当作当前数据验证结果。

#### 现有指标核验模块消费边界

- registry读取版本包，派生既有catalog/queries格式；后端适配器负责requirements、indicatorSystem及三层查询，不把这些旧结构转回Skill的核心输出。
- 迁移现有目录时生成bindings_json，保存metricId→原requirementId/scenarioId/evidenceMetricIds及核对范围关系。例如O-10继续关联R106-03-05和home-o-10。包以指标ID为主，旧场景的历史证据仍可定位。
- 既有模块的分类、页面名称和展示配置由消费模块维护或迁移保留，不由Skill推导或重新设计；这些展示配置不能保存第二套指标公式或SQL。新指标没有旧关联时，由适配器生成明确标为内部兼容锚点的稳定ID，不能编造106原文编号。
- 查询按metricId/layer/dialect派生，执行器按13.6适配；结果契约驱动单值带入，替代硬编码指标列说明。结果为空、SQL缺失和未决问题均能展示，不能导致整份目录加载失败。
- 消费端负责展示指标、三层关系、SQL/记录数和核对结果，保存comparison的结果形状、完整/抽样范围、双方来源及人工判断；本章不规定页面布局、导航或线框。
- 读取、维护、回答、SQL执行和记录能力按既有鉴权明确区分；手工记录不必绑定数据库执行权限，执行仍遵守现有系统管理/全校范围限制。身份、组织范围和本人证据隔离由服务校验，Skill不改权限、不代签。消费端能力未接通时应列为实施缺口，不能声称业务闭环可用。

读取定义、参数、执行、带入和保存均携带mappingRevisionId，在一次请求内使用同一快照。head变化时首版返回409并要求刷新确认，保留人工输入供查看；在途执行只绑定原版本。历史证据能否续用按同环境的相关签名、SQL和范围判断，不仅比较模块版本号。

#### 导入、恢复和切换接口

以下接口已实现在`/api/admin/metric-verification`下，沿用既有包络、认证和当前身份；映射分析和复算不调用生产业务计算接口：

| 方法与路径 | 输入及用途 |
| --- | --- |
| GET /mapping/head | 返回配置作用域的当前版本；无版本时明确为空 |
| GET /mapping/revisions?analysisId=… | 返回获授权分析的草稿/版本摘要，用于找回最近保存的工作，不建设任务列表 |
| GET /mapping/revisions/{revisionId} | 返回持久化包、服务校验和兼容关联 |
| POST /mapping/packages | 完整包，packageId为幂等键；保存草稿，返回revisionId/packageHash及校验结果，不执行包内SQL |
| GET /mapping/questions | 按指标/状态过滤问题及已存答复，支持submissionId查找重试结果 |
| POST /mapping/questions/{questionId}/answers | submissionId/contextHash/rawAnswer、choiceId或customAnswer、范围、生效时点、原意见引用；返回真实answerId |
| POST /mapping/activate | revisionId/expectedHeadRevisionId；事务检查基线与所用答复，切换head并更新采用状态 |
| POST /queries/{queryId}/execute | requirementId/scenarioId、parameters、sqlVersion、mappingRevisionId、executionUse；定义核算另传validationCaseId，服务只执行登记SQL |
| GET /executions/{executionId}/evidence | 读取本人当前身份的留存输入、完整性及已允许展示的结果；独立预期提交前testedResult为空 |
| POST /executions/{executionId}/independent-expectation | method、basisRef、derivation、rows、inputContentHash、resultKnownBeforeCalculation；预期只写一次，成功后揭示结果；不会产生业务符合判断 |
| POST /comparisons/from-execution | 按当前版本、指标和场景带入普通verification的有效单值复算；拒绝definition_validation样本 |
| POST /records | 保存同范围、时点的实际值/需求复算值、来源、人工判断与证据；不能用定义核算样本支撑符合结论 |

服务重算结构、引用、范围和差异，不信任AI上传的passed/批准状态。格式错误、越权、无基线更新和无依据删除拒绝导入；语义未决可存草稿。相同packageId相同包重试返回原版本，不同内容拒绝；不按“看起来相同”自动合并不同验证过程。发布前回读校对，失败不切head。已有授权允许生效时无需逐项重复审批，analyze_only/save_draft不得自行升级。

`registry.py`已通过`mapping_adapter.py`消费固定数据库版本；版本、SQL、问题答复和证据能力均已接入原指标核验页面。`MV_MAPPING_MODE=required`要求存在配置、表和生效版本；`legacy`显式保留旧模式。默认auto允许无数据库配置或无生效版本时明确返回legacyMode；数据库连接失败或已配置库缺映射表不静默回退旧口径。环境首次切换先执行幂等迁移，再校验、保存并生效初始包；不直接覆盖唯一数据库。

业务定义更新入口已改为metric-mapping-build。原metric-verification-maintain仅维护消费、证据和边界；两个旧生成脚本不得继续独立覆盖生效定义，只保留迁移/导出参考。报告/共享包不落学生明细，授权核算输入保存在核验专用记录。服务不可达时保留待导入包及pendingAnswers，明确未入库。
