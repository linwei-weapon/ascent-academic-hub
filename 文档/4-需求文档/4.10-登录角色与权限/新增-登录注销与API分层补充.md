# 登录注销与 API 分层补充

> 日期：2026-09-14；任务：AUTH-01；状态：本次范围内已完成。
> 来源：本轮用户确认、现有认证代码、[统一权限上下文实施记录](85-P2统一权限上下文实施记录.md)与[工程约定](../../项目架构与文档管理约定.md)。本文件补充当前实现，不改写既有文档。

## 1. 功能边界与目的

补齐前端登出与已有 `POST /api/auth/logout` 的连接，使用户确认登出后，当前登录令牌通过后端既有机制撤销。认证请求集中到前端 API 模块，登录状态继续由原 Store 管理。

用户已确认保留账号密码登录、localStorage 的 `bi_token` / `bi_active_identity`、12 小时令牌有效期、当前角色和身份数据。请求路径、JSON 字段、响应包络及身份请求头沿用现有契约；本次不改后端业务规则，不迁移或重置数据库。

## 2. 页面描述

登录页、菜单、身份和范围展示沿用现状。顶部“登出”继续使用原确认框；确认后按钮显示等待状态，避免重复提交。请求完成后清除当前浏览器的令牌、身份、用户和菜单状态，返回登录页。

## 3. 核心流程

账号密码登录、刷新后的 `/api/auth/me` 会话恢复、工作身份切换均通过 `src/api/auth.ts` 调用既有 HTTP 封装。Store 继续应用后端返回的用户、菜单和范围，不增加角色推断或权限计算。

登出时先携带当前令牌和身份请求后端注销，随后清除本地登录状态。后端继续使用现有 `sys_revoked_token` 和审计机制，只撤销本次登录令牌，不注销同账号的其他独立会话。

认证 DTO 移至 `src/types/auth.ts`，原 `src/store/auth.ts` 保留类型转导出，原调用方无需改变导入路径。API 模块依赖类型和 HTTP 底座，不反向依赖 Store。

## 4. 异常容错

服务器不可用、返回失败或注销等待超过 5 秒时，仍清除本地登录状态并返回登录页，提示服务端注销尚未确认。超时只用于注销请求，不改变登录时长或其他业务请求。缺少令牌时直接清除本地状态，不发送空令牌注销请求。

本地状态清除不代表服务器撤销成功；只有后端成功处理后，旧令牌才会因本次注销被拒绝。

## 5. 后续与非目标说明

Cookie 会话、令牌续期及学校统一认证本轮不实施。后续涉及旧会话处理、账号绑定、组织映射或数据兼容时，先向用户确认。

本轮发现并经用户确认保留的既有接口差异：`/api/auth/login` 的 `permissionContext.userId` 为用户名；`/api/auth/me` 和身份切换响应中的同字段为数据库用户 ID 的字符串。原因是原登录查询未选取 `user_id`，权限上下文使用用户名回退。本次不统一返回值、不修改数据库；后续需单独确认字段含义及旧消费者兼容方式。回归分别核对该差异，其他用户信息、菜单和权限上下文应保持一致。
