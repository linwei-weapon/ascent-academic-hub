## 一、项目定位与业务边界

本项目面向高校管理人员，把成绩、学籍、培养方案、教学任务、师资及人员关系加工为可查询、比较和下钻的管理信息。主要使用者为校领导、教务处、二级学院、辅导员、班主任、导师和系统管理员。

系统提供四组业务能力：

| 能力 | 用户需要完成的工作 |
| --- | --- |
| 教学管理分析 | 查看教学总览、预警、教学运行、培养质量、师资保障和学生成长，定位到课程或学生证据 |
| AI 管理决策 | 阅读决策简报、进入分析专题、向专家问策并查证依据 |
| 基础报表 | 按固定口径查询九张统计报表，核对结果并导出 |
| 系统管理 | 管理账号、身份、功能与数据权限、指标、学校方案、审计、参数和采集任务 |

这是代码和需求层面的能力分组，不代表每个账号都获得全部菜单。系统只消费学校业务数据，不维护或回写教务源库；平台自身的账号、配置、分析方案、审计及会话允许受控持久化。

业务分析展示事实及边界，AI 辅助解释和核查，不自动执行开班、排课、毕业认定、教师评价或学生干预。事实指标和规则结果由代码计算，大模型不能临时发明正式指标。

## 二、整体运行架构

```text
浏览器：Vue 3 管理端
  ├─ Router：页面、准入、旧地址兼容
  ├─ 状态：用户、当前工作身份、筛选与分页
  ├─ Element Plus / ECharts：交互、图表与证据抽屉
  └─ HTTP：JWT + X-Active-Identity
          │ /api
          ▼
开发：Vite 代理到 127.0.0.1:8000
构建后：FastAPI 可托管 frontend/dist
          │
          ▼
FastAPI 单体应用
  ├─ Router / 依赖：参数、身份、范围与动作权限
  ├─ 教学分析 / 报表 / 系统管理
  ├─ Skill：事实信号、简报、问策、模型解释
  ├─ 数据访问：sqlite3 与参数化 SQL
  └─ 审计与平台配置写入
          │
          ├─ analytics.sqlite
          ├─ analytics_v2.sqlite
          └─ 个别查询依赖学期源库
                       ▲
          Python ETL：接入、清洗、关联、预聚合
```

当前后端是单体工程，尚未统一拆成 Router、Service、Query 三层。基础报表已有独立 service 和 exporter；多个大 Router 仍同时包含 SQL 和业务计算。后续分层按业务逐步进行，不能将本文件的开发规则理解为所有历史代码已经符合。

## 三、技术栈与运行单元

| 层次 | 当前实现 | 约束 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Element Plus、ECharts、Tailwind CSS | 保留现有技术栈和 Style A 主题 |
| 状态 | Pinia 与 Vue reactive 并用 | 身份和跨页状态集中，页面临时表单留在页面 |
| 接口 | 原生 fetch、公共 http、业务 helper | JSON、下载和 SSE 分别处理 |
| 后端 | Python、FastAPI、Uvicorn、Pydantic | 统一身份和服务端数据范围 |
| 数据库 | SQLite 双分析库 | 核心访问使用 sqlite3，不套用 QuizTestDemo 的 Prisma/MySQL 规则 |
| 数据加工 | pandas、openpyxl、xlrd、python-docx、loader/builder | 保留来源、批次、规则版本及运行记录 |
| 模型 | 兼容 Chat Completions 的 HTTP 接口 | 可配置服务，规则输出可在模型不可用时提供基础结果 |

前端和 Python 后端分别安装依赖、运行；仓库没有统一 npm workspace 启动整个真实系统。前端构建命令目前是 `vite build`，不包含完整类型检查。

## 四、工程职责

前端的 views 负责页面交互，components 负责复用 UI，router 负责地址与准入，store 负责身份及跨页状态，types 保存已有接口类型。utils 当前同时含传输、业务请求和展示工具，后续将进入整理范围的请求抽到业务 API 模块。

后端 api/routers 负责 HTTP 入口，permission_context 统一解析授权，api/db 提供连接。skills 负责确定性分析和问策；etl 负责加工数据；scripts 负责初始化、迁移、启动和检查。后台管理不能以工具脚本或前端隐藏按钮替代权限验证。

## 五、关键业务调用

### 5.1 查询与证据

用户选择范围和统计周期，提交查询后，页面把已应用条件发送到服务端。服务端解析当前工作身份，过滤明细范围或比较范围，再查询与聚合。页面展示指标、图表和名单，证据下钻继承当前对象与条件，并再次接受服务端鉴权。

跨学院聚合对比与学生明细是不同权限语义。能看到其他学院的汇总值，不能据此推定可以打开其他学院学生名单。

### 5.2 报表与导出

九张报表共用页面，根据报表定义切换条件、列和统计结果。查询形成的结果与快照信息用于导出；导出请求必须使用已应用条件，服务端重新验证权限和快照。页面不能把尚未提交的筛选值用于导出当前结果。

### 5.3 决策简报与问策

四类 Skill 读取授权范围内的数据，生成包含对象、事实、严重程度、行动建议和证据的信号。系统合并与比较信号快照，形成简报。问策围绕专家、会话和信号上下文生成解释，证据窗口独立打开。

旧追踪接口保留兼容响应不等于产品仍支持办理闭环；管理动作以当前页面、专项需求与接口行为共同核对。

## 六、数据架构

来源文件和批次登记形成贴源依据；成绩尝试、课程结果、学籍异动、学生方案绑定和人员关系形成事实；课程通过、开课、团队和学生进度等形成聚合；指标定义登记正式口径；学校方案保存允许调整的管理参数和版本。

双库不是两套可随意混算的数据。旧模型、V2 模型以及学期源库可能覆盖不同人群和时间范围，必须逐指标确认来源，不能直接相加。真实、部分真实、推导、演示数据需要保留来源标识。

新增指标登记在 `sys_metric_definition`，页面引用在 `sys_metric_page_binding`。旧 `sys_kpi_config` 是兼容展示配置，不能作为新增正式定义的替代来源。

完整技术说明见 [3.2 数据库与指标](3-技术文档/新增-3.2-数据库与指标.md)。
