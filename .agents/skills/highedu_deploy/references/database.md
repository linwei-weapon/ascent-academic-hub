# 数据库更新

## 操作与范围

| 调用 | 行为 |
| --- | --- |
| `database preview <迁移路径>` | 只读检查并输出执行计划；不创建记录表、不备份、不运行变更 SQL |
| `database apply <迁移路径>` | 对指定迁移完成检查、备份、执行记录及验证；不是执行目录下任意 SQL 的通配入口 |
| `database status` | 查询连接目标、已有迁移记录及异常状态；记录不存在时如实报告 |

占位路径由用户提供或从明确需求定位。迁移 SQL 可以位于独立仓库，按[代码来源](source.md)获取指定分支的固定提交，以仓库相对路径定位文件，不依赖个人盘符。单独 `database` 默认预览。创建或修改本 Skill 不授权执行任何数据库变更。

只更新 RDS MySQL 8.0 的 `edu_analytics_v3`，账号为 `highedu_user`。`edu_source` 仅作只读核对，不申请写权限；不修改其他库、数据库账号或实例配置。数据库恢复不属于 `rollback`（它只回滚代码），需单独制定恢复计划。

## 1. 连接与迁移文件

- 从当前已确认的 RDS 配置取得地址；开发电脑使用 RDS 外网域名，服务器使用内网域名，端口 `3306`。不把 ECS 公网 IP 当作 MySQL 主机。共享 SSH 账号目前禁止端口转发，不能默认使用 SSH 隧道。
- 优先复用已有授权且可安全使用的连接；新连接密码由用户在客户端或终端输入。不读取项目文档中的明文密码来复制到命令、报告或 Skill，不把密码放入参数、连接 URL、仓库或本地临时文件。禁止在控制台打印完整配置。可使用已授权的服务端凭据，只在内存中使用。
- 工具无法安全交互认证时，先把 SQL、备份和执行方案准备好，再交给用户在 DBeaver/Navicat 或交互终端执行；依据实际结果继续验证，不能宣称已自动执行。
- 只读核对 `SELECT DATABASE(), CURRENT_USER(), @@hostname, @@port, VERSION();` 和 `SHOW GRANTS FOR CURRENT_USER();`，确认目标为指定 RDS 和业务库。权限不足报告缺项，不提升或放开权限。
- 先查 Java 项目已有 Flyway/Liquibase 或迁移机制，存在则沿用其目录、版本、校验和、锁与历史表，不引入第二套账本。没有现成机制时，将本次 MySQL SQL 和验证说明保存在 Java 项目明确的迁移目录；仅在本仓库交付 SQL 时使用 `code/scripts/sql/mysql/`，按版本命名。随代码保存，提交和推送按用户授权执行。
- 本仓库现有 Python/SQLite 迁移不能直接执行到 MySQL。不得把整库 dump 当作增量迁移，不得扫描目录后自动执行所有 `.sql`。

## 2. 预览与执行条件

输出一张表：目标实例及库、源提交、按顺序列出的迁移版本与路径、SHA-256、涉及表/字段、预计影响行数、锁表或停写需求、代码兼容性、备份范围、验证方法及恢复办法。

检查实际 SQL，包括 `USE`、跨库限定名、动态 SQL、存储过程和触发器可能产生的间接写入；无法确定影响时不执行。只指定默认库不能阻止 SQL 改其他库。不可用正则关键词筛选或 `EXPLAIN` 代替完整审阅，不可用“执行后回滚”来预览 DDL。

检查前置结构、目标结构、非空/唯一/外键约束、字符集及 MySQL 版本兼容性。数据更新先只读统计匹配行数及键范围，避免在聊天输出业务明细。幂等设计需区分“目标状态已完整存在”和“部分执行或结构不符”，不能简单忽略报错。

`apply` 已授权明确范围内的常规迁移，完成预览和检查后继续。对删除表/字段、清空表、批量删除或覆盖数据、可能截断数据的类型收缩，先准备可审阅的 SQL、影响数量和恢复方案；如果本轮尚未对这项具体影响取得确认，再说明原因并请求确认。SQL 内容或影响范围改变后重新核对授权。不要对每条普通 SQL 重复询问。

## 3. 备份

在首次写入（包括新增迁移记录表）之前完成并核对备份。按影响范围选择结构及受影响数据备份，或时间足够新的可用 RDS 备份；记录实例、库、时间、对象范围、位置/备份 ID 和恢复方式。范围或时间不满足时不能以“已有自动备份”代替。新建空表也要记录变更前不存在及相应结构基线。

优先保存在服务器受限目录或 RDS，数据库内容不放 Git、不默认下载到同事电脑；服务器目录 `0700`、文件 `0600`，核对空间与导出退出码、文件非空、散列和包含对象。需要的视图、触发器、过程等须纳入范围；权限不足或备份失败则停止更新。

使用 `mysqldump` 时按客户端版本选择参数，InnoDB 可用 `--single-transaction --quick --no-tablespaces --set-gtid-purged=OFF`；它不保证非事务表一致性，备份期间还要避免其他连接对相关表执行 DDL。涉及持续写入的数据更新要安排一致的备份/变更窗口，恢复不能覆盖备份之后的合法新数据。影响较大时先在独立临时库验证恢复；没有验证时如实注明。参见 [MySQL 备份说明](https://dev.mysql.com/doc/refman/8.0/en/mysqldump.html)。

## 4. 执行记录与并发

已有迁移工具按其机制执行。无工具时，每次准备具体迁移的执行方案，至少落实以下约定；本 Skill 不假定服务器已安装通用数据库发布命令，现有 `highedu-publish` 没有 `database` 子命令：

1. 同一持久数据库连接调用 `GET_LOCK('highedu:edu_analytics_v3:migration', 10)`，只有返回 `1` 才继续；`0`、`NULL` 或连接中断即停止。检查是否还有不遵守该锁的人工迁移，约定同事不要并行改表。此锁不会阻止普通应用写入，需要停写的迁移必须另行落实。
2. 首次 apply 可创建 `edu_analytics_v3.highedu_schema_migrations`，在预览中列出该项。先检查同名表是否已有其他用途或不兼容结构，不能覆盖。记录至少包括唯一版本、SQL SHA-256、源提交、实际执行人员（共享数据库账号不能区分个人）、开始/完成时间、状态和备份位置；不保存密码或业务明细。
3. 成功版本且校验和相同则跳过；相同版本不同 SQL、历史失败、执行中或结果未知时停止核对。不删除失败记录后重跑，不把“重复列/表”错误直接视为成功。
4. 执行前持久记录 `running`，按固定顺序执行 SQL，设置适当的连接和锁等待超时。无现成解析器时不要按分号简单拆分含过程/触发器的脚本。禁止用 `mysql --force` 忽略错误。客户端必须设置遇错停止；手动操作也须记录每步结果。
5. 对纯 InnoDB DML 使用事务，在提交前核对受影响行数和数据约束；已明确的预期不满足则回滚并停止。DDL 不承诺整批事务回滚。逐步核对后置条件，全部完成才将记录标记为 `applied`；业务验证仍可单独标记待验收。
6. 结束时在持锁连接释放锁；连接断开后重新核对账本及实际结构，不自动重连重试写入。不得用一次 `mysql -e GET_LOCK(...)` 退出，再启动另一连接迁移；前一连接退出锁就释放。参见 [MySQL 命名锁说明](https://dev.mysql.com/doc/refman/8.0/en/locking-functions.html)。

## 5. 验证、失败与恢复

核对新增/修改后的列、类型、索引和约束；校验受影响行数、重复键、空值、外键关系及迁移特有断言。再检查关联接口和页面；不能只凭 SQL 退出码或健康接口判定成功。只报告统计及必要结构，不输出学生等业务明细。

执行失败即停止后续迁移和依赖该迁移的代码发布。纯 DML 在事务仍有效时回滚；DDL 或断线后的结果可能部分落地，核对实际状态后标记 `failed` 或 `unknown`，记录已执行步骤和脱敏错误。已有代码不要无条件回滚到与新结构不兼容的版本。

MySQL 的许多 DDL 会隐式提交，不能靠包一层事务撤销整个脚本。恢复使用经审阅的补偿迁移，或先恢复至独立库核对后再制定切换/合并方案；原库覆盖恢复涉及现有新数据，不能自动执行。参见 [MySQL 隐式提交说明](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html)。

最终回报目标库、迁移版本及散列、备份位置、每步状态、验证结果、未完成事项和恢复方案。没有执行的明确标为“仅预览”；凭据未获得或用户尚未执行时明确标为“待执行”。代码回滚与数据库恢复分别报告。
