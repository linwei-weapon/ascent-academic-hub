# 高教代码与数据库部署

## 使用入口

- `$highedu_deploy frontend`：自动识别当前仓库、当前分支及前端模块后发布。
- `$highedu_deploy backend`：自动识别当前仓库、当前分支及 Java 后端模块后发布。
- `$highedu_deploy status`：只查看当前版本和服务状态。
- `$highedu_deploy rollback 版本目录名`：回滚到指定完整版本。
- `$highedu_deploy database preview 迁移文件路径`：只读检查 SQL、目标库、影响范围和历史执行情况，不执行备份或写入。
- `$highedu_deploy database apply 迁移文件路径`：检查、备份、执行业务库迁移并验证。
- `$highedu_deploy database status`：只读查看数据库连接及已有迁移记录。

从用户请求和上下文确定操作、代码来源。只说“部署”而未确定组件时先澄清，同时进行本地检查。用户明确要求发布时即已授权该次发布，无需重复确认；解释用法、创建 Skill 或查看状态不包含发布授权。

`database` 操作先读[数据库更新](references/database.md)，不走代码打包流程。未指定 preview/apply 时默认 preview；未提供迁移文件时检查项目已有迁移并询问范围，不自动执行找到的全部 SQL。普通代码发布不会附带数据库更新。

## 从仓库选择代码

前端、Java 后端和迁移 SQL 可以来自不同仓库。默认读取调用者当前项目的 Git 信息和构建文件，不要求用户先填写仓库地址或本地路径。记录“仓库＋分支/标签/提交＋模块相对目录”；具体规则见[代码来源](references/source.md)。

用户可选指定 `仓库=<Git克隆地址> 分支=<分支名> 模块=<相对目录>`，这些是对 Codex 的指令，不是必填参数或终端程序参数。当前仓库没有对应组件时，说明发现的技术栈，请同事在实际代码仓库内调用本 Skill，或提供另一个仓库；不继续追问原作者电脑上的旧路径。相对目录如 `code/backend-java` 或仓库根目录 `.` 可跨电脑复用。只有用户明确选择本地源码或现成 JAR 时才要求本地路径。

## 代码发布流程

1. 按[代码来源](references/source.md)定位调用者当前项目或明确指定的仓库。读取所选仓库 AGENTS，识别分支、固定实际提交，在隔离目录构建；默认当前分支的本地 HEAD，明确要求远端分支时才取对应远端版本。保留现有修改，不自动合并、提交或推送。有影响构建的未提交改动且是否发布这些改动不明时询问。
2. 按[发布操作](references/publish.md)检查登录、当前版本和健康接口。密码由用户在自己的交互终端输入，不索取到聊天、不写配置或日志、不使用命令行明文密码。已有授权连接可复用；工具无法让用户安全输入密码时，先完成构建，提供本次具体上传及发布命令，待用户执行后继续验证，不声称已自动完成。
3. 记录发布前版本、服务 PID、源提交和本次范围，核对新接口及数据库结构是否已由远端支持。Vite 的开发代理不会随静态包部署；涉及专家资源或指标核验等独立服务时检查服务器已有对应服务及 Nginx 路由，不能仅凭本地可用宣布线上支持。
4. 构建用户选定的组件，检查产物、计算 SHA-256，使用唯一版本号。上传后核对远端文件散列；不一致则停止发布。详细文件名、命令和限制见操作指南。
5. 切换前再次读取当前版本；如果其他人已发布，先核对新基线的兼容性和回滚目标，不能覆盖尚未核对的并发变更。使用服务器已安装的发布工具，不直接修改 `current`、sudo、SSH、Nginx 或共享配置。
6. 检查命令退出码和发布输出，再核对当前版本、服务状态、公网首页、入口引用的静态资源和 `/api/health`。前端发布核对线上 `index.html` 的 SHA-256 与本地产物一致；后端发布核对版本目录内 JAR 的散列一致。登录及关键业务页面用现有可用会话验证，需用户登录时说明待验收；健康接口成功不等于业务验收通过。
7. 回报仓库、分支/标签、完整提交、模块相对目录、发布版本、访问地址、实际验证结果、原版本和回滚命令。无凭据的记录可放已忽略的 `work/runtime/highedu_deploy/<版本号>/` 或系统临时目录；不记录密码、Token、数据库内容或服务器环境变量。

## 失败与范围控制

- 构建、权限、健康或校验失败时定位具体原因，不通过提权、放开权限、重建数据库或跳过检查来继续。发布遇到锁占用或 SSH 断线，先读取状态确认是否完成，不盲目重试切换；同一原因修复后仍失败则报告阻塞。
- 发布器在切换后的健康检查失败时尝试恢复原版本；必须再次检查当前链接和健康状态，不能把错误输出当成已恢复健康。
- 回滚会切换完整版本并重启 Java 后端，不回退数据库；先核对目标与当前数据库兼容。不要回滚覆盖其他人的后续发布。
- 工具每次只发布一个组件。用户要求前后端一起发布时先确认兼容的顺序；每一步验证通过再继续。这不是原子联合发布，第二步失败不能宣称整体完成。
- 代码发布不附带数据库迁移、菜单授权修改、账号管理或独立 Python 服务部署。用户要求数据库更新时使用独立 `database` 操作；代码与数据库一并更新时按兼容性确定顺序，记录两者独立结果。
