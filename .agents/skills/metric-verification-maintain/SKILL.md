# 指标核验维护

## 范围与依据

从本技能目录上溯三级定位仓库，以下路径均相对仓库根。先读 `AGENTS.md`，确认用户本次变更范围和已有修改。
当前首个模块是教学数据总览，以106需求为优先依据；已有源码、表字段和查询成功状态不能替代需求决定。

业务映射已采用 [metric-mapping-build](../metric-mapping-build/SKILL.md) 的3.1契约和数据库版本。需求/公式/字段来源/SQL变更先走该Skill的prepare、validate、publish；本Skill维护消费和证据校验，不再独立生成业务目录。旧catalog/queries仅用于首次迁移和明确的兼容展示，不能与生效版本并行维护口径；尚未生效时说明仍处显式旧模式。

只读取受影响条目及其上下文：

- [106需求原文](../../../文档/4-需求文档/4.1-教学数据总览/106-教学数据总览功能指标详细需求说明.md)：场景、公式、展示和验收条件。
- [需求与指标目录](../../../code/metric-verification/catalog/teaching-overview.json)：`module.definitionAuthority`、需求原文定位、指标变体及冲突处理。
- 当前已确认方案按目录 `conflicts` 中 `userConfirmed=true` 定位（C106-04、C106-08、C106-13），阅读其 `resolution` 和 `evidence` 指向的原文；保留用户决定，不重新套用旧确认书覆盖。
- [指标口径确认书](../../../文档/4-需求文档/公共需求/本科教学分析与学业决策支持平台需求调研及指标口径确认书V2.md)：只补充不与当前106及明确决定冲突的口径。
- [模块说明](../../../文档/4-需求文档/4.9-系统管理/指标核验模块说明.md)：连接配置、执行权限、持久化和当前未完成条件；凭据只从已有服务端配置读取，不输出或复制。

## 从需求改到可核验资产

1. 列出变更涉及的需求ID、场景、指标、数据层及SQL，区分需求改变、结构差异与实现缺陷。未确定的业务含义保留具体问题，不能用字段名猜定口径。
2. 经metric-mapping-build维护业务包与原106依据，保留稳定指标ID和未受影响关联；页面路径和旧requirement/scenario兼容锚点由消费适配器维护，不写入业务核心包。
3. 全部文档编辑完成后，按源文件最终字节更新 `module.sourceSha256`，复核覆盖范围及引用；`baselineSha256` 表示原登记基线，不能随当前文件哈希一起无理由覆盖。
4. SQL正文随映射包冻结并由服务读取；旧 `metric_verification_build_queries.py` 和 `metric_verification_build_indicator_system.py` 只作历史迁移/导出参考，禁止再执行它们覆盖业务资产。通过统一CLI检查新旧契约转换和指标消费，不维护第二份权威SQL。
5. 影响公式、筛选、去重、参数、范围或来源的修改要更新登记版本与SQL版本；保持SQL文件和登记文本一致。新增指标键必须有需求引用，不另设脱离需求的指标工作区。
6. 贴源结构由配置中的真实源库或贴源镜像核实；事实层、聚合层、SYS及字典职责以实际结构和业务语义共同确认。不同粒度的记录数不强求相等，SYS配置行数不能替代业务结果。
7. 无独立源端结果时登记 `applicability` 和 `directSource`；应用层从事实层复算时保留 `mappingMode=reference_from_fact` 及说明。参考值不能改名为应用实值；未解决条件保留 `remainingGaps` 和阻止执行原因。

## 分层验证

使用项目Python环境，从仓库根运行统一CLI和相关消费端测试；命令参数以实际帮助为准：

```text
python code/scripts/metric_mapping.py --help
python code/scripts/metric_mapping.py validate --package PACKAGE.json --report work/metric-mapping/validation.json
```

离线检查应核对需求引用、只读SQL、绑定参数、登记文本、字段依赖及代表性算术边界；SQLite隔离样本不证明MySQL或Oracle运行正确。
不要把历史检查器中的“候选全部禁止”等旧断言原样扩展到已确认条目；随明确口径和执行规则维护检查，不能仅删除失败断言。

真实库验证只使用本次已授权测试环境和只读连接：

- 先核对真实schema、枚举、业务标识及快照/批次，不从连接成功推定结构或语义一致。
- 通过已登记映射版本和既有授权服务执行，不用旧直连检查脚本绕过版本、身份及证据留存。
- 使用限定组织、学期、批次和样本，绑定参数；复核脚本自动选择的种子范围。脚本无法约束所需范围时先调整验证方式，不直接无参数扫全库。
- 技术探测可记录候选SQL是否执行成功，但不得据此提升 `executionApproval` 或生成“符合”。正式开放复算还需要需求口径、数据映射和执行条件成立。
- 同一SQL遇到结构缺失、权限拒绝或持续超时，记录原因并停止重复尝试该项；保留其余独立检查进度。报告和共享映射包只存摘要与证据引用，不落学生原始明细和凭据。授权核算的必要原始输入及结果保存于核验专用执行记录，供服务鉴权回读；不依赖历史业务批次重取。

## 关联、旧证据与交付

核验后端位于 `code/backend/metric_verification/`，前端位于 `code/frontend/src/views/admin/system/metric-verification/`，DTO/API在同名 `types/metricVerification.ts` 与 `api/admin/metricVerification.ts`。
业务页面→指标场景→需求出处→三层→SQL保持关联；新增参数应支持适当候选值和手填，不自动选择统计时点或业务规则。多个需求共用章节号时按具体条目绑定，不直接取第一条。分母、分布档位和规则输入作为指标内部依据，不全部变成主清单任务。
复核需求校验值、SQL版本/校验值及 `current` 判定：变更后的旧证据应标过期，历史记录仍可读，不能继续用于新“符合”判断；不要删除旧证据来掩盖变更。
根据改动运行相关后端测试、前端构建/类型检查，并走查选指标、读参数、执行、录入真实对照、保存、刷新回看证据和无权限/条件不足路径。单值复算可从持久化执行带入；新增输出字段或单位时同步 `evidence_import.py`，只读取当前身份、场景和定义的完整单行结果。保存时重新核对绑定值及所有组成项，不以客户端草稿替代SQL证据；不把取数时间当业务截至时点，也不把记录数或应用参考带入为实际指标。手工真实对照可不引用内部SQL，但须记录双方值、单位、来源、时间、范围和比较规则；差异由服务端计算。条件变更清空旧结果与证据选择，旧意见保留为历史，不能跨场景继承符合。
含指标的“符合”须由核验人员对照当前定义、同范围真实证据和实际表现判断；查询成功、登记覆盖、参考复算以及构建通过都不是业务验收通过。

更新同一模块说明与指标口径确认书中的名称、计算逻辑、用途、来源、边界和核查路径，不另建同主题完成报告；数量由当前登记统计，不复制本技能中的固定总数。
交付说明列明受影响条目、已完成验证、仍缺证据及旧结果失效范围；不附带部署、提交、修改个人技能配置或写入教务源库。
